## 2. Root Cause Analysis & Architectural Remediation

### 2.1 [P0] Peer Resolution: Negative ID Misclassification (`-123` Basic Group vs `-100...` Channel)
* **Location:** [`internal/telegram/resolver.go:137-147`](file:///home/dhimas/any/random/ultroid-go/internal/telegram/resolver.go#L137-L147)
* **The Problem:**
  ```go
  if id < 0 {
      channelID := id
      str := strconv.FormatInt(id, 10)
      if strings.HasPrefix(str, "-100") {
          channelID = parsed
      } else {
          channelID = -id // <--- BUG!
      }
      return &tg.InputPeerChannel{ChannelID: channelID}, nil
  }
  ```
  Telegram supergroups and broadcast channels use `-100<ID>`. Legacy basic groups (and Bot API chat IDs) use negative integers **without** `-100` (e.g. `-12345`). Slicing `-12345` into `channelID = 12345` and returning `&tg.InputPeerChannel{ChannelID: 12345}` causes all basic group operations (ban, mute, pin, send, schedule) to fail with `CHANNEL_INVALID`.
* **The Fix:**
  - If `strings.HasPrefix(str, "-100")` $\rightarrow$ Channel/Supergroup (`&tg.InputPeerChannel{ChannelID: parsed, AccessHash: hash}`).
  - If `id < 0` without `-100` $\rightarrow$ Basic Group (`&tg.InputPeerChat{ChatID: -id}`).
  - If `id > 0` $\rightarrow$ Try user first, then basic chat (`&tg.InputPeerChat{ChatID: id}`).

### 2.2 [P0] Peer Resolution: False Success & Fabricated AccessHash
* **Location:** [`internal/telegram/resolver.go:82, 160`](file:///home/dhimas/any/random/ultroid-go/internal/telegram/resolver.go#L82)
* **The Problem:**
  `ResolveUser` and `ResolveChat` return `&tg.InputPeerUser{UserID: uid}` (with `AccessHash: 0`) and `&tg.InputPeerChannel{ChannelID: channelID}` (with `AccessHash: 0`) when peers cannot be resolved from memory, storage, or network. The caller receives `err == nil` and assumes resolution succeeded, only to crash at the RPC layer.
* **The Fix:**
  - Introduce typed `PeerRef`:
    ```go
    type PeerKind uint8
    const (
        PeerUser PeerKind = iota
        PeerChat
        PeerChannel
    )
    type PeerRef struct {
        Kind       PeerKind
        ID         int64
        AccessHash int64
    }
    ```
  - When resolving users or channels, if no valid access hash can be acquired, return explicit error `core.ErrAccessHashMissing` / `core.ErrNotFound` rather than fabricating an invalid `InputPeer`.

### 2.3 [P0] Lifecycle: Dispatcher & Addon Runtimes Never Stopped in `App.Shutdown`
* **Location:** [`internal/app/shutdown.go:11-46`](file:///home/dhimas/any/random/ultroid-go/internal/app/shutdown.go#L11-L46)
* **The Problem:**
  - `a.client.Dispatcher().Stop(ctx)` is never invoked. The dispatcher's `peerQueue` background workers continue writing to SQLite (`storage.Save`, `storage.SaveEntity`) while `a.db.Close()` is executing, causing data races and use-after-close errors.
  - `a.addonMgr.ShutdownRuntimes()` is never invoked, leaving external addon child processes orphaned.
  - `callbackStore` and `inlineEngine` cleanup is only deferred in `Run()`.
* **The Fix:**
  Implement strict shutdown sequencing in `App.Shutdown`:
  ```text
  1. Quiesce (reject new updates, claims, commands)
  2. Dispatcher.Stop(ctx) (drain peerQueue, wait workers)
  3. Scheduler.Stop()
  4. AddonManager.ShutdownRuntimes()
  5. PluginManager.ShutdownWithContext(ctx)
  6. EventBus.Close() (drain events)
  7. CallbackStore.Stop() & InlineCache.Stop()
  8. RateLimiter.Close()
  9. Database.Close() (safe, zero lingering DB workers)
  10. Logger.Sync()
  ```

### 2.4 [P0] Context: Missing `Source` Field & Fragile String Prefix Inference
* **Location:** [`internal/core/context.go:65-78`](file:///home/dhimas/any/random/ultroid-go/internal/core/context.go#L65-L78), [`internal/core/executor.go:49-52`](file:///home/dhimas/any/random/ultroid-go/internal/core/executor.go#L49-L52)
* **The Problem:**
  - `core.Context` does not have a `Source` field. Handlers cannot tell if they are executing interactively, from a scheduler, or via system.
  - `executor.go:Execute` determines source using `strings.HasPrefix(ctx.CorrelationID, "sched-")`. An arbitrary correlation ID like `"sched-test"` causes interactive commands to be flagged as scheduled.
* **The Fix:**
  - Add `Source ExecutionSource` to `core.Context`.
  - Expand `ExecutionSource`: `ExecutionInteractive`, `ExecutionScheduled`, `ExecutionAssistant`, `ExecutionAddon`, `ExecutionSystem`, `ExecutionAutomation`.
  - Propagate `exec.Source` directly into `ctx.Source`.
  - Discard correlation prefix inspection in favor of explicit `ctx.Source`.

### 2.5 [P0] Addon: IPC Reader Goroutine Leak on Timeout
* **Location:** [`internal/addon/ipc.go:184-214`](file:///home/dhimas/any/random/ultroid-go/internal/addon/ipc.go#L184-L214)
* **The Problem:**
  In `callLocked`, a goroutine is launched with `line, err := r.stdout.ReadBytes('\n')`. When `select` selects `<-ctx.Done()`, the function returns, but the goroutine remains permanently blocked on `ReadBytes('\n')`. Repeated timeouts spawn leaking goroutines.
* **The Fix:**
  - Restructure IPC reading to prevent goroutine leaks on timeout. If context cancels, terminate the process or close pipes gracefully to unblock the reader.
  - Provide a state machine for `Manager`: `shuttingDown atomic.Bool` to reject new `StartRuntime` and `Call` during shutdown.
  - Run addons with an isolated working directory instead of inheriting the binary's directory.
  - Redirect addon stderr to structured logging rather than `os.Stderr`.

### 2.6 [P1] EventBus: Observability & Message Handler Priorities
* **Location:** [`internal/core/events.go:180, 243`](file:///home/dhimas/any/random/ultroid-go/internal/core/events.go#L180), [`internal/telegram/dispatcher.go:178-186`](file:///home/dhimas/any/random/ultroid-go/internal/telegram/dispatcher.go#L178-L186)
* **The Problem:**
  - EventBus drops events on full queue without counter or log (`default: // best-effort`).
  - Worker panic recovery swallows panics silently (`_ = recover()`).
  - Dispatcher executes message handlers in registration order. In `app.go`, `AFK` was registered before `PMPermit`, allowing AFK auto-replies to trigger on unapproved PMs before PMPermit can block or warn.
* **The Fix:**
  - Add atomic counters `droppedCount`, `panicCount`, `deliveredCount` to `EventBus`.
  - Log warnings on dropped events and recovered panics.
  - Add declarative handler priorities:
    ```go
    type HandlerPriority int
    const (
        PrioritySecurity      HandlerPriority = 10 // PMPermit, Blacklist
        PriorityModeration    HandlerPriority = 20 // Filters
        PriorityFeature       HandlerPriority = 50 // AFK, Voice
        PriorityObservability HandlerPriority = 90 // UserLog
    )
    ```
  - Sort message handlers by priority so security interceptors always precede feature handlers.

### 2.7 [P1] Telegram RPC: Stale Access Hash Recovery & Error Mapping
* **Location:** [`internal/telegram/service.go:26-43, 90-109`](file:///home/dhimas/any/random/ultroid-go/internal/telegram/service.go#L26-L43)
* **The Problem:**
  - When Telegram returns `PEER_ID_INVALID` or `CHANNEL_INVALID`, it usually means the cached access hash is stale. Goultroid maps this directly to `core.ErrNotFound` without attempting to invalidate the cache and re-resolve.
  - `RIGHTS_NOT_MODIFIED` is mapped to `core.ErrPermissionDenied` even though it indicates that the requested permissions are already set (idempotent success).
  - Generic network errors (EOF, connection reset, timeout) do not retry with exponential backoff.
* **The Fix:**
  - Treat `RIGHTS_NOT_MODIFIED` as idempotent `nil` (success).
  - In `ExecuteRPC`, on `PEER_ID_INVALID` / `CHANNEL_INVALID`, invalidate peer storage cache, re-resolve entity from network, and retry the RPC once.
  - Add transient network retry with backoff for connection errors.

## 3. Implementation Phasing Strategy

```text
Phase 1: Peer / Entity Resolution Hardening (P0)
├── Fix -123 Basic Group vs -100 Supergroup/Channel logic
├── Eliminate fabricated InputPeerUser{AccessHash: 0} fallbacks
├── Add PeerRef, PeerKind, and source tracking
└── Canonical username normalization in storage

Phase 2: Closed-Loop Lifecycle & Shutdown (P0)
├── App.Shutdown invokes Dispatcher.Stop() and AddonManager.ShutdownRuntimes()
├── Quiescing state preventing new work during shutdown
└── Centralize interaction caches shutdown in App.Shutdown

Phase 3: Execution Context & Middleware (P0/P1)
├── Context.Source field & expanded ExecutionSource enum
├── Remove "sched-" string prefix heuristic
└── Source-aware rate limiter keys

Phase 4: Addon Process & IPC Hardening (P0/P1)
├── Fix IPC reader goroutine leak on context timeout
├── Manager shutdown state (reject work when stopping)
└── Working directory isolation and stderr capture

Phase 5: EventBus Observability & Dispatcher Priorities (P1)
├── EventBus drop and panic metrics
└── Declarative handler priorities (Security -> Moderation -> Feature -> Observability)

Phase 6: Telegram RPC Resilience & Recovery (P1)
├── Idempotent RIGHTS_NOT_MODIFIED
├── Stale access hash invalidation and one-shot re-resolution
└── Transient network retry with backoff
```
