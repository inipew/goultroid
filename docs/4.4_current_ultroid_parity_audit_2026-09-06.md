# GoUltroid — Current Ultroid Parity & Full Implementation Audit

> **Audit date:** 2026-09-06  
> **GoUltroid repository:** `inipew/goultroid`  
> **Audited branch:** `main`  
> **Audited HEAD:** `69be68d3c8d9c102e19fca29145edf23689ded27`  
> **Reference:** `TeamUltroid/Ultroid` `main`  
> **Purpose:** audit the actual current implementation, behavior, architecture, bugs, missing functionality, and feature parity.

---

## 0. Executive conclusion

GoUltroid **is not yet functionally equivalent to Ultroid**.

It is important to define the target correctly:

> GoUltroid should **not** translate Python Ultroid line-by-line into Go. It should implement the same user-facing capabilities using a Go-native architecture: strongly typed domain models, reusable services, explicit lifecycle management, bounded concurrency, durable state, testable interfaces, and safe Telegram/OS integrations.

The current project has a reasonably good foundation for that target, especially around:

- command routing;
- permissions;
- middleware/interceptors;
- SQLite persistence;
- scheduler durability and leases;
- Telegram peer caching;
- media/storage abstractions;
- plugin registration;
- callback/inline framework scaffolding;
- resource guards;
- structured logging;
- a single shared command executor.

However, the project currently has a large gap between **framework/scaffolding** and **real end-user functionality**.

Several components are currently only partial implementations or placeholders. Some are particularly dangerous because their names and documentation imply production functionality while the implementation does not actually provide it.

The most important examples are:

1. **Voice chat uses `NewMockBackend()` in production wiring.** Therefore VC playback/join/leave is not a real Telegram voice-chat implementation.
2. **Addon installation only stores metadata.** It does not download, validate, load, register, execute, unload, or update executable addon code.
3. **Assistant inline/callback routing is wired with `nil` Telegram service.** The framework can dispatch, but handlers requiring Telegram operations cannot function correctly.
4. **Scheduled commands construct a synthetic outgoing message with `Message.ID = 0`.** Commands relying on `EditOrReply`, replies, target resolution, or message deletion can therefore fail or behave differently from normal commands.
5. **Scheduled commands bypass `GroupOnly`/`PrivateOnly` filtering because the synthetic message is marked outgoing.** This can allow a scheduled group-only command to execute outside its intended scope.
6. **Any sudo user can cancel or inspect history of a scheduled job by numeric ID without chat/creator authorization.** This is an authorization flaw.
7. **`.exec` uses a shell command string rather than direct argv execution.** It creates command-injection risk if the command is reachable with untrusted or insufficiently constrained input.
8. **The Docker build uses Go 1.24 while `go.mod` requires Go 1.27.** The published Docker build contract is therefore inconsistent with the module requirements.
9. **The latest normal CI run before the current lifecycle-repair commit was failing.** The current `main` commit has no corresponding normal CI result, so the current tree should not be considered CI-verified.
10. **The rate limiter is instantiated but not integrated into the command/update path.** The framework exists but does not enforce the declared policy.
11. **Broadcast is capped by the Telegram `GetDialogs` implementation at 30 dialogs even though the plugin asks for 100.** This makes the advertised broadcast scope incorrect.
12. **User logging workers are started as unmanaged goroutines and use `context.Background()`.** There is no lifecycle-aware shutdown/drain mechanism.
13. **Moderation warnings are reset even when the threshold action fails.** This loses active warning state after a failed mute/kick/ban.
14. **The current feature set is far smaller than the current Ultroid plugin ecosystem.** Many major areas—chat actions, greetings, force-subscribe, chatbot, AI, media tooling, PDF, QR, stories, search, Google Drive, YouTube/Twitter utilities, advanced sticker tools, VC tools, and many others—are absent.

### Overall assessment

| Area | Current state | Assessment |
|---|---|---|
| Core architecture | Strong foundation | Good |
| Command framework | Implemented | Good, but needs more semantics |
| Permissions | Implemented | Good foundation; scheduled path needs hardening |
| Telegram messaging | Mostly implemented | Several peer/access-hash gaps |

| Scheduler | Advanced foundation | Good design, several correctness/security issues |
| Media | Partial | Real transcoding exists, ecosystem incomplete |

# 2. Current architecture: what is already good

## 2.1 Command router

`internal/core/router.go` provides:

- normalized command names;
- aliases;
- batch registration;
- duplicate detection;
- quoted arguments;
- escaped characters;
- raw argument preservation.

This is a better long-term foundation than copying Ultroid's decorator model literally.

### Recommendation

Keep this architecture. Add higher-level semantics rather than replacing it.

Required future command metadata should include:

- incoming/outgoing policy;
- reply requirement;
- group/private/channel policy;
- target type;
- required Telegram permissions;
- cooldown/rate-limit class;
- whether command is scheduler-safe;
- whether command is assistant-safe;
- whether command can run from inline callback;
- idempotency requirements.

---

## 2.2 Permission model

`internal/core/permissions.go` provides owner/sudo/regular permission resolution.

This is a good basis for Go-native authorization.

The problem is not the base model; the problem is that some execution paths bypass normal command semantics, especially scheduled commands.

### Required invariant

Every command execution must carry an explicit execution principal:

```text
Interactive owner
Interactive sudo
Interactive regular user
Scheduled owner
Scheduled sudo
Internal system task
Assistant user
Addon/system capability
```

A synthetic `IsOutgoing=true` message must never be used as a substitute for authorization context.

---

## 2.3 SQLite durability

The database layer is one of the stronger parts of the project.

The scheduler already has:

- persistent jobs;
- execution history;
- claim tokens;
- leases;
- retry attempts;
- durable state transitions;
- retry handling for SQLite locking;
- transaction-based completion/failure state updates.

The latest scheduler hardening also explicitly recognizes that external Telegram effects are **at-least-once**, not exactly-once.

That is the correct conceptual model.

### Remaining requirement

Scheduled Telegram side effects need an idempotency strategy where possible. A lease can fence stale database workers, but it cannot undo a Telegram message already sent before a crash.

---

## 2.4 Peer cache

The peer cache architecture is sensible:

```text
Telegram entities
       ↓
bounded queue
       ↓
SQLite peer storage
       ↓
resolver
```

The bounded worker pool is preferable to creating an unbounded goroutine per update.

However, command paths still need to consistently resolve access hashes before constructing Telegram `InputPeer` values.

---

## 2.5 Storage/media abstraction

The storage and media services are correctly separated from plugins.

This is exactly the right direction for a Go-native implementation.

The following architecture should be retained:

```text
Plugin
  ↓
Domain service
  ↓
Process runner / Storage / Downloader
  ↓
External tool
```

Do not put ffmpeg/yt-dlp/shell details directly into Telegram command handlers.

# 3. Critical implementation bugs

## P0-01 — Docker Go version is incompatible with `go.mod`

### Evidence

- `go.mod` declares Go `1.27`.
- `Dockerfile` uses `golang:1.24-alpine`.

### Impact

The Docker build contract is inconsistent with the module requirement.

A clean Docker build using the declared base image cannot be treated as supported.

### Fix

Use a Go 1.27 image or a deliberately compatible toolchain image.

Also pin the build environment consistently across:

- Docker;
- GitHub Actions;
- local development documentation;
- release workflow.

### Acceptance

```text
docker build .
  -> success

go test ./...
  -> success
```

---

## P0-02 — `.exec` is shell-based and creates command-injection risk

### Location

`internal/services/process/service.go`

### Problem

The process runner uses shell execution and constructs a command string from arguments.

That is unnecessary for a Go process abstraction.

### Correct implementation

Use:

```go
exec.CommandContext(ctx, executable, args...)
```

instead of:

```text
shell + strings.Join(args)
```

### Why this matters

The process runner is a privileged capability. If any future plugin passes user-controlled input to it, shell metacharacters can become code execution.

### Required architecture

```text
Command
  ↓
validated capability
  ↓
argv []string
  ↓
exec.CommandContext
```

No shell unless a specific feature explicitly requires a shell, and then it must use a narrowly controlled command template.

---

## P0-03 — Scheduled command context is semantically invalid

### Location

`internal/scheduler/engine.go` → `executeCommand`

### Current synthetic message

The scheduled command creates approximately:

```text
Message.ID = 0
Message.IsOutgoing = true
ReplyToID = 0
```

### Problem

Many existing commands use `EditOrReply()`.

Normal behavior:

```text
incoming command
  -> reply or edit depending on message direction
```

Scheduled behavior currently becomes:

```text
scheduled command
  -> IsOutgoing=true
  -> Edit
  -> Message.ID=0
  -> invalid Telegram edit
```

Therefore scheduler support is not command-compatible.

### Additional impact

Commands depending on:

- reply message;
- target user from reply;
- command message deletion;
- album context;
- message entities;
- topic metadata;
- outgoing/incoming semantics;

can behave incorrectly.

### Correct design

Introduce an explicit execution source:

```go
type ExecutionSource int

const (
    SourceInteractive ExecutionSource = iota
    SourceScheduled
    SourceAssistant
    SourceSystem
)
```

Then make response behavior explicit:

```text
Command execution context
 ├── Principal
 ├── Source
 ├── Chat
 ├── Peer
 ├── Optional trigger message
 ├── Optional reply message
 └── ResponsePolicy
```

A scheduled command should not pretend to be an outgoing Telegram message.

---

## P0-04 — Scheduled commands bypass GroupOnly/PrivateOnly semantics

### Root cause

The scheduled context sets:

```text
IsOutgoing = true
```

The command executor/filter logic treats outgoing messages as exempt from some normal chat filters.

### Impact

A command marked `GroupOnly` or `PrivateOnly` can execute through a scheduled context even when the actual destination does not match the command's declared policy.

### Fix

Never use `Message.IsOutgoing` as a scheduler authorization bypass.

Command policy must be evaluated independently:

```text
CommandPolicy
       +
ExecutionContext
       ↓
PolicyDecision
```

For scheduled commands, enforce the destination chat type from the persisted job.

---

## P0-05 — Scheduler cancellation/history lacks ownership authorization

### Location

`plugins/scheduler/scheduler.go`

The plugin accepts:

```text
.cancelschedule <id>
.schedhistory <id>
```

The engine then operates on the numeric job ID directly.

### Problem

`Cancel()` deletes by job ID without validating:

- current chat;
- creator ID;
- owner override;
- sudo authorization scope.

`JobHistory()` similarly retrieves by job ID without a creator/chat authorization check.

### Impact

A sudo user who knows another job ID can manipulate or inspect a schedule outside the current chat.

### Fix

Use scoped operations:

```go
CancelScheduledJob(ctx, requester, chatID, jobID)
GetScheduledJobHistory(ctx, requester, chatID, jobID)
```

Authorization rules:

```text
Owner
  -> global control

Sudo
  -> current chat + jobs they are allowed to control

Regular user
  -> no scheduler access unless explicitly enabled
```

The database query itself should enforce scope, not only the plugin.

---

## P0-06 — Voice chat is a mock backend in application wiring

### Location

`internal/app/app.go`

Current production construction uses:

```text
voiceBackend := voiceSvc.NewMockBackend()
```

### Impact

The voice plugin may expose commands that appear functional, but the underlying voice-chat implementation is not a real Telegram voice-chat transport.

This is not feature parity with Ultroid's VC ecosystem.

### Fix

Implement a real backend behind an interface:

```text
VoiceBackend
  ├── Join
  ├── Leave
  ├── Play
  ├── Pause
  ├── Resume
  ├── Stop
  ├── Seek
  ├── Queue
  └── Volume
```

Possible implementation choices must be evaluated for Telegram MTProto voice-chat compatibility, media pipeline requirements, and long-running session lifecycle.

Until then, the feature should be explicitly labeled experimental/unsupported instead of production-ready.

---

## P0-07 — Addon manager does not implement a real addon runtime

### Locations

- `internal/addon/manager.go`
- `plugins/addon/addon.go`

### Current behavior

The manager loads/stores addon metadata/manifests and capability information.

It does not provide the full lifecycle expected from an addon ecosystem:

```text
fetch
↓
verify
↓
install
↓
load
↓
register commands
↓
register callbacks/inline handlers
↓
run
↓
unload
↓
update
↓
rollback
```

### Impact

The feature is an addon registry/metadata layer, not a functioning dynamic addon ecosystem.

### Correct Go-native approach

Do not load arbitrary Go plugins directly unless portability and ABI constraints are explicitly accepted.

Prefer a sandboxed external addon protocol, for example:

```text
GoUltroid
   │
   ├── capability broker
   │
   ├── IPC/RPC
   │
   └── addon process
          ├── commands
          ├── callbacks
          └── lifecycle
```

This allows capability restrictions, version negotiation, crash isolation, and safe unload/restart.

---

## P0-08 — Assistant inline/callback execution receives `nil` Telegram service

### Location

`internal/assistant/client.go`

The assistant callback/inline handlers call the generic framework with a nil service.

### Impact

The same inline/callback handlers that work from the userbot dispatcher can fail when executed from the assistant bot if they require Telegram API operations.

### Fix

The assistant needs its own service adapter:

```text
Assistant Telegram client
        ↓
AssistantTelegramService
        ↓
Inline/Callback Engine
```

Do not pass `nil` and rely on handlers not needing Telegram operations.

# 4. Important correctness bugs

## P1-01 — Scheduler starts before Telegram client readiness

`App.Run()` starts the dispatcher and scheduler before `client.Run(ctx)` establishes the authenticated Telegram session.

A due job can therefore be claimed before the Telegram service is ready.

### Correct lifecycle

```text
DB ready
↓
Telegram connect/auth
↓
self identity resolved
↓
peer resolver ready
↓
dispatcher ready
↓
scheduler ready
↓
assistant ready
```

The scheduler should not execute external Telegram actions before a readiness gate is satisfied.

---

## P1-02 — Scheduler catch-up is at-least-once and can duplicate external side effects

The current implementation correctly documents this risk.

However, catch-up can execute multiple Telegram actions for missed intervals.

Example:

```text
interval = 1h
bot offline = 6h
catch-up = 3
```

Potentially:

```text
send
send
send
```

This may be correct for some jobs and wrong for others.

### Recommendation

Add per-job misfire policies:

```text
skip
run-once
catch-up-N
coalesce
```

For messages, default to `run-once/coalesce`.

For automation commands, require an explicit policy.

---

## P1-03 — Lease expiration can duplicate Telegram side effects

The scheduler uses a 90-second lease with 30-second renewal.

If a worker loses its lease after sending a Telegram message but before completing DB state, another worker can eventually execute the job again.

This is an unavoidable property of external side effects under crash recovery.

### Required mitigation

Add an idempotency key where possible:

```text
job_id + scheduled_execution_id
```

Persist an execution record before performing the external effect when the target API supports deduplication or when the application can safely detect its own prior effect.

At minimum, document the at-least-once contract for all scheduled command authors.

---

## P1-04 — Moderation warnings are reset after failed punishment

### Location

`internal/services/moderation/service.go`

At threshold:

```text
add warning
↓
count >= threshold
↓
action
↓
ResetWarnings()
```

The reset happens even if the action fails.

### Bad scenario

```text
3rd warning
↓
Mute API fails
↓
warning records reset
↓
user returns to 0 warnings
```

### Correct behavior

Only clear warnings after successful enforcement, or transition to an explicit enforcement-pending state.

```text
threshold reached
    ↓
try action
 ┌──┴──┐
success failure
  ↓      ↓
clear   retain
        + retry/log
```

---

## P1-05 — Broadcast dialog enumeration is inconsistent with plugin expectation

`plugins/broadcast/broadcast.go` asks for a larger dialog set, but the Telegram service implementation caps `GetDialogs()` at 30.

### Impact

Broadcast does not operate over the full dialog set expected by the plugin.

### Fix

Implement paginated dialog retrieval:

```text
GetDialogs(offset_id, offset_date, offset_peer, limit)
        ↓
iterate until exhausted
```

Then apply explicit policy:

- include groups;
- include supergroups;
- include channels;
- optionally include private users;
- exclude archived if configured;
- exclude blocked/forbidden destinations;
- respect Telegram flood limits.

---

## P1-06 — Broadcast cancellation has a potential stale-cancel race

The service keeps a single cancellation function.

If an old broadcast finishes after a new broadcast starts, the old cleanup path can clear state belonging to the new broadcast.

### Fix

Use a generation/token:

```text
broadcast ID
↓
cancel token
↓
cleanup only if token still owns active slot
```

---

## P1-07 — Userlog workers are unmanaged and use `context.Background()`

`plugins/userlog/userlog.go` starts 32 workers during construction.

There is no plugin shutdown mechanism that:

- stops the workers;
- closes the queue;
- drains pending logs;
- waits for completion.

Queued jobs also use `context.Background()` rather than the application lifecycle context.

### Fix

Give userlog a lifecycle:

```text
Start(ctx)
Stop(ctx)
```

Workers should use a derived application context and a bounded drain period.

---

## P1-08 — Rate limiter is instantiated but not integrated

`internal/app/app.go` creates a limiter with a defined policy, but command dispatch does not enforce it globally.

### Impact

The presence of the framework can create a false impression that rate limiting is active.

### Fix

Integrate it into command execution:

```text
incoming update
↓
parse
↓
permission
↓
rate limit
↓
cooldown
↓
command
```

Different command classes should have different policies.

---

## P1-09 — Telegram `SendMessage`/edit paths do not consistently guarantee access hashes

Forwarding explicitly performs peer preparation, but normal send/edit operations can be passed an `InputPeerUser`/`InputPeerChannel` with zero access hash.

This is especially fragile for:

- scheduled messages;
- AFK replies;
- userlog destinations;
- offline peer resolution.

### Fix

Centralize peer preparation:

```go
PrepareInputPeer(ctx, peer) (tg.InputPeerClass, error)
```

Every Telegram operation should use the prepared peer unless the operation is inherently self/chat-ID-only.

---

## P1-10 — `ResolveTargetUser()` accepts invalid negative numeric IDs

Numeric parsing checks for non-zero but does not reject negative values.

A negative number should not be treated as a valid Telegram user ID.

### Fix

Require:

```text
userID > 0
```

and return a typed invalid-target error otherwise.

---

## P1-11 — Event bus deletion events lose chat identity for normal message deletions

`OnDeleteMessages` publishes:

```text
ChatID = 0
```

because the update does not directly carry the chat ID.

That is understandable at the raw update layer, but it limits downstream functionality.

### Fix

Maintain a message-to-peer index or use update/entity context where possible.

At minimum, expose:

```text
ChatID optional
PeerUnknown bool
```

rather than treating `0` as a normal chat identity.

---

## P1-12 — Current `.update` implementation has a fragile executable replacement model

`plugins/system/system.go` builds into `bin/goultroid` and then restarts using `os.Executable()`.

This is fragile when GoUltroid is run through:

- `go run`;
- another wrapper executable;
- a container entrypoint;
- a symlinked launcher.

The executable being restarted may not be the newly built binary.

### Correct model

Use an explicit installation/update manager:

```text
fetch
↓
verify
↓
build temp binary
↓
atomic rename
↓
exec known installed binary
```

The running binary path must be a known deployment artifact, not inferred from the current process in every environment.

# 5. Infrastructure and lifecycle issues

## 5.1 Shutdown semantics are safer than before, but incomplete

The latest lifecycle hardening correctly avoids closing the database while scheduler workers may still be alive after a timeout.

That is an important improvement.

However, the resulting process-level contract must be explicit:

```text
Shutdown timeout
↓
return error
↓
process supervisor terminates process
```

Do not leave the application in a half-running state indefinitely.

Also add lifecycle management for:

- userlog workers;
- voice backend;
- assistant client;
- media/process jobs;
- addon workers;
- peer-cache workers;
- event bus;
- rate limiter/background cleanup.

---

## 5.2 Process runner resource policy needs stronger limits

Current process execution has a timeout and output-size limit, which is good.

Still required:

- process count metrics;
- CPU/resource policy where practical;
- temporary-directory quotas;
- child-process cleanup verification;
- cancellation tests;
- SIGTERM/SIGKILL escalation tests;
- disk quota accounting for transcoding;
- per-command concurrency classes.

A timeout alone does not guarantee that an external process tree is completely terminated.

---

## 5.3 Media service needs dependency discovery

Media conversion depends on ffmpeg being available.

The Docker image does not currently install the required media toolchain.

### Fix

At startup expose a capability report:

```text
ffmpeg: available/version
ffprobe: available/version
yt-dlp: available/version
python: available/version
```

Commands should fail with a precise dependency error instead of a generic process failure.

# 8. Telegram semantics that need a common abstraction

The current project has too much logic that directly constructs Telegram peers.

Introduce a common abstraction:

```text
PeerRef
 ├── UserID
 ├── ChatID
 ├── ChannelID
 ├── Username
 ├── AccessHash
 └── Kind
```

Then:

```text
PeerResolver
   ↓
ResolvedPeer
   ↓
Telegram adapter
```

A `ResolvedPeer` should be guaranteed to contain the information required for the requested operation.

Do not allow a command to silently continue with an access hash of zero if the target type requires one.

# 9. Command execution model should be upgraded

```text

├── Principal

├── ReplyMessage (optional)
├── Peer
├── Services

└── Deadline
```

This solves several current problems at once:

- scheduled commands;
- assistant commands;
- inline callbacks;
- ownership;
- reply semantics;
- audit logging;
- idempotency.

# 10. Security audit

## 10.1 Shell execution

**Severity:** Critical.

Replace shell-based process execution with direct argv execution.

---

## 10.2 Addon capabilities

The capability gate is a good idea, but capability checks must actually guard executable behavior.

Required capabilities should be explicit, for example:

```text
telegram.send
telegram.delete
telegram.admin
filesystem.read
filesystem.write
network.outbound
process.execute
database.read
 database.write
```

Dangerous capabilities must never be granted implicitly.

---

## 10.3 Scheduled authorization

A schedule is not itself an authorization grant.

Persist:

```text
created_by
created_in_chat
required_permission
command_name
command_policy_snapshot/version
```

At execution time, validate the job against the stored policy.

---

## 10.4 External URL downloads

Downloader features must protect against SSRF and local network access.

At minimum:

- block loopback;
- block RFC1918/private ranges unless explicitly allowed;
- block link-local;
- block metadata endpoints;
- validate redirects;
- enforce maximum response size;
- enforce content-type policy.

---

# 16. What should NOT be done

## Do not copy Python architecture

Do not create a Go equivalent of every Python decorator.

Instead:

```text
Ultroid feature
    ↓
behavioral contract
    ↓
Go domain service
    ↓
Go-native command/callback/inline adapter
```

## Do not create fake implementations

Examples that must be avoided:

```text
Voice backend = mock
Addon install = metadata only
Inline handler = registered but cannot answer
Feature command = returns "not implemented"
```

If a feature is not complete, mark it explicitly as experimental or unavailable.

## Do not make security depend on UI

Authorization must be enforced at the service/database boundary, not merely because the command is normally shown to the owner.

## Do not treat scheduler leases as exactly-once execution

The scheduler is at-least-once for external effects.

Design around that invariant.

# 18. Final verdict

## Current state

**GoUltroid is a promising Go-native foundation, but it is not yet an Ultroid-equivalent userbot.**

The most important distinction is:

```text
Architecture maturity
        !=
Feature parity
        !=
Production readiness
```

The project has several good architectural decisions, particularly around typed command infrastructure, SQLite durability, scheduler leases, bounded resource handling, and service separation.

But there are still several **P0 correctness/security issues** that should be fixed before expanding the feature set aggressively.

The largest feature gap is not one missing plugin; it is the missing **platform layer** for:

- chat events;
- assistant interactions;
- inline/callback UX;
- media tooling;
- external integrations;
- real voice chat;
- addon execution;
- rich moderation automation.

The recommended strategy is therefore:

```text
1. Fix correctness/security P0s
          ↓
2. Finish execution-context architecture
          ↓
3. Build event + interaction platform
          ↓
4. Build reusable media/download services
          ↓
5. Implement major Ultroid capability families
          ↓
6. Implement real VC + addon runtime
          ↓
7. Expand feature breadth
          ↓
8. Run full parity matrix + integration tests
          ↓
9. Claim parity only after acceptance criteria pass
```

**Do not convert Ultroid Python to Go. Build GoUltroid as a native Go implementation of the same behavioral capabilities.**

That is the correct long-term direction for this project.
