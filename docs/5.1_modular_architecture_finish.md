# Modular Architecture — Steps 9–12 Finish

This document records the final hardening pass after the feature-module refactor.

## Step 9 — Execution Context & Middleware

The canonical command execution path is `core.CommandExecutor`. It already composes recovery, correlation, logging, surface, permission, source-filter, cooldown, and timeout middleware before invoking a handler.

The separate `internal/execution` package remains transport-neutral and must not import features or the composition root. It provides the source/actor/capability vocabulary used to prevent feature-specific authorization logic from leaking into individual plugins.

### Invariants

- Authorization is evaluated at execution time.
- Surface availability is checked before the handler.
- Group/private/reply restrictions are centralized in executor middleware.
- Rate limiting and cooldown are applied before handler execution.
- Correlation IDs and recovery wrap the complete execution chain.
- Feature packages must not implement their own global authorization registry.

## Step 10 — Legacy Architecture Removal

The remaining `internal/database` feature-adjacent files are intentionally tracked by `TestLegacyFeatureDatabaseSurfaceIsExplicit`:

- `addon.go`
- `scheduler.go`
- `settings.go`
- `userlog.go`

These are the final migration targets. They must be moved behind their owning service boundaries before the legacy list can become empty. This branch does **not** delete them speculatively because doing so without updating every caller would create a behavior-breaking migration rather than an architectural cleanup.

Definition of done for Step 10:

1. Feature/service-specific SQL is owned by its service or feature package.
2. `internal/database` contains only generic DB primitives and migration infrastructure.
3. The explicit legacy list becomes empty.
4. All callers use the new owner APIs.
5. Fresh and upgraded databases produce identical functional state.

## Step 11 — Production Hardening

The existing application lifecycle enforces dependency-aware shutdown:

1. assistant client
2. Telegram dispatcher
3. scheduler
4. settings worker
5. addon runtimes
6. plugins
7. event bus
8. callback/inline state stores
9. rate limiter
10. database
11. logger

The critical invariant is that the database is closed only after background consumers have stopped.

Plugin shutdown is reverse-registration-order and message hooks are detached before plugin teardown.

## Step 12 — Final Acceptance

The architecture guard now additionally enforces:

- feature packages cannot import `internal/app`, `internal/application`, or `cmd`;
- feature packages cannot import sibling features;
- execution packages cannot import features or composition packages;
- feature packages cannot use `init()` for registration;
- the existing database legacy surface remains explicit and cannot silently grow.

CI acceptance remains:

```text
gofmt -l .
go vet ./...
go test -race ./...
go run ./tools/featuregen && git diff --exit-code -- internal/app/generated_modules.go
go build ./cmd/goultroid
```

A final production release must additionally pass the Step 10 legacy-removal gate. Until those four service-owned database surfaces are migrated, the project is **architecturally hardened but not yet at the final zero-legacy state**.
