# 4.7 PMPermit Fix — Hapus Setelah Approve, Auto-Allow Outgoing, Blokir Nyata

Date: 2026-09-06
Related: `docs/4.6_callback_inline_implementation_audit_2026-09-06.md`, `plugins/pmpermit/*`, `internal/services/pmpermit/*`, `internal/database/pmpermit.go:62`, `internal/telegram/service.go:1164`

## 1. Konteks & Masalah

PMPermit adalah security gate untuk PM: `pending → approved|blocked`, `warn_count` via `IncrementPMWarn:86`, `maxWarns=4`. Riset `profiler:12f431` menemukan 3 bug P0:

**Bug1 — Approved tidak menghapus pesan:** `plugins/pmpermit/pmpermit.go:51` `handleApprove` & `service.go:48` `Approve` hanya `SetPMStatus approved + ResetPMWarn`, `service.go:60` `HandleIncomingPM` `SendMessage` warn/block discard `*tg.Message.ID:78` tanpa `DeleteMessage`. Efek warning `Warning x/4` menumpuk, clutter, leak state.

**Bug2 — Tidak auto-allow saat kita chat duluan:** `plugins/pmpermit/pmpermit.go:31` guard `if msg.Out {return nil}` drop semua outgoing; tidak ada `AutoApproveOutgoing`. Owner DM pertama ke userX → `IsApproved` tetap false → balasan userX kena warn/block padahal kita inisiator. Python Ultroid `outgoing=True` → approve.

**Bug3 — Block hanya pesan, tidak RPC:** `service.go:58` `Block` hanya `SetPMStatus blocked`, tidak `contacts.Block`. `plugins/pmpermit/pmpermit.go:64` `handleBlock` juga DB-only. `telegram/service.go:1164` `BlockUser` ( `ContactsBlock` + `ensureUserAccessHash`) tidak pernah terpanggil (grep 0). Status `blocked` di SQLite tapi Telegram blocklist kosong → spam tetap masuk, `warn_count` growth tak terbatas:32.

## 2. Tujuan

- G1: Outgoing private pertama owner → `AutoApprove(target)` sebelum lawan balas, termasuk `Unblock` jika sebelumnya blocked & `clearWarnMsgs`.
- G2: Setelah `approve` (manual/auto), hapus semua warning `Warning x/4` + `Limit Reached` yang pernah dikirim ke PM tersebut (best-effort `DeleteMessage`, cap 20).
- G3: `blockpm` / `warn>=4` auto-block memanggil nyata `contacts.Block` (dan `Unblock` saat `approve/disapprove`), dengan `InputPeerUser{AccessHash}` resolusi.
- G4: Tidak regresi: `IsEnabled`, `IsSudo/Owner` bypass `service.go:32`, `MarkMessageHandled` spam-suppress tetap, `maxWarns` unchanged, group PM tetap ignore `PeerUser` only.

## 3. Non-Goals

- Ubah `maxWarns` policy atau UI buttons inline (Fase 3).
- Persist warn IDs cross-DC tak terbatas — cap 20, best-effort.
- Group PM permit (tetap `PeerUser` only `pmpermit.go:32`).
- Quota/FloodWait tuning (reuse `retryOnFloodWait:89`).

## 4. Definisi Selesai (DoD)

- `.approve @user` dalam 2s → PM `user` bersih (0 warning), `GetPMRecord` `approved`, `deletedMsgIDs` di test terverifikasi, tidak ada `Limit Reached` lagi.
- Owner kirim PM pertama ke `userX` → `IsApproved(userX)==true` sebelum `userX` balas (test `msg.Out`).
- `warnCount==4` → `mock.blockedUserIDs` berisi `userID` + DB `blocked`, Telegram blocklist `ContactsBlock` terpanggil.
- `go vet ./...` clean, `go test ./...` PASS termasuk `pmpermit_test.go` baru.

## 8. Alur UX Baru

- **Outgoing first:** Owner → `PeerUser(target)` `msg.Out==true` → `AutoApproveOutgoing` → DB `approved`, cache, `Unblock` + `DeleteWarn` → balasan target `IsApproved true` → allow, tidak warn.
- **Incoming warn 1-3:** `IsApproved false` → `IncrementPMWarn` → `SendMessage Warning x/4` (ID disimpan) → `MarkMessageHandled` suppress command.
- **Incoming warn 4:** `BlockWithPeer` → `contacts.Block` + `SendMessage Limit Reached` (+ID disimpan) → thereafter `IsApproved` false tapi `StatusBlocked`, setiap `UpdateNewMessage` tetap `true` tapi tidak increment lagi? `IncrementPMWarn` akan terus `warn_count+1` diatas 4; mitigasi: `HandleIncomingPM` sebelum increment cek `Status==blocked` → langsung `SendMessage blocked` tanpa increment.
- **Approve:** `SetPMStatus approved` + `ResetPMWarn` + `DeleteMessage(warnIDs)` + `ClearWarnMsgIDs` + `UnblockUser` → PM bersih.
- **Blockpm manual:** `.blockpm @user` → `BlockWithPeer` + `contacts.Block` → appear in Telegram blocklist.

## 11. Risiko & Mitigasi

- **AccessHash miss** → `DeleteMessage` gagal `PEER_ID_INVALID`; mitigasi `ensureUserAccessHash` fallback ke storage/peers.Manager, best-effort log Warn, Approve tetap sukses DB.
- **msg.Out selfID ambiguity** → jika `ownerID!=selfID` (bot vs owner beda), auto-allow salah target; mitigasi `IsSudoID` check + `target!=ownerID`.
- **FloodWait on Block/Delete burst 20** → `retryOnFloodWait` 5s retry, batch `DeleteMessage` 100 per call `service.go:372` (50), cap 20 aman.
- **JSON column corrupt** → `GetWarnMsgIDs` `json.Unmarshal` error → return `[]`, log Warn, continue.
- **Race double approve** → `ClearWarnMsgIDs` idempotent, `DeleteMessage` second call `MESSAGE_ID_INVALID` ignore via `mapTelegramError`.

## 12. Alternatif Dipertimbangkan

- **Tabel terpisah** `pmpermit_warn_messages` — lebih SQL-normal tapi butuh JOIN + prune index; ditolak untuk cap kecil.
- **Memory-only** — hilang restart; dipilih hybrid JSON+memory untuk audit.
- **Handler kedua** `HandleOutgoingMessage` terpisah — ditolak, satu handler dengan `msg.Out` branch lebih sederhana dan FIFO order sama.
