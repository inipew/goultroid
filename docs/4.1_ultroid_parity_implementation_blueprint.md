# GoUltroid — 4.1 Ultroid Parity Implementation Blueprint

> Dokumen implementasi lanjutan berdasarkan audit `docs/4_ultroid_parity_audit.md`.
>
> Tujuan dokumen ini bukan sekadar daftar fitur yang belum ada, tetapi blueprint teknis: **kode apa yang harus dibuat, di mana diletakkan, bagaimana alurnya, kontrak API-nya, tujuan tiap komponen, target behavior, acceptance criteria, dependency, prioritas, dan urutan implementasi**.
>
> Audit baseline: 2026-09-06
> Repository: `inipew/goultroid`
> Reference ecosystem: `TeamUltroid/Ultroid`

---

## 1. Tujuan Utama

Target GoUltroid bukan membuat clone Python Ultroid secara literal. Targetnya adalah:

> **Membangun userbot Telegram Go yang memiliki feature coverage setara/lebih baik dari Ultroid, tetapi dengan architecture Go-native, strongly typed, testable, durable, resource-bounded, dan production-oriented.**

Karena itu setiap fitur Ultroid harus dipetakan menjadi **capability platform** terlebih dahulu, kemudian plugin.

Jangan melakukan pendekatan:

```text
Ultroid command A -> copy command A
Ultroid command B -> copy command B
Ultroid command C -> copy command C
```

Gunakan:

```text
Ultroid feature
      ↓
Domain capability
      ↓
Reusable service/API
      ↓
Event / middleware / framework
      ↓
Thin plugin
      ↓
Command / inline / callback
```

Contoh:

```text
.inline search
.inline callback
.inline pagination
.inline media
       ↓
Inline Engine
       ↓
Inline Service
       ↓
Individual inline plugins
```

# 3. Prinsip Implementasi Wajib

## 3.1 Plugin tidak boleh menjadi framework

Plugin hanya menggabungkan capability yang sudah tersedia.

Buruk:

```go
func (p *Plugin) Handle(...) {
    // resolve peer
    // call telegram API
    // download media
    // create temp file
    // execute ffmpeg
    // send result
    // cleanup
}
```

Target:

```go
func (p *Plugin) Handle(ctx *core.Context) error {
    result, err := p.media.Convert(ctx.Context(), request)
    if err != nil {
        return err
    }
    return ctx.Messages().SendMedia(ctx, result)
}
```

## 3.2 Semua side effect harus context-aware

Tidak boleh menggunakan:

```go
context.Background()
```

di execution path hanya untuk menghindari cancellation.

Gunakan:

```go
ctx.Ctx
```

atau derived context dengan deadline yang jelas.

## 3.3 Resource budget wajib

Setiap feature yang berpotensi mahal harus mempunyai:

- timeout;
- concurrency limit;
- size limit;
- disk budget;
- memory budget bila relevan;
- cancellation;
- cleanup.

## 3.4 Permission dievaluasi saat execution

Jangan menyimpan authorization sebagai fakta permanen di job/plugin state.

Target:

```text
request
  ↓
resolve principal
  ↓
permission policy
  ↓
execute
```

## 3.5 UNKNOWN != FAILED

Error transient harus dibedakan dari permanent failure.

Minimal taxonomy:

```text
ErrInvalidInput
ErrPermissionDenied
ErrNotFound
ErrUnavailable
ErrTimeout
ErrRateLimited
ErrResourceLimit
ErrConflict
ErrInternal
```

# 5. Phase 0.2 — Scheduler Hardening

File:

```text
internal/scheduler/engine.go
internal/database/*scheduler*
```

Current scheduler sudah memiliki claim, lease, fencing token, retry, heartbeat, dan history. Jangan rewrite.

## 5.1 Bounded concurrency

Target:

```text
claim 10
   ↓
queue
   ↓
N workers
```

Tambahkan config:

```go
SchedulerMaxConcurrency int
SchedulerQueueSize      int
```

Default contoh:

```text
max concurrency = 4
queue = 32
```

Nilai final harus configurable.

## 5.2 Lease-loss cancellation

Target:

```text
worker owns token
       ↓
heartbeat fails
       ↓
leaseLost = true
       ↓
cancel job context
       ↓
handler stops
```

Jangan mengandalkan fencing token saja untuk side effects eksternal. Fencing melindungi state DB; cancellation melindungi external side effects.

## 5.3 Misfire policy

Tambahkan:

```go
type MisfirePolicy int

const (
    MisfireSkip MisfirePolicy = iota
    MisfireRunOnce
    MisfireCatchUp
)
```

Recurring job harus menyimpan policy secara eksplisit.

### Acceptance criteria

- scheduler tidak menciptakan goroutine tanpa bound;
- job yang kehilangan lease menerima cancellation;
- restart tidak duplicate secara tidak terkendali;
- recurring job punya deterministic misfire behavior.

# 7. Phase 0.4 — Process / Exec Safety

Target service:

```text
internal/services/process/
```

Interface:

```go
type Runner interface {
    Run(ctx context.Context, req Request) (Result, error)
}
```

Request harus mempunyai:

```go
type Request struct {
    Args       []string
    Timeout    time.Duration
    MaxOutput  int64
    WorkingDir string
    Env        []string
}
```

Jangan menerima arbitrary shell string jika tidak diperlukan.

Jika `.exec` membutuhkan shell syntax, gunakan explicit opt-in:

```go
Shell bool
```

dan tetap batasi:

- timeout;
- stdout;
- stderr;
- process count;
- environment;
- working directory.

### Acceptance criteria

- process selalu berhenti ketika context timeout;
- output tidak dapat menghabiskan memory;
- child process tidak menjadi zombie;
- secret tidak masuk log;
- concurrent `.exec` dapat dibatasi.

# 29. Security Boundary

Target permission harus berkembang dari level command menjadi capability.

Current permission tiers seperti Everyone/Owner/Sudo sudah menjadi foundation yang baik. Middleware saat ini juga fail-closed untuk command non-public ketika permission provider tidak tersedia. fileciteturn22file0

Target:

```text
Owner
Sudo
Admin
Moderator
Everyone
```

Tetapi untuk addon/service gunakan capability:

```text
telegram.read
telegram.send
telegram.delete
media.download
process.execute
storage.write
scheduler.create
scheduler.cancel
```

Ini penting terutama untuk external addons.

# 30. Testing Strategy

Feature parity tidak boleh dinilai dari "command bisa jalan sekali".

## Unit tests

Wajib untuk:

- router parser;
- permissions;
- middleware;
- rate limiter;
- scheduler state machine;
- retry classification;
- peer resolver;
- callback parser;
- inline pagination;
- media budget;
- filename sanitization;
- URL/SSRF validation.

## Integration tests

Wajib:

```text
SQLite
scheduler + executor
router + middleware
peer DB
media pipeline
callback state
```

## End-to-end

Minimal:

```text
Telegram update
 ↓
Dispatcher
 ↓
Router
 ↓
Middleware
 ↓
Plugin
 ↓
Telegram response
```

## Race tests

Jalankan:

```bash
go test -race ./...
```

terutama setelah refactor scheduler, event bus, caches, registries, dan inline state.

# 36. Definition of Done per Feature

Setiap fitur baru hanya dianggap selesai jika semua terpenuhi:

### Code

- [ ] service boundary jelas;
- [ ] plugin tipis;
- [ ] context-aware;
- [ ] no uncontrolled goroutine;
- [ ] no hidden global state;

### Tests

```text

  ↓
```

Bukan:

```text
  ↓

  ├── FFmpeg
  ├── HTTP
  ├── peer resolution
  ├── permissions
  ├── scheduler
  └── Telegram raw API
```

Jika plugin mulai mempunyai terlalu banyak dependency langsung, berarti capability tersebut harus dipindahkan ke `internal/services`.

# 38. Indikator Keberhasilan

GoUltroid dapat dianggap mendekati parity apabila:

1. command coverage mayoritas core Ultroid sudah tersedia;
2. inline/callback ecosystem sudah menjadi first-class capability;
3. media/downloader ecosystem sudah reusable;
4. assistant dapat berjalan sebagai mode resmi;
5. moderation/security ecosystem lengkap;
6. localization tersedia;
7. addon model tersedia;
8. voice/music backend tersedia atau memiliki documented supported backend;
9. scheduler dan core execution tetap reliable di bawah load;
10. semua feature besar mempunyai tests dan resource budgets;
11. deployment/release/CI sudah reproducible.

# 39. Final Direction

**Jangan mengejar jumlah command. Kejar jumlah capability.**


Satu `ModerationService` dapat melahirkan:


Dengan pendekatan ini, parity akan tumbuh cepat **tanpa membuat codebase menjadi kumpulan command yang saling duplikasi**.
