**Document:** `docs/4.7.md`  
**Date:** 2026-09-06  
**Status:** Approved Blueprint & Architecture Plan  
**Target System:** GoUltroid PM Permit Subsystem (`plugins/pmpermit`, `internal/services/pmpermit`, `internal/database`, `internal/telegram`)  
**Reference Implementations:** TeamUltroid (`plugins/pmpermit.py`), Telegram MTProto Specification (`contacts.block`, `contacts.unblock`, `messages.deleteMessages`)

---

## 1. Executive Summary

Subsystem **PM Permit** (Private Message Access Control & Anti-Spam Shield) pada GoUltroid saat ini bertindak sebagai penjaga gerbang pesan pribadi (DM/PM) agar akun owner tidak dibanjiri spam oleh pengguna yang belum diizinkan.

Meskipun fondasi pemfilteran pesan masuk dan pencatatan status peringatan pada SQLite telah berjalan, audit mendalam menemukan **3 (tiga) kecacatan fatal pada logika interaksi dan keamanan** yang menurunkan fungsionalitas dan pengalaman pengguna (UX) secara drastis dibandingkan standar userbot (khususnya referensi Ultroid Python):

1. **Pesan Approval dan Peringatan Tidak Dihapus Pasca Approve / Allow**:
   - Pesan peringatan (`👋 Hello! I haven't approved you... Warning X/Y`) yang telah dikirimkan ke pengguna tidak pernah dilacak ID-nya (`msg.ID` dibuang dengan blank identifier `_, _`).
   - Ketika pengguna di-approve (baik via perintah `.approve`/`.allow` maupun tombol interaksi), pesan-pesan peringatan lama tersebut tetap tertinggal di chat.
   - Pesan konfirmasi persetujuan dari bot (`✅ Approved user ... for private messaging.`) juga ditinggalkan secara permanen di dalam obrolan pribadi tanpa mekanisme penghapusan otomatis (*delayed self-destruction*), sehingga mengotori riwayat percakapan antara pemilik akun dan lawan bicaranya.
2. **Tidak Ada Auto-Allow Saat Pemilik Akun Memulai Percakapan Duluan (Outgoing PM)**:
   - Interceptor pesan PM permit di level plugin secara sengaja melakukan pengecekan `if msg.Out { return nil }` dan langsung mengabaikan seluruh pesan keluar.
   - Dampaknya, ketika pemilik userbot berinisiatif mengirim pesan pribadi ke seseorang (*"Halo Mas Budi, ini berkas yang kemarin"*), sistem tidak menandai Mas Budi sebagai pengguna yang disetujui. Begitu Mas Budi membalas (*"Baik, terima kasih"*), bot justru membalas pesan Mas Budi dengan peringatan spam PM permit (*"Warning 1/4! Anda belum disetujui untuk mengirim pesan"*). Perilaku ini sangat mengganggu dan tidak logis untuk sebuah userbot.
3. **Pemblokiran Palsu / Hanya Pesan Teks (Tidak Ada Tindakan Blokir Nyata di Telegram MTProto)**:
   - Ketika seorang spammer melampaui batas peringatan (`warnCount >= maxWarns`) atau saat owner menjalankan perintah `.blockpm`, fungsi `Service.Block` hanya melakukan `UPDATE` status string `'blocked'` ke tabel SQLite `pm_permit_records`.
   - Bot mengirim pesan teks: `⛔ PM Permit Limit Reached... You have been blocked`, tetapi **tidak pernah memanggil Telegram MTProto API `contacts.block` (`svc.BlockUser`)**.
   - Di aplikasi resmi Telegram (Android/iOS/Desktop/Web), kontak tersebut **sama sekali tidak terblokir**. Spammer masih bisa melihat status online, membaca bio/profil, melakukan panggilan suara/video Telegram ke pemilik akun, dan terus mengirim pesan yang memicu respons teks bot berulang-ulang.

Dokumen ini menyajikan analisis akar masalah teknis, riset komparatif terhadap implementasi referensi Ultroid, tujuan dan target spesifikasi perbaikan, arsitektur desain baru, serta rencana implementasi bertahap untuk menutup ketiga masalah tersebut secara tuntas dan aman.

## 2. Root Cause Analysis (RCA)

### 2.1 RCA 1: Kegagalan Pembersihan Pesan Peringatan dan Pesan Konfirmasi Persetujuan

#### Penelusuran Kode Sumber
Pada `internal/services/pmpermit/service.go`:
```go
// Baris 77-78
warnMsg := fmt.Sprintf("👋 <b>Hello!</b>\n\nI haven't approved you for private messaging yet...\n\n⚠️ <b>Warning %d/%d</b> (%d remaining before block)", warnCount, maxWarns, remaining)
_, _ = svc.SendMessage(ctx, peer, warnMsg)
```
- Nilai balik `*tg.Message` dari `svc.SendMessage` yang berisi nomor ID pesan Telegram yang baru saja dikirim (`sent.ID`) diabaikan begitu saja menggunakan blank identifier `_, _`.
- Struct `PMPermitRecord` maupun map in-memory di `Service` tidak memiliki field untuk mencatat ID pesan peringatan yang aktif.
- Akibatnya, ketika pengguna mengirim 3 pesan beruntun tanpa izin, bot mengirim pesan peringatan 1/4, lalu 2/4, lalu 3/4. Ketiga pesan tersebut menumpuk di chat pribadi.

Pada `plugins/pmpermit/pmpermit.go`:
```go
// Baris 55-56
if err := p.svc.Approve(ctx.Ctx, target, reason, 0); err != nil { return ctx.EditOrReply(...) }
return ctx.EditOrReply(fmt.Sprintf("✅ <b>Approved</b> user <code>%d</code> for private messaging.", target))
```
- Ketika owner menjalankan `.approve` / `.a`, fungsi `p.svc.Approve()` hanya memutasi database SQLite dan cache RAM. Tidak ada pemanggilan operasi penghapusan pesan peringatan sama sekali.
- Perintah `.approve` dieksekusi menggunakan `ctx.EditOrReply(...)`. Karena pesan perintah berasal dari akun sendiri (`c.Message.IsOutgoing == true`), pesan `.approve` diedit menjadi `✅ Approved user...` dan menetap di chat selamanya. Tidak ada penjadwalan timer pembersihan (*auto-destruct*) setelah konfirmasi terbaca.

### 2.2 RCA 2: Ketiadaan Auto-Allow pada Inisiasi Percakapan Keluar (Outgoing PM)

#### Penelusuran Kode Sumber
Pada `plugins/pmpermit/pmpermit.go`:
```go
// Baris 30-31
func (p *Plugin) HandleIncomingMessage(ctx context.Context, e tg.Entities, msg *tg.Message, isCommand bool, cmdName string) error {
	if p.svc == nil || !p.svc.IsEnabled() || msg == nil || msg.Out { return nil }
```
- Parameter `msg.Out` menandakan apakah pesan dikirim oleh akun pemilik userbot (`true`) atau oleh lawan bicara (`false`).
- Pengecekan baris 31 langsung keluar (`return nil`) jika `msg.Out == true`.
- Dispatcher (`internal/telegram/dispatcher.go`) sebenarnya memanggil daftar interceptor `messageHandlers` untuk **seluruh update pesan baru** (`OnNewMessage`), termasuk pesan keluar yang dikirim oleh owner dari aplikasi Telegram HP maupun Telegram Desktop.
- Karena `pmpermit` langsung menghentikan eksekusi pada `msg.Out`, sistem tidak memiliki logika untuk mendeteksi:
  1. Apakah pemilik akun sedang mengirim pesan pribadi ke seorang pengguna?
  2. Apakah pesan tersebut merupakan teks percakapan biasa (bukan eksekusi perintah bot dengan prefix titik, misal `.ping`)?
  3. Apakah pengguna tersebut saat ini belum berstatus approved?
- Karena inisiatif chat dari pemilik akun tidak dicatat, pengguna tersebut tetap berstatus `pending` di mata `pmpermit`. Ketika pengguna membalas sapaan pemilik akun, pembalasan tersebut dianggap sebagai pesan asing yang tidak diizinkan.

### 2.3 RCA 3: Pemblokiran Palsu Tanpa Pemanggilan API MTProto Telegram (`contacts.block`)

#### Penelusuran Kode Sumber
Pada `internal/services/pmpermit/service.go`:
```go
// Baris 58
func (s *Service) Block(ctx context.Context, userID int64, reason string) error {
	s.approvedCache.Delete(userID)
	if reason == "" { reason = "blocked by user" }
	if s.db == nil { return fmt.Errorf("pm permit database is unavailable") }
	return s.db.SetPMStatus(ctx, userID, StatusBlocked, reason, nil)
}

// Baris 75
if warnCount >= maxWarns {
	_ = s.Block(ctx, senderID, "exceeded pm warning threshold")
	_, _ = svc.SendMessage(ctx, peer, "⛔ <b>PM Permit Limit Reached</b>\n\nYou sent too many unapproved messages without waiting. You have been blocked from private messaging.")
	return true, nil
}
```
- Perhatikan baris 58: Fungsi `Block` hanya menerima `userID int64`. Tidak ada parameter `peer tg.InputPeerClass` atau pemanggilan ke Telegram API. Satu-satunya aksi yang dilakukan adalah memanggil query SQL `s.db.SetPMStatus(ctx, userID, StatusBlocked, reason, nil)`.
- Pada baris 75 saat batas peringatan tercapai, bot hanya memanggil `s.Block` lokal, lalu mengirim pesan peringatan teks bahwa pengguna telah diblokir.
- Padahal pada `internal/telegram/service.go` baris 1165:
```go
func (s *Service) BlockUser(ctx context.Context, peer tg.InputPeerClass) error {
	if s.api == nil {
		return fmt.Errorf("%w: api is not initialized", core.ErrInternal)
	}
	peer = s.ensureUserAccessHash(ctx, peer)

	_, err := retryOnFloodWait(ctx, func() (bool, error) {
		return s.api.ContactsBlock(ctx, &tg.ContactsBlockRequest{ID: peer})
	})
	return err
}
```
- Dan pada interface `core.TelegramServicer` (`internal/core/context.go` baris 55):
  `BlockUser(ctx context.Context, peer tg.InputPeerClass) error` dan `UnblockUser(ctx context.Context, peer tg.InputPeerClass) error` **sudah tersedia lengkap dengan flood wait retry dan resolusi access hash**.
- Namun, implementasi `pmpermit` tidak pernah menghubungkan pemblokiran lokal ke metode `BlockUser` tersebut! Akibatnya, pemblokiran bersifat kosmetik belaka. Spammer tidak pernah terblokir di infrastruktur server Telegram.

### Kesimpulan Riset untuk Desain GoUltroid:
1. **Penyimpanan ID Pesan Peringatan**: Perlu ada mapping `chat_id -> warn_msg_ids` (disimpan pada cache memori atomik dan persistensi database). Ketika peringatan baru dikirim, peringatan lama dihapus; saat disetujui, semua peringatan dihapus.
2. **Pembersihan Otomatis Pesan Konfirmasi**: Pesan konfirmasi `.approve` / `.allow` harus memiliki masa hidup terbatas (*time-to-live*) sekitar 3-5 detik sebelum dihapus otomatis dari chat.
3. **Auto-Approve Pesan Keluar**: Setiap pesan keluar di private chat (`msg.Out == true` dan `!isCommand`) harus secara otomatis menandai pengguna tujuan sebagai `StatusApproved` dan menghapus pesan peringatan sebelumnya.
4. **Real MTProto Blocking**: Saat batas peringatan tercapai atau perintah `.blockpm` dijalankan, sistem wajib memanggil `svc.BlockUser(ctx, peer)` (`tg.ContactsBlockRequest`). Sebaliknya, saat pengguna yang pernah diblokir disetujui kembali via `.approve`, sistem harus memanggil `svc.UnblockUser(ctx, peer)` (`tg.ContactsUnblockRequest`).

## 4. Goals and Target Specifications

### 4.1 Tujuan (Goals)
1. Menjadikan subsystem PM Permit di GoUltroid bekerja dengan **kebersihan chat maksimal (Zero Clutter)**, di mana tidak ada pesan peringatan atau pesan konfirmasi approval yang mengotori obrolan pribadi setelah persetujuan diberikan.
2. Memberikan **pengalaman percakapan alami (Natural Conversation Flow)**, di mana percakapan yang diinisiasi oleh pemilik akun tidak akan pernah terganggu oleh peringatan anti-spam.
3. Menjamin **keamanan perlindungan akun riil (Genuine Anti-Spam Protection)** di level server Telegram, di mana spammer yang melanggar batas peringatan benar-benar diblokir dari kontak Telegram pengguna.

### 4.2 Target Spesifikasi (Target Specifications)

| Fitur / Komponen | Perilaku Lama (Defect) | Perilaku Baru (Target Parity) |
| :--- | :--- | :--- |
| **Tracking Pesan Peringatan** | ID pesan peringatan dibuang (`_, _`), pesan menumpuk di chat. | ID pesan peringatan dicatat (`last_warn_msg_id`). Peringatan sebelumnya diperbarui/dihapus sehingga hanya 1 peringatan aktif di chat. |
| **Pembersihan Pasca Approve** | Pesan peringatan tetap ada di chat lawan bicara. | Seluruh pesan peringatan yang pernah dikirim ke pengguna tersebut dihapus seketika saat di-approve. |
| **Pesan Konfirmasi `.approve`** | Menetap selamanya di chat pribadi. | Menampilkan pesan konfirmasi, lalu dihapus otomatis (*self-destruct*) setelah 4 detik. |
| **Outgoing Message (Chat Keluar)** | Diabaikan (`msg.Out -> return nil`). Pengguna tetap unapproved. | Otomatis mendeteksi inisiasi chat oleh owner (`msg.Out == true` & bukan command). Menyetujui user seketika (`AutoApprove`) & menghapus peringatan lama. |
| **Blokir Batas Peringatan** | Hanya kirim teks peringatan & ubah status SQLite. Kontak tetap bisa chat/telepon. | Mengirim pesan pemblokiran final, menghapus peringatan lama, dan **memanggil `svc.BlockUser` (`contacts.block`) di Telegram**. |
| **Perintah `.blockpm`** | Hanya update status SQLite. | Update status SQLite dan **memanggil `svc.BlockUser` di Telegram**. |
| **Persetujuan Ulang Kontak Terblokir** | Hanya ubah status SQLite. Kontak masih terblokir di Telegram. | Ubah status SQLite dan **memanggil `svc.UnblockUser` (`contacts.unblock`) di Telegram**. |

## 5. System Architecture & Interaction Design

### 5.1 Alur Interaksi Komponen

```text
========================================================================================
1. INCOMING UNAPPROVED PM FLOW
========================================================================================
Telegram Server ---> Dispatcher.OnNewMessage ---> pmpermit.HandleMessage
                                                       |
                          [msg.Out == false & !IsApproved]
                                                       v
                                          pmpermit.HandleIncomingPM
                                                       |
                         +-----------------------------+----------------------------+
                         | warnCount < maxWarns                                     | warnCount >= maxWarns
                         v                                                          v
          Delete Previous Warn Msg (if any)                         Delete Previous Warn Messages
                         |                                                          |
             Send New Warning Message                                  Send Final Blocked Message
                         |                                                          |
          Save WarnMsgID in RAM & Database                             Call svc.BlockUser(peer) [MTProto]
                                                                                    |
                                                                       Set PM Status 'blocked' in DB
                                                                                    |
                                                                       Spammer BLOCKED on Telegram!
```

```text
========================================================================================
2. OUTGOING PM (AUTO-APPROVE) FLOW
========================================================================================
Owner sends message in PM ---> Dispatcher.OnNewMessage ---> pmpermit.HandleMessage
                                                                 |
                                    [msg.Out == true & !isCommand & PeerUser & !IsApproved]
                                                                 v
                                                     pmpermit.AutoApprove
                                                                 |
                                            +--------------------+--------------------+
                                            |                                         |
                                            v                                         v
                              Delete Previous Warn Msg(s)                   Save Status 'approved'
                                            |                               (DB & in-memory cache)
                                            v                                         |
                               Chat Clean & Uninterrupted! <--------------------------+
```

```text
========================================================================================
3. MANUAL APPROVAL / ALLOW FLOW (.approve / .allow)
========================================================================================
Owner runs .approve ---> pmpermit.handleApprove
                              |
                              +---> Resolve Target User ID & Peer
                              |
                              +---> pmpermit.Service.Approve
                              |        |
                              |        +---> Save Status 'approved' (DB & cache)
                              |        +---> Reset PM Warnings to 0
                              |        +---> If previously blocked -> svc.UnblockUser(peer)
                              |        +---> Delete all tracked Warn Messages
                              |
                              +---> Edit/Reply "✅ Approved user ..."
                              |
                              +---> Schedule Auto-Delete after 4 seconds (time.AfterFunc)
                              |
                              v
                   Chat Pristine & Clean!
```

## 6. Detailed Technical Specifications

### 6.1 Layer Database (`internal/database`)

#### Migration 12: Tambah Kolom Pelacakan Pesan Peringatan (JSON Array)
Perbarui `internal/database/migrations.go` dengan menambahkan versi migrasi ke-12:
```sql
ALTER TABLE pm_permit_records ADD COLUMN warn_msg_ids TEXT NOT NULL DEFAULT '[]';
```
Kolom `warn_msg_ids` bertipe `TEXT` menyimpan array JSON dari integer message IDs (dibatasi maksimum 20 pesan terakhir secara FIFO) untuk menjamin pelacakan seluruh pesan peringatan aktif maupun pesan limit-reached tanpa memerlukan tabel relasi baru yang berlebihan.

#### Pembaruan `internal/database/pmpermit.go`
Tambahkan fungsi-fungsi database helper khusus:
1. `GetWarnMsgIDs(ctx context.Context, userID int64) ([]int, error)`:
   - Menjalankan `SELECT warn_msg_ids FROM pm_permit_records WHERE user_id = ?`.
   - Mengurai JSON array menjadi `[]int`. Jika data kosong atau `[]`, mengembalikan slice kosong `nil`.
2. `AddWarnMsgID(ctx context.Context, userID int64, msgID int) error`:
   - Membaca daftar ID saat ini, menambahkan `msgID` baru di akhir slice.
   - Membatasi panjang slice maksimal 20 item (`ids[len(ids)-20:]`).
   - Menyimpan kembali ke kolom `warn_msg_ids` dalam format string JSON.
3. `ClearWarnMsgIDs(ctx context.Context, userID int64) error`:
   - Mengosongkan daftar pesan peringatan dengan mengupdate kolom `warn_msg_ids = '[]'` saat user disetujui (`Approve`/`AutoApproveOutgoing`) atau status direset.

### 6.2 Layer Service (`internal/services/pmpermit/service.go`)

Tambahkan dependensi pelacakan in-memory dan integrasi API Telegram:

1. **Struktur `Service`**:
   ```go
   type Service struct {
       db            *database.DB
       svc           core.TelegramServicer
       svcFunc       func() core.TelegramServicer
       ownerID       int64
       perms         *core.Permissions
       logger        *zap.Logger
       enabled       bool
       maxWarns      int
       mu            sync.RWMutex
       approvedCache sync.Map
       
       // Track active warning message IDs per user: userID -> []int
       warnMsgs      sync.Map
   }
   ```

2. **Metode `TrackWarnMessage(userID int64, msgID int)` & `GetWarnMessages(userID int64) []int`**:
   - Menyimpan dan mengambil daftar ID pesan peringatan aktif yang telah dikirim ke pengguna tersebut.

3. **Metode `DeleteWarnMessages(ctx context.Context, peer tg.InputPeerClass, userID int64) error`**:
   - Mengambil ID pesan dari cache memori dan database (`last_warn_msg_id`).
   - Memanggil `svc.DeleteMessage(ctx, peer, msgIDs)`.
   - Mengosongkan catatan ID pesan setelah penghapusan berhasil.

4. **Metode `Block(ctx context.Context, peer tg.InputPeerClass, userID int64, reason string) error`**:
   - Menghapus user dari `approvedCache`.
   - Menyimpan status `StatusBlocked` ke database.
   - **Memanggil `svc.BlockUser(ctx, peer)`** ke server Telegram MTProto jika parameter `peer` tersedia.

5. **Metode `Approve(ctx context.Context, peer tg.InputPeerClass, userID int64, reason string, duration time.Duration) error`**:
   - Jika pengguna sebelumnya berstatus `StatusBlocked`, secara proaktif memanggil `svc.UnblockUser(ctx, peer)` ke server Telegram.
   - Memperbarui status menjadi `StatusApproved` di database dan cache.
   - Menghapus seluruh pesan peringatan pengguna via `DeleteWarnMessages(ctx, peer, userID)`.

6. **Pembaruan `HandleIncomingPM(ctx context.Context, peer tg.InputPeerClass, senderID int64)`**:
   - Sebelum mengirim pesan peringatan baru, jika sudah ada pesan peringatan sebelumnya, hapus pesan lama terlebih dahulu (sehingga tidak pernah ada lebih dari satu pesan peringatan bot di layar).
   - Simpan ID pesan peringatan yang baru dikirim ke cache dan database via `TrackWarnMessage`.
   - Saat `warnCount >= maxWarns`:
     - Panggil `DeleteWarnMessages` untuk membersihkan pesan peringatan bertingkat sebelumnya.
     - Kirim pesan pemblokiran final.
     - Panggil `s.Block(ctx, peer, senderID, "exceeded pm warning threshold")` yang mengeksekusi pemblokiran Telegram nyata (`contacts.block`).

### 6.3 Layer Plugin (`plugins/pmpermit/pmpermit.go`)

1. **Outgoing Message Interceptor & Auto-Approve**:
   ```go
   func (p *Plugin) HandleIncomingMessage(ctx context.Context, e tg.Entities, msg *tg.Message, isCommand bool, cmdName string) error {
       if p.svc == nil || !p.svc.IsEnabled() || msg == nil { return nil }
       
       peerUser, ok := msg.PeerID.(*tg.PeerUser)
       if !ok || peerUser == nil { return nil }
       
       targetUserID := peerUser.UserID
       peerInput := p.resolveInputPeer(e, peerUser.UserID)
              // Skenario A: Outgoing Message oleh Pemilik Akun (Auto-Approve)
        if msg.Out {
            // Guard 1: Jangan auto-approve jika pesan adalah command (.disapprove, .blockpm, dll.)
            if isCommand || cmdName != "" || strings.HasPrefix(msg.Message, ".") { return nil }
            // Guard 2: Jangan auto-approve jika pesan adalah pesan bot/peringatan PM permit sendiri
            if p.svc.IsPMPermitMessage(msg.Message) { return nil }
            if targetUserID == p.svc.OwnerID() || p.svc.IsSudoID(targetUserID) { return nil }
            // Guard 3: Abaikan jika ID pesan ini adalah pesan peringatan yang tercatat
            if p.svc.IsWarnID(targetUserID, msg.ID) { return nil }
            // Guard 4: Jangan auto-approve jika pengguna berstatus 'blocked'
            if p.svc.IsBlocked(ctx, targetUserID) { return nil }
            
            approved, err := p.svc.IsApproved(ctx, targetUserID)
            if err == nil && !approved {
                // Pemilik akun berinisiatif mengirim chat personal baru: Auto-Approve seketika
                _ = p.svc.AutoApproveOutgoing(ctx, peerInput, targetUserID)
            }
            return nil
        }
       
       // Skenario B: Incoming Message dari Lawan Bicara
       handled, err := p.svc.HandleIncomingPM(ctx, peerInput, targetUserID)
       ...
   }
   ```

2. **Delayed Auto-Delete pada Perintah `.approve` / `.allow`**:
   - Di `handleApprove`:
     - Eksekusi `p.svc.Approve(ctx.Ctx, peerInput, target, reason, 0)`.
     - Tampilkan konfirmasi menggunakan delayed delete helper:
       ```go
       return ctx.Messages().EditOrReplyWithDelay(fmt.Sprintf("✅ <b>Approved</b> user <code>%d</code> for private messaging.", target), 4*time.Second)
       ```
     - Dalam 4 detik, pesan konfirmasi `.approve` akan terhapus secara mandiri (*self-destruct*) dari riwayat obrolan.
   - Terapkan delayed auto-delete serupa pada perintah `.disapprove` dan `.blockpm` agar obrolan tetap bersih.

3. **Perbaikan `handleBlock`**:
   - Teruskan `peerInput` yang valid ke `p.svc.Block(ctx.Ctx, peerInput, target, reason)` sehingga eksekusi perintah manual `.blockpm` benar-benar memblokir pengguna di Telegram.

### 6.4 Helper Ekstensi Core (`internal/core/context_messages.go`)

Tambahkan helper `EditOrReplyWithDelay` pada `MessagesFacade`:
```go
// EditOrReplyWithDelay updates the trigger/response and schedules its deletion after the specified duration.
func (m *MessagesFacade) EditOrReplyWithDelay(text string, delay time.Duration) error {
	c := m.ctx
	if c == nil {
		return errors.New("context is nil")
	}
	if err := m.EditOrReply(text); err != nil {
		return err
	}
	if delay <= 0 || c.Svc == nil || c.PeerID == nil {
		return nil
	}
	targetID := c.LastResponseID
	if targetID == 0 && c.Message != nil && c.Message.IsOutgoing {
		targetID = c.Message.ID
	}
	if targetID > 0 {
		peer := c.PeerID
		svc := c.Svc
		time.AfterFunc(delay, func() {
			delCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
			defer cancel()
			_ = svc.DeleteMessage(delCtx, peer, []int{targetID})
		})
	}
	return nil
}
```

## 8. Test Matrix & Verification

### 8.1 Skenario Pengujian PM Permit

1. **Skenario 1: Pesan Peringatan Bertingkat Tunggal (Single Active Warn Message)**
   - *Input*: Pengguna asing mengirim pesan 1, lalu pesan 2, lalu pesan 3.
   - *Ekspektasi*: Bot mengirim peringatan 1. Saat pesan 2 datang, peringatan 1 dihapus dan digantikan peringatan 2. Saat pesan 3 datang, peringatan 2 dihapus dan digantikan peringatan 3. Di chat hanya tersisa 1 pesan peringatan aktif.

2. **Skenario 2: Penghapusan Peringatan Saat Disetujui (`.approve` / `.allow`)**
   - *Input*: Pengguna memiliki pesan peringatan aktif di chat. Pemilik akun menjalankan `.approve`.
   - *Ekspektasi*: 
     - Pesan peringatan yang ada di chat terhapus bersih via `svc.DeleteMessage`.
     - Pesan konfirmasi `✅ Approved user ...` muncul, lalu terhapus otomatis setelah 4 detik.
     - Chat menjadi bersih tanpa jejak sisa pesan bot.

3. **Skenario 3: Inisiasi Chat Keluar (Outgoing Message Auto-Approve)**
   - *Input*: Pemilik akun mengirim pesan pribadi pertama kali ke pengguna baru: *"Halo kawan"*.
   - *Ekspektasi*:
     - Sistem mendeteksi `msg.Out == true` dan `!isCommand`.
     - Pengguna baru otomatis berstatus `StatusApproved`.
     - Ketika pengguna baru membalas, bot **tidak mengirim peringatan apa pun** (`HandleIncomingPM` me-return `false`).

4. **Skenario 4: Pemblokiran Riil di Level Telegram MTProto (`contacts.block`)**
   - *Input*: Spammer terus mengirim pesan hingga mencapai batas `maxWarns` (default 4).
   - *Ekspektasi*:
     - Pesan peringatan lama dihapus.
     - Bot mengirim pesan final limit reached.
     - Database berstatus `StatusBlocked`.
     - **Panggilan `svc.BlockUser(ctx, peer)` berhasil dieksekusi**, memblokir ID spammer secara permanen di server Telegram.
     - Mock server / service mencatat panggilan ke `tg.ContactsBlockRequest`.

5. **Skenario 5: Pembukaan Blokir Saat Di-Approve Kembali**
   - *Input*: Pengguna yang sebelumnya berstatus `blocked` disetujui kembali via `.approve`.
   - *Ekspektasi*:
     - Sistem mendeteksi status lama `blocked`.
     - **Panggilan `svc.UnblockUser(ctx, peer)` berhasil dieksekusi** (`tg.ContactsUnblockRequest`).
     - Status database berubah menjadi `StatusApproved`.

## 9. Definition of Done (DoD)

Perbaikan subsystem PM Permit dinyatakan selesai apabila:
1. ID pesan peringatan bot berhasil dilacak dan dihapus secara otomatis sehingga tidak terjadi penumpukan peringatan di obrolan pribadi.
2. Seluruh pesan peringatan terhapus seketika saat pengguna disetujui (`.approve`/`.allow` maupun auto-approve).
3. Pesan konfirmasi perintah `.approve`, `.disapprove`, dan `.blockpm` memiliki timer penghapusan otomatis mandiri (*delayed self-destruction*).
4. Pemilik akun yang memulai percakapan pribadi secara otomatis menyetujui lawan bicara (*auto-approve on outgoing message*) tanpa intervensi manual.
5. Pemblokiran saat mencapai batas peringatan dan pemblokiran via `.blockpm` mengeksekusi API pemblokiran riil Telegram MTProto (`contacts.block`), serta membuka blokir Telegram (`contacts.unblock`) saat disetujui kembali.
6. Seluruh unit test pada `internal/services/pmpermit`, `plugins/pmpermit`, `internal/database`, dan `internal/core` lulus pengujian 100% tanpa regresi.
