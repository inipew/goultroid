# GoUltroid — Full Plugin & Addon Audit

> Audit date: 2026-09-08
> Repository: `inipew/goultroid`
> Reference: `TeamUltroid/Ultroid` and `TeamUltroid/UltroidAddons`
> Scope: first-party plugins, plugin lifecycle/registration, message hooks, callback/interactive integration, addon registry, addon runtime/IPC, capabilities, persistence, lifecycle, and Ultroid parity.

## Executive verdict

GoUltroid has a sound Go-native plugin architecture, but it is **not yet functionally equivalent to Ultroid**. The correct target is behavioral parity, not a line-by-line Python port.

The current first-party catalog contains 25 plugins:

```text
ping, help, alive, pin, forward, downloader, sudo, notes, afk,
admin, media, sticker, info, system, filters, fun, scheduler,
locks, blacklist, profile, pmpermit, broadcast, userlog, addon, settings
```

The plugin foundation is strong: commands are registered atomically, lifecycle hooks are explicit, execution sources are typed, callback state is durable, and message hooks can be prioritized.

The largest remaining gap is **feature coverage** and the addon ecosystem. Ultroid has a much broader plugin surface and a separate addon repository containing many independently loaded Python modules. GoUltroid currently has a manifest/registry plus an external-process IPC foundation for addons, but not yet the complete artifact installation, command registration, host capability RPC, restart supervision, and ecosystem workflow required for Ultroid-like extensibility.

## 1. Can Ultroid + UltroidAddons be recreated from zero?

**Yes, functionally.** Do not port Python implementation details. Port the user-facing behavioral contracts.

Recommended model:

```text
GoUltroid core
    |
    +-- first-party Go plugins
    |      typed Plugin contract
    |      command registry
    |      message hooks
    |      callback/inline handlers
    |
    +-- addon host
           manifest
           artifact store
           compatibility
           signature/hash verification
           isolated process
           JSON-RPC/JSON-lines protocol
           capability authorization
           supervisor
           command proxy registration
```

Ultroid's Python addons run in-process. GoUltroid should keep third-party code isolated in external processes rather than loading arbitrary code into the main userbot process.

### Plugin lifecycle

`internal/plugin.Manager` now correctly performs pre-check, validation, initialization outside the manager lock, then atomic router registration/commit. `core.Router.RegisterBatch` validates a complete command batch before mutating state.

The application wires the Telegram dispatcher into the manager before registering plugins, so `MessageHookPlugin` implementations such as AFK receive their hooks.

Application shutdown already stops addon runtimes before plugin shutdown and closes the database after background consumers. Any older document claiming otherwise is stale.

### Required quality gate for every plugin

- unique command/aliases;
- deterministic initialization;
- explicit owner/sudo/source/scope policy;
- canonical peer resolution and access-hash preservation;
- no display-ID arithmetic for MTProto peers;
- correct reply/media/topic context;
- no synthetic trigger message for scheduled execution;
- durable state where required;
- idempotent/cancellable background work;
- callback state scoped to the initiating user/chat;
- Telegram-safe long output.

## 3. Primary addon defect — fixed

### P0: ExternalRuntime startup deadlock

`internal/addon/ipc.go` held `ExternalRuntime.mu` across `Start()` and then called `handshake()`. The handshake called `callLocked()`, which tried to acquire the same mutex.

```text
Start
  -> lock r.mu
  -> handshake
      -> callLocked
          -> lock r.mu  // deadlock
```

A valid external addon therefore could not complete startup.

### Fix

`Start()` now holds the mutex only while constructing/publishing process state, unlocks before the blocking handshake, and calls `Stop()` if the handshake fails.

A regression test was added in `internal/addon/ipc_test.go` using a real executable fixture and a protocol-1 hello response.

This fix is already on `main`.

## 4. Addon audit

### Existing strengths

- YAML/JSON manifest parsing;
- manifest validation;
- version compatibility;
- capability allow-list;
- persistent addon registry;
- enable/disable/uninstall;
- isolated external process model;
- executable validation;
- optional SHA-256 verification;
- JSON-lines IPC;
- protocol handshake;
- runtime tracking;
- application shutdown of active runtimes.

### Major missing functionality

`.addon install` currently registers a manifest; it is not yet a complete artifact installer.

`AddonRecord` does not persist executable artifact path/digest, signature identity, runtime state, protocol version, command bindings, or artifact metadata.

`LoadInstalled()` restores capability registrations but cannot reconstruct external runtime processes because executable identity is not persisted.

Most importantly, manifest `Commands` are validated/displayed but are not converted into Go router command proxies. An addon declaring `foo` therefore does not automatically provide `.foo`.

That is the main functional blocker for an Ultroid-like addon ecosystem.

## 5. Addon upgrade design

### Phase A — artifact registry

Persist:

```text
artifact_path
artifact_sha256
signature
protocol_version
runtime_state
last_exit_code
last_started_at
last_stopped_at
restart_count
```

Treat installed versions/artifacts as immutable and use explicit upgrade transactions.

### Phase B — command proxy

```text
manifest command
    -> Go router proxy
    -> authorization
    -> addon manager
    -> ExternalRuntime.Call
```

The proxy should pass execution source, permission/scope, chat/peer context, args/raw args, reply metadata, cancellation, and correlation ID.

### Phase C — real capability RPC

Capabilities must be checked at host-operation boundaries, not merely stored in a gate.

Recommended mapping:

```text
telegram.send       -> telegram.send_message
telegram.read       -> telegram.get_message / resolve_peer
telegram.delete     -> telegram.delete_message
media.download      -> media.download
storage.write       -> storage.write
scheduler.create    -> scheduler.create
scheduler.cancel    -> scheduler.cancel
```

Do not add an unrestricted generic `host.call` method.

### Phase D — supervisor

Add health checks, handshake timeout, crash detection, bounded exponential restart, crash-loop suppression, persistent runtime state, graceful stop/hard kill, and failure of all pending IPC requests on process exit.

### Phase E — secure remote installation

```text
source
 -> staging download
 -> size/type validation
 -> digest/signature verification
 -> atomic artifact install
 -> manifest validation
 -> DB transaction
 -> runtime health check
 -> activation
```

Never execute an unverified downloaded artifact.

## 6. IPC follow-up upgrade

The deadlock fix makes startup functional, but the IPC design should later move from one reader goroutine per serialized request to a single stdout reader plus response-ID routing:

```text
stdout reader
     |
     v
response ID router
   /   |   \
 reqA reqB reqC
```

Every pending request gets its own channel. Process exit must fail all pending requests immediately. This allows future concurrent addon calls without protocol changes.

### Tier 3 — UltroidAddons

Port useful addons as Go-native plugins or external Go addons, not as a Python compatibility layer. Good early candidates are small utilities such as anime/animechan, astronomy, encoding/decoding, figlet/fonts, IMDB/search, Morse/code, OCR, inline search helpers, QR, and weather/search helpers.

Anything requiring privileged process execution, filesystem access, or broad Telegram access must use explicit capabilities.

## 8. Implementation order

```text
1. Primary runtime/plugin fixes                 DONE for current P0 addon deadlock
2. Regression tests                             DONE for the fixed deadlock
3. Normalize peer/authorization contracts
4. Finish addon command proxy + artifact model
5. Add supervisor + capability RPC
6. Upgrade all existing 25 plugins to common contracts
7. Add missing Tier-1 feature families
8. Port selected UltroidAddons
9. Add feature-parity contract tests
10. Expand addon catalog
```

The important principle is: **fix execution semantics before mass-adding features**. Otherwise new plugins will inherit the same lifecycle, peer, authorization, and addon problems.

## 9. Final classification

```text
GoUltroid plugin architecture      Strong foundation
Current first-party feature set   Partial Ultroid parity
Addon registry                    Functional foundation
Addon runtime                     Functional after deadlock fix
Addon command execution           Incomplete
Addon capability enforcement      Incomplete
Addon artifact lifecycle          Incomplete
Ultroid feature parity            Not yet equivalent
```

The project can absolutely be rebuilt from zero to functional Ultroid parity in Go. The correct strategy is to preserve GoUltroid's stronger typed/lifecycle architecture and systematically fill behavioral feature gaps rather than copying Ultroid's Python structure.
