# 1. Executive Summary

Hasil re-audit menunjukkan bahwa **dokumen 4 dan 4.1 belum selesai secara implementation parity**.

Bukan karena blueprint-nya kurang lengkap, tetapi karena repository sudah bergerak lebih cepat daripada dokumen sebelumnya: banyak capability yang sebelumnya disebut "belum ada" sekarang **sudah mempunyai package/service**, tetapi beberapa masih:

1. belum di-wire ke application composition root;
2. belum benar-benar usable end-to-end;
3. masih berupa abstraction/skeleton/mock backend;
4. belum mempunyai integration test terhadap Telegram;
5. belum mencapai feature breadth Ultroid.

Dengan demikian status yang benar sekarang adalah:

```text
4   = audit/gap map       -> masih valid sebagai baseline, tetapi sebagian status sudah stale
4.1 = implementation plan -> blueprint sangat lengkap, tetapi belum berarti implementasi selesai
4.2 = current gap + root cause + concrete fixes + acceptance targets
```

## Critical finding: bot lambat sejak v1.1.9

**Ya, ada regresi yang sangat kuat dan langsung berkaitan dengan perubahan v1.1.9.**

v1.1.9 mengubah banyak plugin dari:

```go
ctx.Reply(...)
```

menjadi:

```go
ctx.EditOrReply(...)
```

Implementasi awal `EditOrReply()` selalu melakukan:

```go
Edit()
```

terlebih dahulu, baru:

```go
Reply()
```

jika edit gagal.

Masalahnya adalah `Edit()` memilih `LastResponseID`, dan bila belum ada response, fallback ke:

```go
ctx.Message.ID
```

Pada **incoming command**, `ctx.Message` adalah pesan `.command` milik user/pengirim, bukan pesan milik userbot. Jadi hampir setiap command incoming melakukan:

```text
Telegram update
   ↓
handler
   ↓
EditMessage(incoming user's .command)
   ↓
Telegram RPC gagal
   ↓
Reply()
   ↓
Telegram RPC kedua
```

Ini menambahkan satu network round-trip gagal ke hampir setiap response command.

### Fix yang sudah diterapkan

`EditOrReply()` sekarang membedakan ownership message:

```text
LastResponseID != 0
    → Edit response

incoming command
    → Reply langsung

outgoing/self command
    → Edit command
```

Jadi normal incoming command kembali menjadi:

```text
Telegram update
   ↓
handler
   ↓
Reply()
```

tanpa failed edit RPC.

Selain memperbaiki latency, ini juga mengembalikan behavior yang diharapkan: **pesan `.command` incoming tidak diubah menjadi response bot**.

Perubahan utamanya adalah response call dari `Reply()` menjadi `EditOrReply()`.

Pada saat yang sama, implementasi `EditOrReply()` saat itu adalah:

```go
func (m *MessagesFacade) EditOrReply(text string) error {
    if err := m.Edit(text); err == nil {
        return nil
    }
    return m.Reply(text)
}
```

Sedangkan `Edit()` menggunakan:

```go
msgID := c.LastResponseID
if msgID == 0 && c.Message != nil {
    msgID = c.Message.ID
}
```

Ini membuat incoming command mencoba mengedit message yang bukan milik userbot.

## Dampak

Untuk command sederhana seperti:

```text
.ping
.alive
.help
.info
```

response path menjadi dua RPC ketika incoming message tidak dapat diedit.

Secara kasar:

```text
Old:
update → handler → SendMessage

v1.1.9:
update → handler → EditMessage(fail) → SendMessage
```

Jika RTT Telegram cukup besar atau koneksi sedang busy, latency tambahan dapat terasa signifikan.

Pada command yang sudah melakukan Telegram RPC lain, biaya ini menumpuk.

# 3. Correct Semantics untuk Message Response

`EditOrReply` bukan berarti "selalu coba edit sesuatu".

Semantics yang benar adalah:

```text
                  ┌─ LastResponseID exists ──→ EDIT response
                  │
EditOrReply ───────┤
                  │
                  ├─ no response + outgoing ─→ EDIT outgoing command
                  │
                  └─ incoming command ───────→ REPLY
```

## Kenapa LastResponseID diprioritaskan?

Karena workflow seperti:

```go
ctx.Reply("Loading...")
ctx.Edit("Done")
```

memang membutuhkan edit.

Jangan mengganti behavior ini dengan `Reply()` selalu.

## Kenapa incoming message harus Reply?

Karena userbot tidak boleh menggunakan generic `EditMessage` terhadap pesan incoming hanya karena message ID tersedia.

Message ownership adalah bagian dari semantic contract.

# 4. Fix yang Sudah Diimplementasikan

File:

```text
internal/core/context_messages.go
```

Commit:

```text
9962ef27a622290f66696dd5b89fa82939ce9b0c
```

Implementasi baru:

```go
func (m *MessagesFacade) EditOrReply(text string) error {
    c := m.ctx
    if c == nil {
        return errors.New("context is nil")
    }

    if c.LastResponseID != 0 {
        return m.Edit(text)
    }

    if c.Message != nil && c.Message.IsOutgoing {
        return m.Edit(text)
    }

    return m.Reply(text)
}
```

## Target behavior

| Context | Operation |
|---|---|
| Incoming `.ping` | `SendMessage` |
| Incoming `.help` | `SendMessage` |
| Incoming command + no response yet | `SendMessage` |
| Outgoing `.ping` | `EditMessage` |
| `Reply()` then `EditOrReply()` | `EditMessage` response |
| No message | `Reply`/normal error path |

## Expected performance effect

Normal incoming command kehilangan satu failed Telegram RPC.

Jadi improvement yang diharapkan adalah:

```text
command response latency
        ↓
~ one Telegram RPC less
```

Exact milliseconds harus diukur dengan runtime benchmark/production telemetry; jangan mengklaim angka tetap tanpa measurement.

# 5. Hal yang Tidak Boleh Dilakukan Setelah Fix

Jangan mengubah kembali semua plugin menjadi `Reply()` hanya untuk menghindari bug ini.

`EditOrReply()` tetap berguna untuk:

- outgoing userbot commands;
- multi-stage responses;
- progress messages;
- loading → result flows;
- interactive UI;
- callback-driven workflows.

Yang diperbaiki adalah **decision logic**, bukan menghapus capability.

# 31. Final Verdict

## Apakah GoUltroid sekarang sudah sama dengan Ultroid?

**Belum.**

Tetapi gap-nya sekarang berbeda dari audit awal.

Dulu banyak capability memang belum ada.

Sekarang banyak capability sudah mempunyai code, tetapi tantangan utamanya adalah:

```text
code exists
   ≠
runtime feature exists
   ≠
production feature
   ≠
Ultroid parity
```

GoUltroid sudah memiliki fondasi yang cukup serius untuk mengejar parity, tetapi harus menyelesaikan integration dan production semantics terlebih dahulu.

## Apakah v1.1.9 memang penyebab kuat bot terasa lambat?

**Ya, berdasarkan code diff, ini adalah regression yang sangat kuat dan spesifik.**

Perubahan v1.1.9 mengubah banyak normal `Reply()` menjadi `EditOrReply()`, sementara implementasi awal `EditOrReply()` melakukan failed `EditMessage` terhadap incoming command sebelum melakukan `Reply()`.

Itu secara langsung menambahkan Telegram RPC pada response path normal.

Fix sudah diterapkan di:

```text
internal/core/context_messages.go
```

dengan commit:

```text
9962ef27a622290f66696dd5b89fa82939ce9b0c
```
