Ya. Untuk target **userbot yang handal, ringan, cepat, dan sangat minim edge-case**, Goultroid menurut saya memang perlu **redesign parsial pada jalur userbot utama**. Tetapi saya **tidak menyarankan rewrite total** dan tidak menyarankan mengutak-atik lagi seluruh Worker/Task/Job/Scheduler hanya karena ingin menjadikannya userbot yang lebih baik.

Saya cek ulang branch `test-next`; HEAD yang terlihat masih `3d598e5c`. Dari kondisi kode sekarang, masalah utamanya bukan kurang fitur atau kurang abstraksi. Justru beberapa jalur sudah terlalu “infrastructure-heavy” untuk sesuatu yang seharusnya menjadi hot path userbot.

Voice saya keluarkan dari prioritas. Karena memang belum ingin diimplementasikan penuh, solusi yang benar sekarang adalah **jangan expose/register voice sebagai fitur aktif secara default**, bukan membangun voice service lebih jauh.

## Redesign yang saya sarankan

Arsitektur userbot saat ini secara kasar:

```text
Telegram update
      │
      ▼
Dispatcher
      │
      ├─ parse command
      ├─ durable idempotency DB
      ├─ peer/entity handling
      ├─ security hooks
      ├─ moderation hooks
      ├─ feature hooks
      ├─ event bus
      └─ command execution
```

Untuk userbot, saya akan mengubahnya menjadi:

```text
Telegram / gotd
      │
      ▼
Canonical Normalizer
      │
      ▼
Ingress Classifier              ← sangat murah, memory-only
      │
      ├── irrelevant ───────────────► DROP
      │
      ├── security candidate
      │
      ├── automation candidate
      │
      ├── event candidate
      │
      └── command candidate
              │
              ▼
       Invocation Policy
              │
              ▼
        Authorization
              │
              ▼
        Feature/Command
              │
              ▼
       Telegram Facade
```

Prinsipnya:

> **Pesan yang tidak relevan harus selesai hampir tanpa kerja.**

Itulah perubahan terbesar yang diperlukan.

# 1. P0 — redesign hot path update Telegram

Ini menurut saya prioritas tertinggi.

Di `internal/telegram/dispatcher_dispatch.go`, setiap message sekarang menjalankan:

```go
d.idempotencyMgr.CheckAndSet(...)
```

dan idempotency manager memakai `SQLiteRepository`.

Di `internal/idempotency/repository.go`, claim tersebut menjadi:

```sql
INSERT INTO idempotency_keys(...)
ON CONFLICT(key) DO UPDATE ...
```

Jadi secara praktis:

```text
1000 pesan Telegram masuk
        │
        ▼
±1000 SQLite idempotency claims
```

meskipun 999 pesan:

* bukan command,
* bukan PM yang perlu PMPermit,
* tidak match blacklist,
* tidak match filter,
* tidak mention owner,
* tidak membutuhkan userlog,
* tidak memerlukan tindakan apa pun.

Untuk sebuah **userbot**, ini desain yang terlalu mahal.

### Seharusnya

Ingress deduplication biasa:

```text
(chat_id, message_id)
       │
       ▼
bounded in-memory recent-set
```

misalnya TTL/LRU kecil.

Durable idempotency baru digunakan **setelah diketahui ada side effect yang benar-benar penting**.

Contohnya:

```text
Incoming ordinary message
    → memory dedup
    → no feature interested
    → return
```

sedangkan:

```text
.broadcast ...
    → command identified
    → authorization
    → durable operation
    → durable idempotency if needed
```

atau:

```text
scheduled payment / durable operation
    → durable execution identity
```

### Target

Hot path pesan biasa harus:

```text
0 DB write
0 DB read
0 Telegram RPC
0 TaskEngine submission
0 goroutine baru
```

kalau memang tidak ada fitur yang tertarik.

Ini akan mempunyai efek jauh lebih besar terhadap CPU, I/O, dan latency daripada micro-optimization fungsi Go.

# 2. P0 — jangan broadcast setiap message ke semua plugin

Sekarang plugin message hook memakai model:

```go

```

Dispatcher pada dasarnya harus memanggil handler dahulu agar plugin bisa memutuskan:

```go

...
```

Contohnya `blacklist` dan `filters`.

Itu terbalik.

Dispatcher seharusnya **sudah tahu plugin mana yang mungkin tertarik sebelum menjadwalkan handler**.

Saya akan memperkenalkan konsep:

```text

```

misalnya:

```text
PMPermit
  incoming
  private
  human sender

  incoming
  group/supergroup
  text
  chatHasBlacklist

Filters
  incoming
  group/supergroup
  text
  chatHasFilters

  if AFK active:
      incoming PM
      mention

      auto-unAFK

```

Kemudian:

```text
message
   │
   ▼
InterestIndex
   │
   ├─ no consumers → return
   │
   ├─ PMPermit
   │
   └─ Filters
```

bukan:

```text

   ↓
PMPermit?
Blacklist?
Filters?
AFK?
Userlog?
plugin X?
plugin Y?
...
```

Ini menghasilkan kompleksitas hot path mendekati **O(features interested)**, bukan O(all feature hooks).

# 3. Cache harus menjadi bagian dari feature state, bukan fallback setelah handler dipanggil

`blacklist` sebenarnya sudah punya cache yang lumayan bagus.

`filters` juga punya compiled cache.

Masalahnya handler tetap harus masuk ke execution path untuk mengetahui cache tersebut.

Lebih ideal:

```text
FeatureStateIndex
│
├── blacklistChats: map[ChatID]*CompiledBlacklist
├── filterChats:    map[ChatID]*CompiledFilters
├── pmPermitState
├── afkState
└── userlogState
```

dan mutation command:

```text
.blacklist foo
      │
      ├─ persist DB
      └─ atomically update snapshot
```

Maka incoming message:

```text
snapshot.Load()
      │
      └── O(1)
```

DB menjadi **persistence**, bukan bagian dari decision hot path.

Ini salah satu pola paling penting jika Goultroid ingin terasa cepat seperti userbot native daripada application server.

# Invariant yang harus dijadikan aturan desain

Saya akan menjadikan beberapa hal ini sebagai **hard invariant**, bukan sekadar optimisasi:

1. **Irrelevant Telegram update tidak boleh menulis DB.**
2. **Irrelevant update tidak boleh masuk TaskEngine.**
3. **Feature yang disabled tidak punya hot-path cost.**
4. **DB bukan source lookup per-message untuk stable configuration.**
5. **Raw MTProto tidak boleh tersebar ke plugin biasa.**
6. **Permission dan invocation adalah dua konsep berbeda.**
7. **Satu Telegram update dinormalisasi satu kali.**
8. **Satu command diparse satu kali.**
9. **Satu peer diselesaikan paling banyak sekali per execution.**
10. **Durable idempotency hanya pada durable side effect.**
11. **Settings yang disebut live harus benar-benar live.**
12. **Semua cache harus bounded dan memiliki invalidation yang eksplisit.**
13. **Tidak ada periodic poll jika event/wake bisa digunakan.**
14. **Tidak ada fitur yang muncul di `.help` jika dependency-nya tidak tersedia.**
15. **Normal idle harus mendekati zero work di luar kebutuhan MTProto.**

Kalau invariant-invariant ini dipenuhi, codebase akan jauh lebih mudah dipertahankan.

## Yang sebaiknya tidak didesain ulang lagi

Agar tidak jatuh ke endless refactor, saya akan **freeze** beberapa area kecuali ada bug nyata:

* `RPCExecutor` dan centralized Telegram RPC;
* hierarchical RPC limiter setelah optimisasi yang sudah dilakukan;
* resolver/cache architecture;
* bounded SQLite pool + WAL;
* TaskEngine core;
* Job/Scheduler architecture yang sudah kita perbaiki;
* plugin capability gate;
* module dependency graph;
* assistant shared command registry.

Redesign harus terjadi **di atas fondasi tersebut**, bukan membongkarnya lagi.

## Bentuk perubahan yang paling tepat

Jadi jawabannya bukan:

> “rewrite Goultroid menjadi userbot baru.”

Tetapi:

> **buat satu redesign besar terakhir terhadap userbot execution model: ingress → classification → invocation/security → feature routing → side effects.**

Setelah itu feature existing seperti PMPermit, AFK, filters, blacklist, admin, media, settings, assistant, dan lain-lain dimigrasikan secara bertahap ke model baru.

Dengan cara itu kita mendapatkan kombinasi yang sekarang belum sepenuhnya dimiliki Goultroid:

```text
reliability dari arsitektur sekarang
+
resource usage userbot yang minimal
+
behavior yang predictable
+
plugin model yang mudah dikembangkan
+
tanpa membuang hasil redesign performa sebelumnya
```

Dan khusus target **“flawless”**: tidak ada software yang bisa dijamin bebas bug, tetapi arsitektur di atas akan menghilangkan banyak kelas bug sekaligus—duplicate side effect, config yang tidak live, command origin ambigu, plugin interference, unnecessary DB writes, redundant dispatch, serta fitur yang terekspos tanpa dependency.

Kalau melanjutkan implementasi sekarang, saya akan mulai dari **P0-A: redesign Telegram ingress/hot path**, karena itu merupakan perubahan dengan efek paling besar sekaligus menjadi fondasi untuk `InvocationPolicy`, feature-interest routing, dan pengurangan DB/resource usage berikutnya.

Pada bot yang melihat banyak user/chat, cache ini bisa terus tumbuh. `internal/assistant/peer.MemoryCache.records` juga tidak memiliki cap/TTL (`internal/assistant/peer/cache.go:20-99`) dan dapat menyimpan peer selama lifetime proses. `internal/services/ratelimit.Limiter.buckets` berupa `map[string]*bucket` tanpa `MaxBuckets`; cleanup hanya tiap 5 menit (`internal/services/ratelimit/limiter.go:17-25, 217-240`). `core.CooldownTracker.records` juga tidak bounded dan `Cleanup()` bukan bagian dari lifecycle dispatcher (`internal/core/cooldown.go:15-72`). Terakhir, `assistant/client.UserRateLimiter` hanya mencoba cleanup ketika >1000 entry, tetapi burst user unik yang semuanya masih fresh tetap bisa membuat map terus membesar (`internal/assistant/client/ratelimit.go`). Ini harus dibereskan sebelum mengejar penghematan stack goroutine.

2. **P0/P1 — Ubah retention TaskEngine supaya RSS kembali turun setelah burst.** Default saat ini `MaxTerminalRetained=1000`, `MaxRetainedBytes=256 MiB`, `MaxOutputBytes=1 MiB`, tetapi **`TerminalTTL=0`**, artinya terminal record tidak expire berdasarkan waktu (`internal/taskengine/engine.go:57-82`, `internal/taskengine/accounting.go:27-38`). Memang closure `Handler`, `Commit`, dan `OnComplete` sudah dibuang saat terminal (`engine.go:1040-1057`), jadi desainnya sudah jauh lebih baik. Namun result/output sampai ratusan MB secara agregat masih boleh tinggal sampai count/byte eviction. Saya akan ubah default menjadi TTL terbatas—misalnya 5 menit—dan mempertahankan configurability `TASKENGINE_TERMINAL_TTL`. Ini berpotensi jauh lebih terasa ke **RSS setelah workload** dibanding mengurangi satu-dua goroutine.

3. **P1 — Buat internal worker lane benar-benar adaptive/lazy.** TaskEngine saat idle tetap mempunyai **4 completion-delivery worker + 4 durability worker**, selain minimum physical pool worker. `completionDelivery.start()` langsung membuat semua worker (`internal/taskengine/delivery.go`), dan `durabilityLane.start()` melakukan hal yang sama (`internal/taskengine/durability_lane.go:49-57`). Padahal pool fisik TaskEngine sendiri sudah bagus: saat startup hanya membuat `MinConcurrency`, total default minimum physical worker = `1+2+1+1+1 = 6` (`internal/taskengine/engine.go:70-74, 557-574`). Jadi bagian lama yang masih fixed justru delivery/durability. Desain yang lebih cocok: **min=0, max=4**, spawn ketika queue menerima pekerjaan, retire setelah idle timeout. Idle bot bisa membuang 8 goroutine permanen tanpa menurunkan peak concurrency.

4. **P1 — Hilangkan duplicate durability waiting.** Ini lebih fundamental. Production mempunyai TaskEngine durability lane 4 worker **dan** `PersistencePump` 2 worker (`internal/app/wiring_core.go:93-119`). Setelah pump menerima commit, durability worker TaskEngine pada dasarnya menunggu `resCh` sampai ack (`internal/taskengine/durability.go:103-165`). Jadi ada dua lapis worker untuk satu operasi durability: worker pump melakukan DB I/O, worker durability menunggu hasil. Lebih efisien bila pump mempunyai completion/ack continuation menuju `engineRequest{opCommitAck}` sehingga successful pump path **tidak membutuhkan goroutine yang sekadar menunggu channel**. Durability lane cukup dipertahankan sebagai bounded fallback untuk `commitPump == nil/saturated`. Ini bisa menurunkan goroutine sekaligus timer allocation karena sekarang waiter menggunakan `time.After(commitWaitTimeout)` per commit.

5. **P1 — Jobs retry pool juga sebaiknya adaptive.** `retryWorkers = 4` dibuat permanen di `Manager.Start()` (`internal/jobs/manager.go:123-132, 245-257`). Keempatnya hanya block pada `retryQueue` dan menjalankan `watchAttempt()` saat ada item. Untuk userbot normal, retry biasanya sporadis. Pola yang lebih sesuai adalah lazy `0..4` worker atau satu baseline worker + burst expansion. `recoveryLoop` dan `outboxLoop` tetap boleh hidup karena mereka benar-benar memiliki durable deadlines/wake ownership. Hasilnya sekitar **4 goroutine idle** lagi dapat hilang.

6. **P1 — PersistencePump bisa 0..2 adaptive dan waiter goroutine dapat dihapus.** Production membuat 2 worker permanen, lalu membuat satu goroutine tambahan hanya untuk `wg.Wait(); close(done)` (`internal/jobs/persistence_pump.go:134-157`). Worker bisa dibuat on-demand, dan `done` dapat ditutup oleh worker terakhir menggunakan atomic counter/pola `remaining`, seperti TaskEngine lane sekarang. Dengan begitu idle cost menjadi 0 worker persistence, bukan 3 goroutine.

7. **P1/P2 — Ada beberapa “waiter-only goroutine” yang tidak diperlukan.** Scheduler membuat `go func(){ e.wg.Wait(); close(runDone) }()` hanya untuk menunggu satu `runLoop` (`internal/scheduler/engine.go:226-239`). `periodicCoordinator` melakukan hal yang sama untuk satu loop (`internal/scheduler/periodic_timer.go:131-143`). Inline cache bahkan membuat goroutine baru pada `Stop()` hanya untuk menunggu `c.wg.Wait()` (`internal/services/inline/cache.go:379-402`). Ini bukan sumber RSS terbesar, tetapi gampang dibersihkan: loop pemilik cukup `defer close(done)`. Tidak ada alasan mempertahankan satu goroutine waiter per subsystem.

8. **P2 — Jadikan housekeeping goroutine benar-benar zero-idle.** `idempotency.Manager` sudah deadline-driven dan tidak polling saat kosong, tetapi goroutinenya tetap hidup (`internal/idempotency/manager.go:52-78`). Inline cache juga tetap punya satu prune goroutine yang block ketika kosong. `services/ratelimit` malah masih memakai periodic cleanup goroutine. Pola `delayedActionScheduler` yang baru sebenarnya lebih baik: coordinator bisa retire ketika tidak ada pekerjaan dan dibangunkan lagi saat diperlukan. Pola itu bisa dipakai konsisten untuk ketiga subsystem ini.

9. **P2 — TaskEngine inbox backing memory layak dibenchmark.** Default `InboxCapacity=2048`, sementara elemennya adalah **`engineRequest` by value** yang membawa `WorkSpec`, `TaskResult`, `OwnerLimits`, `PoolEngineConfig`, context/interface, string headers, dan beberapa pointer (`internal/taskengine/engine.go:163-194`). Jadi channel kosong sekalipun sudah mengalokasikan backing array untuk 2048 struct yang cukup besar. Ini kandidat RSS startup yang nyata. Saya belum akan langsung menggantinya dengan `chan *engineRequest`, karena itu dapat memindahkan biaya menjadi heap allocation per operation dan memperburuk GC. Pilihan yang layak diuji: turunkan default ke 512/1024, atau pointer + bounded pool. Ini harus diputuskan berdasarkan benchmark `B/op`, `allocs/op`, latency, dan saturation behavior.

Secara arsitektur, target akhir yang menurut saya tepat adalah kira-kira seperti ini:

```text
Idle
 ├─ TaskEngine coordinator               1
 ├─ physical workers @ MinConcurrency    6
 ├─ delivery workers                     0
 ├─ durability wait workers              0
 ├─ persistence workers                  0
 ├─ retry workers                        0
 ├─ Jobs recovery                        1
 ├─ Jobs outbox                          1
 ├─ Scheduler timing owner               1
 ├─ Periodic timing owner                1
 └─ cache/rate-limit cleanup workers     0 when empty
```

Jadi dari komponen yang saya audit saja, **steady-state floor berpotensi turun belasan goroutine**, kemungkinan mendekati ~15–20 goroutine tergantung komponen yang aktif. Yang lebih penting, RSS menjadi **bounded by design** dan bisa benar-benar turun secara logical retention setelah burst, bukan sekadar “GC mudah-mudahan membersihkan”.

Untuk urutan implementasi saya akan mulai dari **P0 — bounded memory state + TaskEngine terminal retention**, karena itu yang paling berpengaruh terhadap RSS dan paling berbahaya jika dibiarkan. Setelah itu **P1 — lazy durability/delivery/persistence/retry workers** untuk menekan goroutine floor. Baru sesudahnya P2 inbox/channel compaction dan penghilangan housekeeping/waiter kecil.

Koreksi terbaru ini belum bisa saya persist ke Memory pada sesi ini karena setelah akses repo, penyimpanan Memory tidak tersedia untuk turn tersebut; kalau ingin koreksi HEAD/audit ini ikut tersimpan permanen, buka chat baru dan minta saya menyimpan ringkasan Goultroid terbaru.
