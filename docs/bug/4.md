### Apa sebenarnya “Assistant Bot” di Ultroid?

Dokumentasi Ultroid sendiri memisahkan tiga primitive utama: `ultroid_cmd` untuk command, `in_pattern` untuk inline assistant update, dan `callback` untuk callback event. `ultroid_cmd` juga menangani mode user/bot/dual/manager. ([GitHub][1])

Tetapi setelah membaca implementasinya, assistant Ultroid sebenarnya jauh lebih besar daripada tiga primitive tersebut. Secara konseptual ia menjalankan **lima peran sekaligus**:

| Peran                             | Ultroid                                                                                              |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Owner control plane**           | `/start`, settings, language, timezone, stats, update, addon, PMPermit, bot settings, media settings |
| **Public bot facade**             | welcome, owner info, file/deep-link delivery, help, visitor tracking                                 |
| **Alternative command surface**   | dual-mode commands, manager/group commands, custom `/command`                                        |
| **Interactive UI engine**         | inline query + inline keyboard + callback navigation/workflow                                        |
| **Mailbox / communication proxy** | PM bot relay visitor → owner dan reply owner → visitor                                               |

Jadi kalau tujuan kita hanya membuat `AssistantClient + InlineEngine`, kita masih belum mencapai model Ultroid. **Assistant merupakan surface interaksi lengkap dari userbot.**

Implementasi decorator Ultroid yang menjadi pusat ketiga surface ini ada di `pyUltroid/_misc/_assistant.py`. [Ultroid assistant decorators](https://github.com/TeamUltroid/Ultroid/blob/main/pyUltroid/_misc/_assistant.py?utm_source=chatgpt.com)

# Inline Ultroid jauh lebih penting daripada sekadar “inline search”

Ini salah satu temuan paling penting untuk desain Goultroid.

Di Ultroid, inline mempunyai **tiga fungsi berbeda**.

**Pertama, inline sebagai feature surface.** Misalnya search/app lookup, YouTube, calculator, F-Droid, Google, Saavn, TL object dan berbagai utility lainnya. Dekorator resminya memang dimaksudkan sebagai “Inline Assistant Updates”. ([GitHub][1])

**Kedua, inline sebagai interactive application.** Contoh YouTube:

```text
inline query
    ↓
search results
    ↓
choose result
    ↓
callback: audio / video
    ↓
format selection
    ↓
callback
    ↓
download / edit message
```

Calculator juga melakukan pola serupa: inline message menjadi UI, kemudian tombol callback memutasi state/calculation. Implementasi calculator bahkan menggunakan assistant inline query dari user account lalu meng-click result dengan `hide_via=True`. ([CodeFactor][2])

**Ketiga, dan yang paling menarik: inline sebagai rendering bridge.**

`plugins/_inline.py` memiliki mekanisme `something(...)` dan `STUFF`. Secara kasar:

```text
userbot feature
    ↓
ingin mengirim UI/button-rich message
    ↓
simpan temporary presentation
    ↓
query @assistant stf<ID>
    ↓
assistant menghasilkan inline result
    ↓
userbot click inline result ke target chat
    ↓
Telegram menampilkan interactive message
```

Artinya, Ultroid memakai Assistant Bot untuk mengatasi boundary Telegram antara **user account** dan **bot-style interactive markup**.

[Ultroid inline bridge implementation](https://github.com/TeamUltroid/Ultroid/blob/main/plugins/_inline.py?utm_source=chatgpt.com)

### Ini harus kita pertahankan secara semantik

Tetapi **jangan** membuat plugin Goultroid:

```go
assistant.InlineQuery(...)
cache[id] = ...
Click(...)
```

secara manual.

Di desain baru seharusnya:

```text
Feature
  │
  ▼
PresentationService
  │
  ├── direct userbot rendering
  │
  ├── assistant bot rendering
  │
  └── inline render bridge
```

Feature hanya mengatakan:

```go
Render(ctx, View{...})
```

Transport menentukan bagaimana Telegram harus mewujudkannya.

Ini akan membuat inline bridge menjadi **platform capability**, bukan trik yang tersebar di plugin.

# `/start` Ultroid juga merupakan router, bukan hanya greeting

`assistant/start.py` melakukan banyak hal sekaligus.

Untuk user biasa, ia memberikan welcome, custom text/media, owner information, optional PM relay, dan menangani `/start <payload>` untuk stored file.

Untuk owner/sudo, `/start` berubah menjadi control console dengan menu Settings, Language, Stats, Broadcast, Timezone, dan submenu lain.

Ia juga menyimpan visitor ke `BOT_USERS` dan optional mencatat visitor baru ke log channel.

[Ultroid assistant start flow](https://github.com/TeamUltroid/Ultroid/blob/main/assistant/start.py?utm_source=chatgpt.com)

Goultroid baru sebaiknya tidak membuat satu handler `/start` raksasa. Modelnya:

```text
/start [payload]
       │
       ▼
DeepLinkRouter
       │
       ├── no payload ───────► HomeFlow
       ├── file token ───────► SavedAssetFlow
       ├── feature token ────► FeatureFlow
       ├── auth token ───────► AuthorizationFlow
       └── expired/invalid ──► Safe fallback
```

Dan `HomeFlow` sendiri memilih presentation berdasarkan principal:

```text
anonymous/public
owner
sudo
authorized assistant user
```

Dengan begitu, nanti MyXL, SavedResponse, plugin configuration, file sharing atau workflow lain dapat memakai `/start` tanpa parsing string sendiri-sendiri.

# PM Bot Ultroid layak dianggap subsystem tersendiri

`assistant/pmbot.py` memperlihatkan konsep yang cukup bagus secara produk:

```text
visitor
   │
   │ DM assistant
   ▼
Assistant
   │
   ├── force-sub validation
   ├── blocked-user check
   │
   ▼
forward to owner
   │
   ▼
store forward-message → visitor mapping
   │
owner replies
   │
   ▼
lookup visitor
   │
   ▼
Assistant sends reply
```

Ada juga `/who`, `/ban`, `/unban`.

[Ultroid PM bot relay](https://github.com/TeamUltroid/Ultroid/blob/main/assistant/pmbot.py?utm_source=chatgpt.com)

Di Goultroid jangan memasukkannya ke generic incoming-message handler.

Saya ingin nanti ada:

```text
PMRelayService
 ├─ AdmissionPolicy
 ├─ ConversationRepository
 ├─ RelayMapper
 ├─ BlockRepository
 ├─ DeliveryService
 └─ CleanupPolicy
```

Mapping harus durable dan bounded. Kalau owner membalas forwarded message setelah restart, mapping seharusnya tetap dapat ditemukan selama retention period.

Ultroid menyelesaikan use-case tersebut, tetapi implementasinya masih sangat global/ad-hoc. Kita ambil **semantics-nya**, lalu implement ulang dengan lifecycle yang benar.

# Hal yang tidak boleh kita copy dari Ultroid

Arsitektur Ultroid berhasil secara fungsional, tetapi beberapa mekanismenya justru menjadi contoh apa yang perlu kita hindari.

`asst_cmd`, `in_pattern`, dan `callback` langsung menambahkan event handler ke global `asst`. `ultroid_cmd` juga dapat memasang wrapper yang sama ke userbot maupun assistant ketika dual mode aktif. [Ultroid command decorator internals](https://github.com/TeamUltroid/Ultroid/blob/main/pyUltroid/_misc/_decorators.py?utm_source=chatgpt.com)

Loader kemudian mengaktifkan folder `assistant`, `assistant/manager`, `pmbot`, addons, dan lain-lain secara conditionally. [Ultroid plugin loader](https://github.com/TeamUltroid/Ultroid/blob/main/pyUltroid/startup/loader.py?utm_source=chatgpt.com)

Ini menghasilkan coupling seperti:

```text
plugin
 ├── knows global assistant client
 ├── registers Telegram event itself
 ├── reads global DB key itself
 ├── owns temporary cache itself
 ├── generates callback strings itself
 ├── performs Telegram RPC itself
 └── sometimes owns conversation lifecycle itself
```

**Goultroid baru tidak boleh begitu.**

Plugin/feature tidak boleh tahu dispatcher Telegram, global assistant instance, atau registrasi low-level event.

# Callback baru harus lebih kuat daripada milik Ultroid maupun Goultroid sekarang

Current Goultroid sebenarnya sudah bagus karena callback data sudah versioned:

```text
a1:<namespace>:<action>:<state>
```

dengan batas Telegram 64 byte dan field validation. [Current Goultroid callback payload](https://github.com/inipew/goultroid/blob/test-next/internal/assistant/callback/payload.go?utm_source=chatgpt.com)

Namun pada rewrite saya ingin kita naik satu tingkat.

Jangan memasukkan mutable state secara bebas ke callback data.

Target:

```text
a2:<feature>:<action>:<token>
```

`token` menunjuk pada:

```text
InteractionSession
 ├─ feature generation
 ├─ owner/user
 ├─ chat
 ├─ message
 ├─ current screen/state
 ├─ arbitrary bounded state
 ├─ created_at
 ├─ expires_at
 └─ version
```

Saat callback masuk:

```text
parse
  ↓
resolve token
  ↓
validate TTL
  ↓
validate plugin generation
  ↓
validate actor
  ↓
validate chat/message binding
  ↓
policy
  ↓
transition
  ↓
render
```

Ini menyelesaikan sekaligus stale button, cross-user click, plugin reload, callback replay, state terlalu panjang dan temporary global maps.

# Area yang saya ingin kita buat dari nol

Karena Anda memang ingin rework/reimplement, saya tidak menyarankan mencoba “memperbaiki sedikit-sedikit” `internal/assistant` sekarang.

Namun boundary reimplementation-nya adalah **assistant interaction stack**, bukan TaskEngine/RPC/core infrastructure seluruh Goultroid.

Urutan implementasi yang menurut saya paling tepat adalah:

1. **P0 — Interaction/Surface Contract**: `FeatureSpec`, capability types, canonical surface registry, ownership/lifecycle, typed policy; belum membuat banyak fitur.
2. **P1 — Interaction Session Runtime**: durable/ephemeral bounded state, TTL, user/chat/message binding, callback `a2`, navigation dan prompt/response state machine.
3. **P2 — Presentation + Render Bridge**: canonical `View`, buttons/actions, edit/send/answer, assistant-render dan self-inline bridge tanpa feature mengetahui Telegram trick.
4. **P3 — Assistant shell**: clean AssistantRuntime, update demux, `/start`, deep-link router, owner/public home, typed menu/navigation, help/status/settings.
5. **P4 — Inline vNext**: registry berasal dari FeatureSpec, search/result/pagination/cache/access policies, feature-provided inline handlers, inline callback continuity.
6. **P5 — SavedResponse integration**: saved response → assistant command / inline / deep-link, menggantikan konsep Ultroid `ASST_CMDS`.
7. **P6 — PM Relay**: durable thread mapping, visitor registry, block/access policy, optional force-sub, owner reply, retention/cleanup.
8. **P7 — group/manager + advanced workflows**: admin feature exposure, calculator, downloader/search workflows, callback-heavy flows sebagai validation.
9. **P8 — migration/parity + delete old stack**: behavioral matrix Ultroid vs Goultroid, resource/idle/load tests, unload/reload/shutdown tests, kemudian hapus implementation lama.

Ini satu-satunya daftar phase yang saya sarankan; fitur lain masuk ke capability framework tersebut, bukan menambah arsitektur baru tiap kali.

```text
TaskEngine bila memerlukan execution resources
   ↓
feature use-case
   ↓
PresentationService
   ↓
RPC executor
```

**Tidak ada plugin yang langsung mendaftarkan event handler ke Telegram client. Tidak ada plugin yang membuat callback-data protocol sendiri. Tidak ada plugin yang menyimpan conversation goroutine sendiri. Tidak ada command registry kedua khusus Assistant.**

Itulah target yang menurut saya paling tepat.

### Kesimpulan

Setelah membedah Ultroid, saya akan menetapkan tujuan Goultroid seperti ini:

> **Goultroid Assistant vNext harus memiliki kelengkapan UX Ultroid—control bot, dual command surface, rich inline, callbacks, interactive menus, PM relay, custom responses, deep links, manager functionality, render bridge—tetapi semuanya merupakan surface dari feature/use-case Goultroid yang sama, bukan sekumpulan bot plugins independen.**

Yang bagus dari current Goultroid seperti **canonical `core.Command`, `InvocationPolicy`, execution surfaces, TaskEngine, centralized RPC, plugin scope, callback payload validation dan inline result model** tetap menjadi dependency/foundation. Yang kita **reimplement dari nol adalah interaction model dan assistant-facing architecture di atasnya**. Dengan pendekatan itu kita tidak mundur dari redesign yang sudah kita lakukan hanya demi meniru Ultroid.

Langkah pengerjaan yang paling tepat setelah studi ini adalah **P0 — desain dan implement `Feature Surface / Interaction Contract`**, sebelum menyentuh `/start`, settings atau inline feature satu per satu.

# Parity P6 — PM Relay

North-star-nya sebaiknya:

```text
Assistant Update
      │
      ▼
RelayIngress
      │
      ├── visitor message
      │       ↓
      │   admission/policy
      │       ↓
      │   TaskEngine
      │       ↓
      │   PMRelayService
      │       ↓
      │   durable delivery intent
      │       ↓
      │   Assistant transport
      │       ↓
      │   owner
      │
      └── owner reply to mapped message
              ↓
          durable mapping
              ↓
          admission/revalidation
              ↓
          TaskEngine
              ↓
          copy/send to visitor
```

`PMRelayService` sebaiknya memiliki domain sendiri:

```text
internal/services/pmrelay/
    service.go
    repository.go
    sqlite.go
    migration.go
    policy.go
    delivery.go
    errors.go
```

Sedangkan Telegram-specific adapter tetap di Assistant layer.

### Keputusan arsitektur penting

**Jangan tambahkan `InteractionKindRelay`.** `FeatureSpec` sekarang tepat untuk command, inline, action, screen, dan deep-link. PM Relay adalah implicit data-plane fallback, bukan sebuah interaction yang perlu muncul di FeatureCatalog.

Control plane PM Relay—dashboard, `/who`, ban/unban, settings—boleh dan seharusnya menjadi feature canonical `pm_relay`.

Data plane-nya tetap service/runtime capability.

**Jangan reuse PMPermit database sebagai relay blocklist.** `PMPermit` mengatur siapa yang boleh menghubungi **user account**. PM Relay mengatur siapa yang boleh berbicara melalui **Assistant bot**. Principal, transport, dan semantics-nya berbeda. Sharing abstraction boleh nanti, tetapi sharing rows/status sekarang justru menciptakan coupling yang salah.

## P6-A — Relay domain contract + persistence

Ini sebaiknya pekerjaan pertama.

Definisikan tiga konsep durable terpisah:

| Domain           | Fungsi                                                        |
| ---------------- | ------------------------------------------------------------- |
| `RelayMapping`   | menghubungkan message yang diterima owner dengan visitor asal |
| `RelayDelivery`  | idempotency/recovery untuk actual forwarding/copy             |
| `AudienceMember` | registry user Assistant untuk visitor/broadcast               |

Mapping minimal harus menyimpan:

```text
owner_chat_id
owner_message_id
visitor_user_id
visitor_message_id
created_at
expires_at
```

Key lookup utamanya:

```text
(owner_chat_id, owner_message_id)
```

bukan hanya `message_id`, agar boundary-nya eksplisit.

Delivery sebaiknya memiliki unique source identity:

```text
direction
source_chat_id
source_message_id
```

sehingga reconnect/replayed Telegram update tidak mengirim message dua kali.

Untuk delivery yang kuat saya menyarankan pola:

```text
claim durable delivery intent
        ↓
Telegram RPC
        ↓
persist delivered target message ID
```

Dengan deterministic/stored Telegram `random_id`, crash:

```text
RPC sukses
DB commit belum terjadi
process mati
```

dapat diretry tanpa sengaja mengirim dua copy apabila transport mendukung deduplication tersebut.

Ini lebih kuat daripada sekadar:

```go
Forward()
repo.InsertMapping()
```

yang punya failure window permanen.

## P6-B — Assistant relay ingress dan ordering

Jangan langsung taruh forwarding di `OnNewMessage`.

Tambahkan narrow dependency semacam:

```text
RelayIngress
```

ke `UpdateHandlerDeps`.

Urutan normal visitor:

```text
private incoming
    ↓
a2/explicit interaction?
    ↓
known Assistant command?
    ↓
PM Relay fallback
```

Jadi:

`/start`, `/responses`, feature command, dan command lain **tidak pernah masuk mailbox owner**.

Unknown slash command juga sebaiknya mengikuti Ultroid: jangan direlay.

Ada satu exception penting untuk owner: **reply ke forwarded relay message adalah intent yang lebih kuat daripada generic `AwaitInput`.**

Misalnya owner sedang punya Settings input pending tetapi melakukan:

```text
Reply → forwarded visitor message
```

Itu mestinya relay reply, bukan dianggap nilai setting.

Jadi precedence owner idealnya:

```text
slash command
atau
reply_to known relay mapping
        ↓
explicit relay intent
        ↓
baru generic a2 AwaitInput
```

Preparation boleh melakukan bounded DB lookup untuk mengetahui apakah `reply_to_msg_id` adalah relay mapping; actual Telegram side-effect tetap harus sesudah TaskEngine admission dan mapping harus direvalidate ketika task berjalan.

## P6-C — Visitor → owner delivery

Canary pertama sebaiknya text message biasa dahulu.

Flow:

```text

  ↓

  ↓
relay enabled?
  ↓
not locally blocked?
  ↓
rate/quota admission
  ↓
TaskEngine
  ↓
revalidate policy
  ↓

  ↓

  ↓

  ↓
```

Ordering key sebaiknya per conversation:


## P6-D — Owner → visitor reply

Kemudian tutup round-trip.

Owner hanya boleh me-relay message apabila:

```text

message is reply
reply target mempunyai active RelayMapping
```

Lalu:

```text

    ↓

    ↓

  mapping belum expired
  visitor belum diblok
```

Semantik Ultroid yang bagus untuk dipertahankan adalah **visitor menerima message dari bot**, bukan sebuah Telegram forward yang membocorkan owner sebagai forwarded sender.

Text, photo, document, video, audio, sticker/media umum kemudian ditambahkan melalui transport adapter yang sama.

Protected/non-copyable media harus punya typed failure, bukan silent drop.

## P6-H — durability, resource, lifecycle acceptance

P6 baru layak ditutup setelah matriks berikut terbukti:

| Scenario                                            | Expected                                                 |
| --------------------------------------------------- | -------------------------------------------------------- |
| duplicated visitor update                           | tidak double-forward                                     |
| restart setelah mapping dibuat                      | owner reply masih resolve                                |
| crash setelah Telegram send sebelum DB finalization | recovery tidak membuat logical duplicate                 |

## Yang sekarang tersedia

Domain baru ada di:

`internal/services/pmrelay/`

Repository dibagi menjadi tiga durable boundary yang berbeda:

```text
pm_relay_mappings
    owner-visible relay message
             ↕
    original visitor message

pm_relay_deliveries
    durable logical Telegram send
    + random_id
    + claim lease
    + attempts
    + completion

assistant_audience_members
    generic Assistant audience registry
```

Mapping sekarang punya dua identitas unik:

```text
(owner_chat_id, owner_message_id)

(visitor_user_id, visitor_message_id)
```

Exact duplicate bersifat idempotent. Menggunakan kembali salah satu sisi untuk message berbeda menghasilkan `ErrMappingConflict`.

Ini penting agar nanti owner reply setelah restart tetap dapat menemukan visitor tanpa state process-local.

### Durable delivery/idempotency

Logical send sekarang menggunakan identity:

```text
(direction, source_chat_id, source_message_id)
```

dengan direction:

```text
visitor_to_owner
owner_to_visitor
```

`DeliveryIntent` menyimpan **Telegram `random_id` sebelum RPC dilakukan**. Bila source message yang sama diproses ulang setelah restart, repository mengembalikan `random_id` durable lama dan mengabaikan kandidat baru.

Jadi P6-B/P6-C nanti bisa menutup failure window ini:

```text
persist delivery intent
        ↓
Telegram send sukses
        ↓
process crash
        ↓
DB belum mencatat completion
        ↓
restart
        ↓
load intent yang sama
        ↓
reuse random_id yang sama
```

Source yang sama juga **tidak boleh diarahkan ke target chat berbeda**. Kasus itu fail-closed sebagai `ErrDeliveryConflict`.

### Claim/recovery protocol

Delivery mempunyai durable execution lease:

```text
claim_id
claim_expires_at
attempts
last_error
```

Hanya delivery yang:

```text
belum delivered
belum expired
tidak sedang mempunyai active claim
```

yang dapat di-claim.

Concurrent executor kedua mendapatkan:

`ErrDeliveryClaimed`

Setelah lease lama expired, executor baru dapat reclaim intent yang sama.

Successful commit menyimpan:

```text
target_message_id
delivered_at
```

lalu membersihkan claim.

Commit yang dipanggil ulang sesudah successful DB commit bersifat idempotent bila `target_message_id` sama. Jika hasilnya berbeda, fail-closed sebagai conflict.

Failure dapat `ReleaseDelivery()` sehingga intent tetap reusable dan `last_error` disimpan dengan bound maksimal 1024 byte.

### Cleanup aman

Tidak ada eviction tersembunyi.

Saat capacity penuh:

```text
existing identity
    → existing record masih dapat dibaca/update

new identity
    → typed capacity error
```

Repository **tidak pernah** melakukan:

```text
DELETE oldest
LRU eviction
random eviction
```

untuk memberi ruang.

Cleanup hanya tersedia lewat bounded API eksplisit:

```text
PruneExpiredMappings()
PruneExpiredDeliveries()
PruneAudienceBefore()
```

maksimal **256 row per call**.

Delivery expired yang masih mempunyai active claim juga **tidak dapat di-prune**. Baru setelah claim lease ikut expired row tersebut eligible untuk reclamation.

Tidak ada ticker, goroutine, maupun polling baru.

## Retention dan capacity

Invariant yang sekarang dibakukan:

| State                     |             Default | Maximum / hard bound |
| ------------------------- | ------------------: | -------------------: |
| Mapping retention         |             30 hari |              90 hari |
| Delivery retention        |             30 hari |              90 hari |
| Audience retention policy |            180 hari |             365 hari |
| Mapping rows              |              16,384 |               65,536 |
| Delivery rows             |              32,768 |              131,072 |
| Audience users            |              10,000 |               50,000 |
| Cleanup batch             | 64 default fallback |                  256 |
| Delivery claim lease      |           ≤ 5 menit |              5 menit |

Mapping dan delivery menolak row dengan retention yang melebihi maximum domain.

Audience sengaja generic:

```text

AudienceSourceRelay
AudienceSourceInline
AudienceSourceDeepLink
```

Satu user dapat mengakumulasi bit source tanpa duplikasi row.

Dan importantly, audience ini **tidak memakai tabel PMPermit**. Jadi nanti:

```text

    = access control userbot PM

PM Relay block/admission
    = Assistant mailbox policy

AssistantAudience
    = discovery/broadcast population
```

tetap tiga concern berbeda.

## 1. Relay sebelumnya tergantung resolver/a2 presentation

Sebelum hardening saya, path-nya masih:

```go

    return nil

    return nil
}

```

* peer resolver gagal,
* presentation `Interaction` unavailable,

```text

chat_id

```

```text

             ↓
clean unhandled
             ↓
RelayIngress tetap dapat berjalan
```

Test baru membuktikan visitor relay masih dapat masuk ketika:

* `Resolver == nil`
* `Interaction == nil`
* resolver mengembalikan error

selama message memenuhi PM relay classification.

Log resolver juga saya ubah dari misleading:

```text
sender access hash missing, message ignored
```

menjadi lebih tepat:

```text

```

karena message belum tentu benar-benar di-ignore—relay masih dapat mengklaimnya.

## 2. Error klasifikasi AwaitInput sebelumnya bisa berubah menjadi relay

Ini lebih berbahaya.

Sebelumnya pola generic input:

```go
if handled, err := tryText(...); handled {
    ...
    return
}

// relay fallback
```

Kalau hasilnya:

```text
handled = false
err     = database/runtime error
```

error tersebut hilang dan message jatuh ke PM Relay.

Artinya kegagalan mengecek apakah message milik input session bisa salah mengubah message menjadi relay traffic.

Sekarang semantics-nya:

```text
tryText()
   │
   ├─ error
   │    → fail closed
   │    → STOP
   │
   ├─ handled=true
   │    → input owns message
   │    → STOP
   │
   └─ handled=false + nil error
        → clean fallback
        → PM Relay allowed
```

Saya terapkan semantics yang sama pada `/cancel`.

Test baru mengunci kasus:

```text
AwaitInput classification error
        ↓
visitor relay MUST NOT run
```

Ya, **Parity P7 cukup panjang**, tetapi sifatnya berbeda dari P6.

P6 panjang karena membangun satu subsystem baru end-to-end: **PM Relay** dari persistence, ingress, delivery dua arah, control plane, audience, force-sub, sampai durability acceptance.

P7 lebih seperti **membuka Assistant dari private-owner plane menuju group/manager plane dengan contextual authorization**. Jadi pekerjaan utamanya bukan storage/transport baru sebanyak P6, melainkan memastikan feature yang berjalan di grup mempunyai authority yang benar berdasarkan **siapa user-nya, chat mana, role apa, command apa, dan surface mana**.

Secara realistis saya akan pecah P7 seperti ini:

1. **P7-A — Group execution model / contextual principal**

   * definisikan canonical group context untuk Assistant;
   * bedakan `owner`, `sudo`, Telegram group admin/creator, member biasa;
   * authority harus berdasarkan `(actor, chat, surface, feature)`, bukan global permission saja;
   * jangan reuse permission userbot secara buta;
   * tentukan private/group/channel/supergroup boundaries;
   * regression gate agar private-only feature tidak bocor ke group plane.

2. **P7-B — Telegram group role resolver**

   * resolve creator/admin/member/restricted/banned;
   * cache role/member state secara bounded;
   * TTL/invalidation yang aman;
   * managed RPC only, bukan direct Telegram API bypass;
   * distinguish authoritative “not admin” dari verification failure;
   * tidak membuat periodic poller/goroutine baru.

3. **P7-C — Contextual authorization policy**

   * policy seperti:

     ```text
     owner only
     owner or sudo
     group admin
     group creator
     admin with required Telegram right
     ordinary member
     ```
   * authorization tepat sebelum execution, bukan hanya saat parsing;
   * revalidation setelah TaskEngine admission untuk mutation;
   * explicit behavior saat role berubah ketika task queued;
   * fail-closed pada privileged mutation jika auth verification gagal.

4. **P7-D — Group command routing**

   * command Assistant mulai boleh masuk group dengan canonical `core.Router`;
   * mention/prefix semantics;
   * `/command@botusername`;
   * hindari accidental response terhadap percakapan biasa;
   * command collision rules tetap lewat feature catalog;
   * no second dispatcher.

5. **P7-E — Manager/admin command foundation**

   * surface untuk group admins/managers;
   * read-only canary dahulu, misalnya status/help/group info;
   * baru mutation setelah authz contract terbukti;
   * response/error UX untuk permission denied, stale role, unsupported chat.

6. **P7-F — Group-scoped persistent state**

   * bila feature membutuhkan settings per-chat:

     ```text
     chat_id + namespace + key
     ```
   * CAS/revision;
   * owner/admin authority sebelum persistence;
   * tidak memakai global setting ketika semestinya chat-local;
   * bounded state dan cleanup/lifecycle.

7. **P7-G — Moderation/action execution**

   * kick/ban/unban/mute/restrict/pin/delete dan sejenisnya bila memang parity target membutuhkan;
   * rights-aware validation:

     ```text
     can_delete_messages
     ban_users
     pin_messages
     add_admins
     ...
     ```
   * target hierarchy check: bot tidak mencoba action yang Telegram pasti tolak;
   * no mutation before TaskEngine admission;
   * revalidate actor + bot rights tepat sebelum RPC.

8. **P7-H — Event-driven group features**

   * welcome/goodbye/service-message handling bila masuk parity target;
   * feature-interest routing supaya tidak semua group update masuk semua feature;
   * no full-group hot-path fan-out;
   * event subscriptions hanya aktif jika feature memang enabled untuk chat tersebut.

9. **P7-I — Anti-spam / filters / manager rules foundation**

   * kalau parity Ultroid membutuhkan blacklist/filter/warnings;
   * compile/index rules per chat, bukan scan semua rules global tiap message;
   * bounded cache;
   * mutation revision/invalidation;
   * interaction dengan admin bypass dan owner/sudo.

10. **P7-J — Group media/reply/context semantics**

    * reply-target extraction;
    * mentioned/replied bot context;
    * media command input;
    * linked message/thread/topic semantics;
    * forum topic/thread ordering key;
    * jangan membuat reply dari topic A dieksekusi di topic B.

11. **P7-K — Lifecycle/resource hardening**

    * no per-group permanent goroutine;
    * caches bounded;
    * no periodic per-chat polling;
    * role cache and settings cache lazy;
    * TaskEngine quota/order keys per chat/user;
    * FloodWait/backpressure behavior;
    * shutdown/cancellation.

12. **P7-L — Group-plane acceptance**

    * matrix minimal:

      ```text
      private vs group vs channel
      owner vs sudo vs admin vs member
      admin rights present vs missing
      role changed while queued
      bot rights changed while queued
      task rejection
      Telegram verification outage
      restart
      stale cached role
      topic/thread isolation
      high-cardinality groups/users
      idle footprint
      ```
    * architecture test memastikan mutation selalu melewati TaskEngine dan contextual authz;
    * benchmark/hot-path regression untuk normal group messages yang tidak relevan.

Jadi kalau dibandingkan ukuran:

```text
P6  = satu subsystem dalam, durable, end-to-end
P7  = banyak boundary lintas seluruh Assistant/group architecture
```

Saya perkirakan **P7 bisa sama panjang atau sedikit lebih panjang dari P6**, tetapi tidak semua subphase harus besar. Yang paling berat kemungkinan **P7-A/B/C**, lalu **P7-G/I**, dan terakhir **P7-L**. P7-D/E/F relatif lebih mekanis setelah contextual authz sudah benar.

Urutan yang paling aman menurut saya:

```text
P7-A contextual principal
→ P7-B role resolver
→ P7-C authz policy
→ P7-D group routing
→ P7-E read-only manager canary
→ P7-F per-group state
→ P7-G privileged mutations
→ P7-H/I group features
→ P7-J topics/reply/media semantics
→ P7-K resource/lifecycle
→ P7-L acceptance
```

Yang penting: **jangan mulai P7 dari moderation commands**. Kalau contextual principal + role resolver + revalidation belum matang, semua command seperti ban/mute/delete akan membawa correctness dan security debt ke seluruh group plane.

## P7-J source/design complete — group media/reply/context semantics

P7-J sudah ditutup pada source/design di `test-next` setelah baseline P7-I `642c7d6620f74b96afa5053e33ba5fe7253cbb07`.

Closure teknis canonical ada di:

`docs/design/assistant-parity-p7j-group-context.md`

Fondasi yang sekarang berlaku:

```text
Telegram Assistant group message
        ↓
canonical MessageContext
        ├─ media / grouped id / entities
        ├─ reply message + reply peer
        ├─ forum topic/root
        ├─ self identity + mentions
        ↓
core.Context / core.Message
        ↓
shared TaskEngine + existing feature handler
```

Reply-based target resolution sekarang fail-closed terhadap linked chat dan cross-topic reply. Numeric ID atau explicit `@username` tetap merupakan explicit target; bila command adalah reply, argument non-target diperlakukan sebagai payload sehingga case seperti reply + `/warn repeated spam` tidak mencoba me-resolve `repeated` sebagai username. Reply yang tidak lagi dapat mengidentifikasi sender juga tidak boleh jatuh kembali menjadi bare-username interpretation.

Assistant context sekarang mempunyai semantics canonical:

```text
MentionedSelf()
RepliedToSelf()
AddressedToSelf()
```

Mention check tetap zero-RPC; reply-to-self baru melakukan lazy reply lookup ketika memang diperlukan. Mention/reply biasa tidak menjadi command protocol kedua dan tidak melewati canonical slash-command routing.

Forum ordering sekarang memakai:

```text
chat:<chat_id>
chat:<chat_id>:topic:<topic_id>
```

melalui `core.GroupOrderingKey`, dan dipakai oleh canonical group commands, P7-I group-rule work, filter continuation/delivery, serta dynamic Assistant SavedResponse. Topic berbeda tidak saling memakai ordering lane yang sama.

Response text/media memakai `MessageSendContext{ReplyToID, TopicID}`. Untuk text, Telegram memperoleh direct reply + `TopMsgID`; media tetap memakai existing gotd builder yang di-anchor ke originating reply/topic. Yang penting, topic-scoped response sekarang **tidak boleh** fallback ke plain transport yang tidak mampu mempertahankan thread: fallback tersebut menghasilkan `ErrUnavailable` daripada mengirim ke General/other topic.

P7-J tidak menambahkan topic registry, per-topic goroutine, ticker, polling loop, worker pool, TaskEngine kedua, atau Telegram transport kedua. Album identity hanya dipertahankan sebagai `GroupedID`; tidak ada permanent album collector.

Regression/architecture coverage sekarang mengunci linked-peer rejection sebelum RPC, cross-topic reply rejection, topic-root normalization, reply-target precedence, media/self propagation, topic-scoped command + rule ordering, contextual `ReplyToMsgID/TopMsgID`, fail-closed text/media fallback, serta architecture boundary canonical P7-J.

Dengan ini **P7-J CLOSED dari sisi source/design**. Execution evidence repository-wide (`go test ./...`, race suite, full build/CI) tidak diklaim dari environment ini.

Tahap berikutnya sesuai roadmap adalah **P7-K — lifecycle/resource hardening**: audit seluruh group plane P7-A→J terhadap idle footprint, bounded caches/state, TaskEngine quota/backpressure, FloodWait behavior, cancellation/shutdown, dan memastikan tidak ada resource growth berdasarkan jumlah group/topic/user historis.

## P7-K source/design complete — lifecycle/resource hardening

P7-K sudah ditutup pada source/design setelah audit ulang seluruh group plane P7-A→J.

Closure teknis lengkap ada di:

`docs/design/assistant-parity-p7k-lifecycle-resource.md`

Perubahan utamanya bukan membuat runtime baru, tetapi menyatukan pressure/lifecycle boundary yang sudah ada.

Seluruh work group async sekarang memakai aggregate TaskEngine quota owner:

```text
telegram:chat:<chat_id>
```

untuk canonical Assistant group commands, dynamic SavedResponse group commands, P7-I group rules, filter continuation/delivery, dan GroupService EventBus tasks. Topic tetap menjadi transient ordering identity melalui `chat:<chat_id>:topic:<topic_id>`, bukan quota owner baru per-topic. Dengan default admission sekarang satu chat dibatasi 50 waiting / 10 active, sementara pool global dibatasi backlog 500.

Queue age juga dibatasi: group rule 5 detik, group command/SavedResponse 10 detik, GroupService mengikuti subscriber timeout, dan filter continuation mengikuti execution timeout. Canonical group command tanpa timeout eksplisit sekarang memperoleh 30 detik execution timeout sehingga tidak dapat menahan TaskEngine worker tanpa batas.

P7-K menemukan dan menutup satu bug produksi pada filter continuation: WorkSpec sebelumnya mempunyai topic ordering key tetapi tidak mempunyai `QuotaOwner`, sehingga production TaskEngine dapat menolaknya walaupun mock test menerima. Continuation sekarang memakai owner chat canonical.

Bounded state yang diverifikasi:

```text
group-role cache         4096
role verification slots    32
peer cache               4096
GroupState default rows  10000
GroupState hard rows     50000
blacklist/filter rules     512/chat
compiled rule cache        500 chats/domain
filter cooldown            1000
warning rows              50000
warning lock stripes         64
RPC limiter buckets        4096
RPC penalties              4096
service-event users          64/event
```

Group-event state juga diperketat. Disabled welcome/goodbye config tidak lagi ditahan pada hot map; state tetap durable dan dibaca lazy untuk status/config. EventBus subscription GroupService sekarang transport-aware: tidak ada subscriber hanya karena config durable aktif ketika Assistant transport belum hidup, dan `SetTransport(nil)` melepas subscriber. Reattach transport memasang subscription kembali tanpa poller.

Membership service update dengan user list besar sekarang hanya mematerialisasi maksimum 64 user object; total count dibawa terpisah agar template `{count}`/“and N more” tetap berguna tanpa retained payload linear terhadap seluruh action.

P7-K juga menutup fallback topic pada filter/group-rule adapter: transport yang tidak mampu mempertahankan `TopicID` menghasilkan `ErrUnavailable`, bukan plain-send ke General/topic lain.

Role resolver tetap lazy LRU tanpa worker/ticker/wait queue. Saat 32 verification slot penuh, lookup baru fail-fast dengan `ErrGroupRoleSaturated`. GroupState tetap occurrence-driven tanpa cleanup worker. EventBus worker bersifat lazy dan retire saat idle. TaskEngine menghapus owner counters dan ordering locks ketika state kembali nol.

Semua Assistant Telegram path tetap memakai shared application RPCExecutor. Hierarchical RPC limiter bounded/fail-closed; active FloodWait penalty tidak dibuang untuk membuka kapasitas. Non-idempotent Assistant mutation memakai satu attempt dan inline FloodWait max 5 detik.

Shutdown tetap memakai satu App-owned global deadline: quiesce ingress → drain/stop runtime → cancel transport. Assistant exit melepas GroupEvent transport, GroupRule transport, dan role resolver. Tidak ada per-group/per-topic permanent goroutine yang ditambahkan P7-K.

Architecture fence baru:

`internal/architecture/assistant_p7k_test.go`

mengunci cache/state bounds, chat quota, queue/execution deadlines, RPC limiter bounds, owner/ordering cleanup, shutdown ordering, transport-aware subscription, serta larangan per-chat worker/ticker pada group state services.

Dengan ini **P7-K CLOSED dari sisi source/design**. Full build/vet/test/race dan benchmark high-cardinality tidak diklaim dari environment ini; evidence tersebut sengaja menjadi bagian P7-L.

Tahap group-plane yang tersisa sekarang hanya **P7-L — final acceptance**.

Satu gap nyata ditemukan pada final acceptance: setelah P7-K menyatukan seluruh topic di satu chat ke aggregate quota owner `telegram:chat:<id>`, TaskEngine owner queue masih memilih FIFO head saja. Case:

```text
A1 running
A2 queued + blocked ordering key A
B1 queued behind A2 with independent ordering key B
```

membuat B1 ikut tertahan. P7-L memperbaiki admission selector agar mencari earliest eligible entry di owner queue yang sudah bounded. Same-topic tetap serial, tetapi topic berbeda tidak lagi terkena head-of-line blocking. Tidak dibuat per-topic queue/worker baru.
