Ya. Untuk **Assistant v2.5**, saya sarankan kita tidak lagi menganggapnya sebagai “Assistant v2 + beberapa patch”. Ini harus menjadi **fix arsitektur functional parity** di atas v2 yang sekarang.

# Assistant v2.5 — Technical Specification + Migration Map

## 0. Tujuan utama

Invariant baru:

> **One functionality, one implementation, multiple execution surfaces.**

Artinya:

```text
                         GoUltroid
                            │
                    ┌───────┴────────┐
                    │                │
             Capability/Plugin    Shared Services
                    │                │
              ┌─────┴─────┐          │
              │           │          │
          Userbot      Assistant     │
          Surface       Surface      │
              │           │          │
              └─────┬─────┘          │
                    ▼                ▼
                 Use Case ───────────┘
                    │
                    ▼
                 Telegram
```

**Assistant tidak boleh memiliki implementasi functionality sendiri apabila functionality tersebut sudah dimiliki plugin/core.**

---

# 1. Masalah yang v2.5 harus selesaikan

Dari audit kode terbaru, ada enam masalah utama.

### P0 — Duplicate functionality

Sekarang:

```text
Userbot
 └── plugin

Assistant
 └── assistant/command/*
```

Contoh `/ping` dan `/alive` mempunyai implementasi terpisah.

Target:

```text
Plugin / Capability
       │
       ▼
 Shared Use Case
    │       │
    ▼       ▼
Userbot  Assistant
```

---

### P0 — Plugin manager hanya mengenal Userbot

`plugin.Plugin` saat ini hanya mendefinisikan:

```text
Name
Commands
Init
```

dan `Manager` mendaftarkan command ke `core.Router`.

Assistant tidak ikut dalam lifecycle plugin tersebut.

---

### P0 — Dua command registry

Sekarang ada:

```text
core.Router
assistant/command.Router
```

Ini harus menjadi:

```text
Unified Command Registry
```

dengan surface/capability sebagai metadata.

---

### P1 — Assistant masih hybrid v2 + legacy

`BotClient` terbaru masih mempunyai:

```text
v2Router
+
legacy callbackRouter
+
inlineEngine
+
eventBus
```

dan callback update memilih v2 atau legacy berdasarkan payload.

V2.5 harus menghilangkan dual execution path.

---

### P1 — Assistant menu adalah functionality sendiri

Menu boleh khusus Assistant.

Tetapi:

```text
Settings UI
Admin UI
Status UI
Feature toggles
```

tidak boleh mengandung duplicate business logic.

Menu adalah **presentation/controller**, bukan domain implementation.

---

### P1 — Context Userbot dan Assistant belum unified

Kita membutuhkan satu semantic:

```text
ExecutionContext
```

dengan:

```text
Source
Actor
Peer
Message
Permissions
Capabilities
Transport
```

---

# 3. Definisi baru: Capability

Kita membutuhkan konsep `Capability`.

```go
type Capability struct {
    ID          string
    Description string

    Userbot     bool
    Assistant   bool
    Inline      bool
}
```

Contoh:

```text
ping
 ├── Userbot   ✓
 ├── Assistant ✓
 └── Inline    ✗

alive
 ├── Userbot   ✓
 ├── Assistant ✓
 └── Inline    ✗

ban
 ├── Userbot   ✓
 ├── Assistant ✓
 └── Inline    ✗
```

Ini membuat parity menjadi **explicit**, bukan asumsi.

---

# 4. Plugin menjadi capability provider

Plugin tetap menjadi source of truth.

Current:

```go
type Plugin interface {
    Name() string
    Commands() []core.Command
    Init() error
}
```

V2.5:

```go
type Plugin interface {
    Name() string
    Commands() []core.Command
    Capabilities() []Capability
    Init() error
}
```

Tetapi jangan memaksa semua plugin langsung implement `Capabilities()`.

Untuk migration:

```go
type CapabilityProvider interface {
    Capabilities() []Capability
}
```

Dengan demikian plugin lama tetap compatible.

---

# 5. Command menjadi surface-aware

Current:

```text
Command
 ├── Name
 └── Handler
```

Target:

```go
type Command struct {
    Name       string
    Aliases    []string
    Handler    Handler

    Surfaces   SurfaceMask
    Permission PermissionPolicy
}
```

Contoh:

```text
ping
  Surfaces = Userbot | Assistant

ban
  Surfaces = Userbot | Assistant

internal-debug
  Surfaces = Userbot
```

---

# 6. Unified Command Registry

Target:

```text
CommandRegistry
       │
       ├── Userbot dispatcher
       │
       ├── Assistant dispatcher
       │
       └── future inline dispatcher
```

Bukan:

```text
core.Router
assistant.command.Router
```

masing-masing memiliki command sendiri.

# 7. Tetapi jangan memaksa transport memakai handler yang sama

Ini sangat penting.

**Logic sama ≠ Telegram operation sama.**

Contoh `/ping`:

```text
                    PingUseCase
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
      Userbot adapter          Assistant adapter
             │                       │
      edit/reply message        bot reply
```

Handler transport hanya bertugas menerjemahkan input/output.

---

# 8. Execution Context v2.5

Buat:

```go
type Source int

const (
    SourceUserbot Source = iota
    SourceAssistant
    SourceInline
)
```

Context:

```go
type Context struct {
    Context context.Context

    Source Source

    Actor Actor
    Chat  ChatContext

    Permissions PermissionSet

    Message MessageContext

    Capabilities CapabilitySet
}
```

Plugin tidak perlu bertanya:

```text
"Apakah ini Assistant?"
```

kecuali memang behavior-nya transport-specific.

# 9. Capability vs Permission

Jangan dicampur.

### Capability

```text
Apakah Assistant boleh menjalankan fitur ini?
```

### Permission

```text
Apakah user ini boleh menjalankan fitur ini?
```

Jadi:

```text
Callback
 ↓
Surface capability
 ↓
Authorization
 ↓
Plugin/usecase
```

# 10. Unified execution flow

### Userbot

```text
Telegram update
      ↓
Userbot dispatcher
      ↓
Command registry
      ↓
Capability check
      ↓
Permission check
      ↓
ExecutionContext
      ↓
Plugin/usecase
      ↓
Userbot response adapter
```

### Assistant

```text
Telegram update
      ↓
Assistant dispatcher
      ↓
Command registry
      ↓
Capability check
      ↓
Permission check
      ↓
ExecutionContext
      ↓
Plugin/usecase
      ↓
Assistant response adapter
```

**Titik eksekusi setelah permission harus sama.**

# 11. Callback flow

Callback bukan plugin functionality baru.

Misalnya:

```text
Settings
 → Features
 → Toggle X
```

Callback hanya menjadi:

```text
UI event
   ↓
Command/Action
   ↓
same use case
```

Contoh:

```text
a1:settings:toggle:foo
```

→

```text
SettingsUseCase.Toggle("foo")
```

Bukan:

```text
AssistantSettings.Toggle()
```

yang mengimplementasikan logic sendiri.

# 19. Addon

 ↓

# 20. Plugin lifecycle

Plugin manager yang sekarang sudah mempunyai transactional registration dan reverse-order shutdown. Itu bagus dan sebaiknya dipertahankan.

Yang ditambahkan:

```text
Plugin registration
      ↓
Command registration
      ↓
Capability registration
      ↓
Surface availability
```

Saat shutdown:

```text
Assistant stop
 ↓
dispatcher stop
 ↓
plugin execution drain
 ↓
plugin shutdown
```

Jangan sampai Assistant dimatikan tetapi plugin masih menerima callback.

# 32. Apa yang tetap unik milik Assistant?

Ini penting supaya kita tidak overcorrect.

Assistant **tetap boleh memiliki**:

```text
assistant/client
assistant/interaction
assistant/peer
assistant/callback
assistant/menu
assistant/presentation
```

Karena itu adalah **transport/UI mechanics**.

Yang tidak boleh diduplikasi:

```text
business logic
plugin logic
database mutation
settings semantics
permission semantics
capability semantics
runtime state semantics
```

# 33. Rule sederhana untuk code review

Mulai sekarang setiap implementasi Assistant harus melewati pertanyaan:

> **"Apakah ini functionality baru, atau hanya adapter/presentation untuk functionality yang sudah ada?"**

Jika sudah ada di plugin/core:

```text
❌ jangan implement ulang
```

Gunakan:

```text
plugin/usecase
```

Jika hanya terkait Telegram Assistant:

```text
✅ implement di assistant/
```

Contoh:

```text
Inline keyboard rendering       → Assistant
Callback query lifecycle       → Assistant
Peer resolution                 → Assistant
Bot token authentication        → Assistant

Ban logic                       → Shared
Settings mutation               → Shared
Ping semantics                  → Shared
Alive data                      → Shared
Permission                      → Shared/core
Database operation              → Shared
```

# 34. Definition of Done v2.5

Assistant v2.5 baru selesai jika:

### Functional unity

* [ ] Plugin adalah source of truth.
* [ ] Assistant tidak mempunyai duplicate business implementation.
* [ ] Userbot dan Assistant menggunakan capability registry yang sama.
* [ ] Command registry unified.
* [ ] Permission semantics unified.
* [ ] Settings state unified.
* [ ] Runtime status unified.
* [ ] Addon capability unified.

### Assistant-specific

* [ ] Callback engine v2 only.
* [ ] Target immutable.
* [ ] Peer resolver reliable.
* [ ] Message/inline target separated.
* [ ] Delete idempotent.
* [ ] Callback answer exactly-once.
* [ ] Lifecycle deterministic.
* [ ] Menu/presentation tetap Assistant-specific.

### Parity

Minimal:

```text
ping
alive
status
help
settings
admin
common addons
common plugins
```

harus menggunakan **shared functionality**.

# 35. Urutan pengerjaan yang paling aman

Saya akan eksekusi seperti ini:

```text
                   V2.5
                    │
                    ▼
        ┌───────────────────────┐
        │ 1. Execution Context  │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 2. Capability Registry│
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 3. Unified Commands   │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 4. Ping reference     │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 5. Alive reference    │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 6. Help               │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 7. Settings           │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 8. Callback → UseCase │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 9. Plugins/Addons     │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 10. Remove duplicates │
        └───────────────────────┘
```

### Yang paling penting

**Jangan mulai dengan mengubah semua plugin sekaligus.** Jadikan `ping → alive → help → settings` sebagai **reference migration**, karena empat fitur itu mewakili empat jenis masalah berbeda:

* `ping` → shared command/use-case
* `alive` → shared runtime service
* `help` → registry-driven presentation
* `settings` → shared state + callback/menu

Kalau empat ini sudah benar, pola yang sama bisa diterapkan ke plugin lain.

Dengan v2.5 ini, target akhirnya bukan sekadar **“Assistant punya fitur yang sama dengan Userbot”**, tetapi jauh lebih kuat:

> **Userbot dan Assistant adalah dua execution surface dari GoUltroid yang sama.**

Jadi kalau besok kita memperbaiki logic `settings`, `admin`, `ping`, atau addon tertentu, **perbaikannya otomatis berlaku untuk Userbot dan Assistant**, bukan harus memperbaiki dua implementasi terpisah lagi.
