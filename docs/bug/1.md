## 1. Runtime sekarang jauh lebih sehat

Perubahan paling bagus adalah adanya `opMu` terpisah dari state mutex.

Sekarang `Start()`:

```go
r.opMu.Lock()
defer r.opMu.Unlock()

r.mu.Lock()
...
r.mu.Unlock()

for _, comp := range order {
    err := comp.Start(...)
}
```

dan `performStop()` juga hanya memakai `r.mu` untuk snapshot state/order, lalu melepasnya sebelum memanggil component.

Ini menghilangkan kelas deadlock:

```text
Runtime lock
   ↓
Component.Start/Stop
   ↓
component callback ke Runtime
   ↓
deadlock
```

Jadi temuan sebelumnya untuk foreign code di bawah coordinator mutex: **fixed dengan benar**.

# 2. Quiesce/Drain sudah masuk Runtime — bagus

Sekarang Runtime shutdown melakukan:

```text
Quiesce phase
    ↓
Drain phase
    ↓
Stop phase
```

melalui optional interfaces.

Worker manager juga sekarang mempunyai:

```go
func (m *Manager) Quiesce(...)
func (m *Manager) Drain(...)
```

dan `Health()` sudah tidak nested-RLock lagi.

Ini adalah improvement arsitektural yang signifikan.

Namun implementasinya sekarang menghasilkan masalah berikut.

# 🔴 P1 — Workers di-drain dua kali

`Runtime.performStop()` melakukan:

```text
if Drainer:
    comp.Drain(ctx)

kemudian:

comp.Stop(ctx)
```

Tetapi worker manager:

```go
func (m *Manager) Stop(ctx context.Context) error {
    if err := m.Quiesce(ctx); err != nil {
        return err
    }
    return m.Drain(ctx)
}
```

Maka actual shutdown workers menjadi:

```text
Runtime.Quiesce
    ↓
workers.Quiesce()

Runtime.Drain
    ↓
workers.Drain()
        ↓
pool.Stop()

Runtime.Stop
    ↓
workers.Stop()
        ↓
workers.Quiesce()
        ↓
workers.Drain()
            ↓
pool.Stop() lagi
```

`Pool.Stop()` memang idempotent karena `sync.Once`, jadi kemungkinan tidak corrupt.

Tetapi semantics-nya salah dan menambah race/complexity.

Lebih parah, `Drain()` membuat goroutine baru:

```go
go func() {
    m.admissionWG.Wait()
    close(admissionsDone)
}()
```

setiap dipanggil.

Jadi secara desain:

> `Drain()` harus benar-benar Drain, dan `Stop()` tidak boleh mengulang Drain kalau orchestrator sudah mengelola fase.

Saya sarankan contract:

```go
func (m *Manager) Stop(ctx context.Context) error {
    // hanya final teardown
    if m.admissionEnd != nil {
        m.admissionEnd()
    }
    return nil
}
```

atau lebih baik component punya explicit lifecycle:

```text
Quiesce()
Drain()
Stop()
```

dan jangan implement `Stop = Quiesce + Drain`.

Jika tetap ingin `Stop()` aman saat dipanggil standalone, beri internal once-state:

```go
func (m *Manager) Stop(ctx context.Context) error {
    _ = m.Quiesce(ctx)
    _ = m.Drain(ctx)
    return m.finalize()
}
```

sementara `Drain()` sendiri harus idempotent secara eksplisit.

# 5. Runtime startup cancellation sudah lebih benar, tetapi belum bisa memaksa blocking `Start()`

Sekarang dibuat:

```go
componentCtx, componentCancel := context.WithCancel(r.rootCtx)
stopOperationCancel := context.AfterFunc(ctx, componentCancel)

err := comp.Start(componentCtx)
```

Ini lebih baik.

Ketika startup ctx selesai:

```text
startup ctx canceled
      ↓
componentCtx canceled
```

Tetapi tetap cooperative.

Kalau component:

```go
func Start(ctx context.Context) error {
    select {}
}
```

Runtime tetap terjebak.

Tidak ada cara aman di Go untuk force-kill arbitrary goroutine.

Jadi ini bukan bug Runtime sepenuhnya; ini perlu jadi **component contract invariant**:

> `Start(ctx)` wajib menghormati cancellation dan tidak boleh menunggu lifetime goroutine selesai.

Start harus:

```text

return
```

bukan:

```text

```

Saya sarankan tambahkan architecture test yang menyuntik fake component yang merespons cancel.

# 6. 🔴 Runtime Stop masih mempunyai first-caller-context problem

Ini masih ada.

```go
func (r *Runtime) Stop(ctx context.Context) error {
    r.stopOnce.Do(func() {
        r.stopErr = r.performStop(ctx)
        close(r.stopDone)
    })
```

Caller pertama menentukan shutdown context seluruh Runtime.

Contoh:

```text
G1:
ctx deadline = 10ms
Runtime.Stop(ctx1)

G2:
ctx deadline = 30s
Runtime.Stop(ctx2)
```

Karena `stopOnce`:

```text
G1 ctx menjadi shutdown context global
```

Ketika ctx1 habis:

```text
performStop:
  quiesce partial
  drain partial
  stop partial
```

lalu tetap:

```go
r.rootCancel()
Transition(StateStopped)
```

Semua Stop berikutnya hanya mendapatkan hasil shutdown pertama.

Jadi:

```text
Runtime state = Stopped
```

padahal mungkin tidak semua component sudah dihentikan.

Ini menurut saya masih **P1**.

### Arsitektur lebih robust

Pisahkan:

```text
shutdown execution context
caller wait context
```

Misalnya:

```go
func (r *Runtime) Stop(ctx context.Context) error {
    r.stopOnce.Do(func() {
        go r.shutdown()
    })

    select {
    case <-r.stopDone:
        return r.stopErr
    case <-ctx.Done():
        return ctx.Err()
    }
}
```

Sedangkan:

```go
func (r *Runtime) shutdown() {
    shutdownCtx, cancel :=
        context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    r.stopErr = r.performStop(shutdownCtx)
    close(r.stopDone)
}
```

Dengan begitu caller hanya memilih:

> saya bersedia menunggu berapa lama.

Bukan:

> seluruh application hanya boleh shutdown selama saya menunggu.

Itu distinction penting.

# 9. Outbox ordering masih punya satu improvement

`ListPendingOutbox(limit=100)` kemudian stop pada first failure.

Itu bagus untuk ordering.

Tetapi worker hanya drain maksimal 100 rows per wake/tick.

Kalau backlog = 10.000:

```text
wake
 ↓
100 processed
 ↓
worker idle

next fallback tick 15 sec
 ↓
100 lagi
```

Kalau tidak ada wake baru, recovery backlog sangat lambat.

`drainOutbox()` sebaiknya looping:

```go
for {
    entries := ListPendingOutbox(ctx, 100)

    if len(entries) == 0 {
        return
    }

    process(entries)

    if len(entries) < 100 {
        return
    }
}
```

dengan optional fairness bound:

```text
max batches / max wall time
```

Misalnya 10 batches per wake lalu re-wake sendiri.

Ini **P2**, bukan correctness bug.

# 11. 🔴 Worker panic containment masih belum ada

Masih:

```go
taskErr := task.Execute(p.ctx)
```

Tanpa `recover()`.

Ini tetap salah satu titik robustness terbesar.

Apalagi task dapat berasal dari banyak service/plugin path.

Ideal:

```go
func executeTaskSafely(ctx context.Context, task tasks.Task) (err error) {
    defer func() {
        if p := recover(); p != nil {
            err = fmt.Errorf("task panic: %v", p)
        }
    }()
    return task.Execute(ctx)
}
```

dan busy harus menggunakan defer:

```go
p.busy.Add(1)
func() {
    defer p.busy.Add(-1)
    ...
}()
```

Kalau sekarang `task.Execute` panic:

```text
busy tidak decrement
worker tidak recover
process bisa crash
```

Saya klasifikasikan **P1**.

# 13. 🟠 Plugin manifest rollback punya subtle state-loss bug

Ada satu edge case baru.

`stageManifest()`:

```go
previous, existed := m.manifests[name]

gate.RegisterManifest(manifest)
```

rollback:

```go
gate.UnregisterManifest(name)

if existed {
    gate.RegisterManifest(previous)
}
```

Tetapi `CapabilityGate.UnregisterManifest()` melakukan:

```go
delete(g.manifests, pluginID)
delete(g.privilegedMap, pluginID)
```

Kalau sebelumnya plugin punya:

```text
manifest
+
privileged capability grants
```

rollback akan:

```text
delete manifest
delete privileged grants
restore manifest
```

tetapi **tidak restore privileged grants**.

Hasil:

```text
registration attempt gagal
 ↓
previous manifest restored
 ↓
privileged grants hilang diam-diam
```

Ini edge case, tapi benar-benar melanggar transactional compensation.

Fix lebih baik:

```go
type GateSnapshot struct {
    Manifest Manifest
    Privileged map[string]bool
}
```

atau gate menyediakan:

```go
func (g *CapabilityGate) ReplaceManifest(...) (restore func())
```

yang snapshot seluruh state terkait plugin.

Jangan orchestrator mengetahui separuh state gate.

# 16. Tetapi Addon IPC masih punya tiga masalah robustness

### A. stdout masih lifetime-limited 8 MiB

Masih:

```go
r.stdout = bufio.NewReader(io.LimitReader(stdout, 8<<20))
```

Artinya limit 8 MiB berlaku terhadap **seluruh lifetime stream**, bukan satu response.

Addon yang sehat dan hidup lama:

```text
100 KB response × 82 request
≈ >8 MiB
```

lalu EOF artificial.

Harus menjadi **per-frame limit**.

Misalnya:

```text
ReadBytes/ReadSlice with max frame size
```

bukan `LimitReader` pada lifetime pipe.

---

### B. write stdin masih dilakukan sambil memegang `r.mu`

Current:

```go
r.mu.Lock()
...
_, err := r.stdin.Write(...)
stdout := r.stdout
r.mu.Unlock()
```

Kalau child berhenti membaca stdin dan pipe penuh:

```text
Call()
 ↓
r.mu acquired
 ↓
stdin.Write blocks forever
 ↓
Stop()
 ↓
needs r.mu
 ↓
cannot kill process
```

Ini potensial deadlock/hang.

`callMu` sudah menyerialisasi calls, jadi sebenarnya tidak perlu menahan `r.mu` selama Write.

Pattern:

```go
r.mu.Lock()
stdin := r.stdin
stdout := r.stdout
running := r.running
r.mu.Unlock()

write...
```

Tetapi ada lifetime race; solusi terbaik adalah single IPC owner goroutine.

---

### C. stderr scanner masih default 64 KiB token

Masih:

```go
scanner := bufio.NewScanner(stderrPipe)
```

tanpa `scanner.Buffer(...)`.

Satu stderr line >64 KiB membuat scanner berhenti.

Karena `scanner.Err()` juga tidak ditangani, draining pipe berhenti diam-diam.

Lalu child dapat block ketika stderr OS pipe penuh.

Tambahkan:

```go
scanner.Buffer(make([]byte, 64*1024), maxLine)
```

dan log `scanner.Err()`.

Atau gunakan bounded line reader yang terus drain.

# 17. Ada satu issue shutdown worker yang cukup subtle

Di `Drain()`:

```go
select {
case <-admissionsDone:

case <-ctx.Done():
    if admissionEnd != nil {
        admissionEnd()
    }
    <-admissionsDone
}
```

Pada deadline, setelah cancellation, code tetap melakukan:

```go
<-admissionsDone
```

tanpa select kedua.

Kalau salah satu admission goroutine tetap tidak selesai karena bug downstream, **ctx deadline sudah tidak berguna lagi**.

Jadi:

```text
ctx timeout
 ↓
cancel admission
 ↓
wait unbounded
```

Ini bertentangan dengan tujuan bounded shutdown.

Seharusnya:

```go
case <-ctx.Done():
    admissionEnd()
    return ctx.Err()
```

Atau kasih short hard-drain grace period.

Ini saya klasifikasikan **P1** untuk shutdown reliability.

# 18. Runtime phased order perlu dipikirkan lagi

Saat ini:

```go
for phase in [quiesce, drain] {
    for comp in stopOrder {
        phase(comp)
    }
}
```

`stopOrder` adalah reverse startup order.

Untuk `Quiesce`, reverse order masuk akal:

```text
ingress/dependent first
```

Untuk `Drain`, belum tentu seluruh component harus reverse order.

Misalnya:

```text
producer → queue → consumer
```

Shutdown ideal:

```text
producer.Quiesce
queue.Quiesce

consumer drains queue

producer drain irrelevant
```

Jadi semakin matang architecture-nya, phase semantics sebaiknya menjadi explicit capabilities bukan otomatis semua component dipanggil dengan urutan sama.

Namun implementasi sekarang masih acceptable sebagai tahap pertama.

## Prioritas perbaikan berikutnya

Kalau saya urutkan berdasarkan dampak terhadap target Anda — **sinkronisasi mulus, robust, atomic, anti partial-error** — saya kerjakan dalam urutan ini:

1. **P1 — perbaiki `Runtime.Stop()` supaya shutdown memakai internal context, caller ctx hanya untuk wait.**
2. **P1 — hilangkan double lifecycle semantics `Drain()` lalu `Stop()->Drain()` lagi.**
3. **P1 — perbaiki unbounded wait setelah worker drain context expired.**
4. **P1 — tambah panic boundary pada worker task execution.**
5. **P1/P2 — pecah `infrastructureComponent` menjadi component DAG yang nyata.**
6. **P2 — snapshot seluruh CapabilityGate state saat manifest staging supaya rollback benar-benar lossless.**
7. **P2 — jangan panggil auditor sambil gate lock aktif.**
8. **P2 — perbaiki Addon IPC: per-frame stdout limit, nonblocking lifecycle-safe writer, stderr drain robust.**
9. **P2 — loop outbox batches sampai backlog habis/budget tercapai.**

Kesimpulannya: **perubahan terbaru benar-benar memperbaiki sebagian besar masalah utama**, bukan sekadar kosmetik. Saya sekarang akan menilai orchestration core sekitar **8.8/10**, naik cukup besar. Yang tersisa sudah lebih banyak berupa **shutdown semantics dan failure-edge correctness**, bukan masalah fundamental struktur.
