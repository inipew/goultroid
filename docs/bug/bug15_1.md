Sudah saya lanjutkan audit dengan **source Ultroid + source GoUltroid terbaru**, dan hasilnya cukup jelas: **memang lebih tepat rebuild subsystem Assistant interaction daripada meneruskan patch sekarang.**

## 1. Behavioral baseline dari Ultroid

Implementasi Ultroid sebenarnya sederhana tetapi boundary-nya jelas:

* `asst_cmd` → command handler Assistant.
* `callback(...)` → callback registration + authorization wrapper.
* `in_pattern(...)` → inline-query handler.
* callback handler sendiri melakukan `event.answer()`, `event.edit()`, atau `event.delete()`.
* exception pada callback ditangkap sehingga tidak menjatuhkan event handler.

Untuk menu, Ultroid menggunakan callback data langsung seperti:

```text
cbs_apiset
cbs_chatbot
cbs_alvcstm
mainmenu
closeit
```

dan handler kemudian mengedit/delete event tersebut.

Yang menarik: **Ultroid tidak mencoba membuat abstraction Telegram yang terlalu generik.** Telethon sudah menyelesaikan banyak kompleksitas target message untuk mereka.

Di GoUltroid kita memakai gotd, sehingga abstraction tersebut memang harus kita bangun sendiri.

Itulah mismatch fundamentalnya.

# 3. CRITICAL — Message identity masih tidak konsisten

Ini temuan terbesar.

Current:

```go
func (a *BotServiceAdapter) GetMessage(
    ctx context.Context,
    peer tg.InputPeerClass,
    msgID int,
) (*tg.Message, error)
```

tetapi implementasinya:

```go
MessagesGetMessages(
    ctx,
    []tg.InputMessageClass{
        &tg.InputMessageID{ID: msgID},
    },
)
```

**`peer` bahkan tidak digunakan.**

Ini berarti abstraction API mengatakan:

```text
GetMessage(peer, msgID)
```

tetapi implementasinya sebenarnya:

```text
GetMessage(msgID)
```

Itu salah secara semantic untuk dialog-scoped Telegram messages.

Hal yang sama terjadi pada generic delete:

```go
MessagesDeleteMessagesRequest{
    ID: msgIDs,
}
```

lagi-lagi `peer` tidak dipakai.

Kemudian kita membuat `delete.go` khusus untuk menambal Close.

**Ini persis alasan kenapa saya setuju rebuild.**

# 4. CRITICAL — Service abstraction terlalu lebar

`BotServiceAdapter` saat ini mengimplementasikan `core.TelegramServicer`.

Akibatnya Assistant dipaksa menjadi semacam:

```text
TelegramServicer
├── SendMessage
├── EditMessage
├── DeleteMessage
├── React
├── GetMessage
├── Pin
├── Forward
├── Download
├── SendMedia
├── Ban
├── Kick
├── Mute
├── Promote
├── ...
```

Padahal Assistant interaction sebenarnya hanya membutuhkan subset kecil.

Sebagian besar bahkan:

```go
return core.ErrUnsupported
```

Contohnya moderation, media, download, dialogs, full user, dll.

Ini tanda kuat bahwa:

> **Assistant seharusnya tidak bergantung pada `TelegramServicer` yang merupakan abstraction untuk userbot/general Telegram operations.**

Kita perlu interface khusus Assistant.

# 5. CRITICAL — CallbackContext terlalu banyak tanggung jawab

Saat ini `CallbackContext` menangani:

```text
Answer
Edit
EditText
EditMarkup
Delete
GetMessage
ShowProgress
ShowSuccess
ShowError
DisableButtons
RemoveMarkup
AnswerError
AnswerSuccess
```

Selain metadata callback.

Ini sudah menjadi:

> router context + Telegram interaction API + UX helper + error presentation.

Terlalu gemuk.

Lebih sehat:

```text
CallbackEvent
        │
        ▼
Interaction
        │
        ├── Answer()
        ├── Edit()
        ├── EditMarkup()
        ├── Delete()
        └── Message()
```

Sedangkan:

```text
ShowSuccess
ShowError
ShowProgress
```

sebaiknya menjadi presentation/controller concern, bukan primitive interaction.

# 6. CRITICAL — `answered bool` belum cukup untuk concurrency

Current:

```go
answered bool
```

dan:

```go
func (c *CallbackContext) Answer(...) error {
    ...
    err := c.Service.AnswerCallbackQuery(...)
    if err == nil {
        c.answered = true
    }
}
```

Masalahnya:

```text
goroutine A → Answer()
goroutine B → Answer()
```

keduanya bisa masuk sebelum `answered` berubah.

Selain itu `answered` bukan synchronization primitive.

Untuk architecture baru, callback lifecycle harus punya state machine:

```text
Received
   │
   ├── Answered
   │
   ├── Executing
   │
   └── Completed
```

dan answer operation harus **single-flight / exactly-once locally**.

---

# 7. CRITICAL — AutoAnswer abstraction sebenarnya tidak cocok untuk interaction baru

Current router memiliki:

```go
CallbackHandlerOptions{
    AutoAnswer bool
}
```

dan Assistant mematikan:

```go
AutoAnswer: false
```

supaya handler mengurus answer sendiri.

Ini sudah menunjukkan desain conflict:

```text
Router ingin mengontrol lifecycle
        VS
Handler ingin mengontrol lifecycle
```

Untuk subsystem baru:

### Router

hanya:

```text
decode
validate
authorize
resolve handler
create interaction
execute
recover
observe
```

### Interaction executor

yang menjamin:

```text
callback answer lifecycle
```

Dengan demikian **tidak perlu `AutoAnswer` sebagai escape hatch**.

# 8. HIGH — Callback data design terlalu kompleks untuk menu statis

Current format:

```text
v1:<namespace>:<action>:<opaque-id>
```

Contoh:

```text
v1:assistant:nav:<opaque>
```

Ini bagus untuk stateful callbacks.

Tetapi untuk menu statis seperti Ultroid:

```text
mainmenu
closeit
setter
stat
```

kita sebenarnya tidak selalu membutuhkan state store + opaque ID.

Lebih baik architecture mendukung dua mode:

### Static action

```text
a1:assistant:close
a1:assistant:settings
```

### Stateful action

```text
a1:assistant:select:<state-id>
```

Dengan batas payload tetap tervalidasi.

Jadi tidak semua button harus memaksa lifecycle state.

# 9. HIGH — Callback target seharusnya immutable

Current callback target dibangun langsung di dispatcher:

```go
target := core.CallbackTarget{
    Origin: CallbackOriginMessage,
    Peer: inputPeer,
    MessageID: update.MsgID,
    ChatInstance: update.ChatInstance,
}
```

Masalahnya adalah `inputPeer` bergantung pada cache/access hash yang mutable.

Lebih bagus:

```text
Raw Telegram Update
       │
       ▼
TargetResolver
       │
       ▼
ResolvedTarget
```

dan setelah resolved:

```go
type ResolvedMessageTarget struct {
    Peer tg.InputPeerClass
    ID   int
}
```

immutable.

Kalau resolver gagal:

```text
callback tidak masuk business handler
```

bukan:

```text
handler masuk → nanti RPC gagal MESSAGE_ID_INVALID
```

---

# 10. HIGH — Access hash cache masih terlalu sederhana

Current:

```text
userHashes
channelHashes
```

dengan:

```go
map[int64]int64
```

Masalah:

* tidak ada expiry
* tidak ada invalidation
* tidak ada source metadata
* tidak ada negative cache
* tidak ada resolution fallback
* access hash stale tidak dibedakan dari missing
* tidak ada concurrency-aware resolve operation

Untuk subsystem baru:

```go
type PeerRecord struct {
    ID         int64
    AccessHash int64
    Kind       PeerKind
    UpdatedAt  time.Time
}
```

dan resolver:

```text
entity
 ↓
cache
 ↓
API resolution
 ↓
refresh cache
```

Jika RPC mengembalikan access-hash-related error:

```text
invalidate
 ↓
re-resolve
 ↓
retry exactly once
```

**bukan infinite retry.**

# 11. HIGH — Error handling sekarang terlalu transport-oriented

Contoh:

```text
assistant bot EditMessageMarkup:
rpc error code 400: MESSAGE_ID_INVALID
```

Ini bagus untuk logging, tetapi business layer tidak tahu:

```text
target invalid
message already deleted
message inaccessible
peer resolution failed
callback expired
callback already answered
```

Architecture baru harus mempunyai typed error taxonomy:

```text
ErrInvalidTarget
ErrMessageNotFound
ErrMessageAlreadyDeleted
ErrPeerResolution
ErrAccessHashStale
ErrCallbackExpired
ErrCallbackAlreadyAnswered
ErrUnauthorized
ErrCallbackTooOld
ErrUnsupportedTarget
```

Kemudian mapping:

```text
Telegram RPC error
        ↓
Assistant error
        ↓
UX policy
        ↓
toast / edit / silent / log
```

# 12. HIGH — Close sebenarnya harus idempotent

Behavior Ultroid:

```python
@callback("closeit")
async def closet(lol):
    try:
        await lol.delete()
    except MessageDeleteForbiddenError:
        await lol.answer("MESSAGE_TOO_OLD", alert=True)
```

Untuk GoUltroid yang lebih robust:

```text
Close
 ↓
Answer
 ↓
Delete
 ↓
success
```

Kalau message ternyata sudah dihapus:

```text
MESSAGE_ID_INVALID
MESSAGE_NOT_MODIFIED
message not found
```

harus dipertimbangkan sebagai:

```text
desired state = message absent
actual state   = message absent
→ SUCCESS
```

Ini konsep **idempotent destructive operation**.

Jadi tombol Close tidak boleh error hanya karena message sudah tidak ada.

# 13. HIGH — Inline interaction sudah dipisahkan, tetapi delete semantics belum lengkap

Current `CallbackContext.Delete()`:

```text
if inline:
    ErrUnsupported
```

Itu benar secara prinsip.

Tetapi architecture baru harus membuat ini structural:

```go
type InteractionTarget interface {
    Kind() TargetKind
}

type MessageTarget ...
type InlineTarget ...
```

Sehingga compiler/type system membantu kita.

Bukan:

```go
if c.IsInline() { ... }
```

di setiap operation.

# 15. MEDIUM — Menu state belum benar-benar stateful

Sekarang menu lebih seperti:


Belum benar-benar:


# 16. Security: Ultroid behavior perlu dipertahankan tetapi diperketat

Ultroid callback decorator sudah mempunyai:

```text
admins
from_users
owner
```

dan unauthorized owner callback dijawab:

```text
This is OWNER's bot!!
```

GoUltroid harus mempertahankan konsep tersebut, tetapi authorization harus terjadi **sebelum business action**:

```text
callback
 ↓
decode
 ↓
target validation
 ↓
identity validation
 ↓
authorization
 ↓
handler
```

Bukan handler sendiri yang menentukan apakah aman.

```text
 ↓

 ↓

```

```go

```

dipakai sebagai indikator running.

```text

 ↓

 ↓

```

Kita sebaiknya punya explicit state.

Karena:

```text

```

harus deterministic.

### Target kualitas akhirnya

Bukan sekadar:

> "Close bekerja."

Tetapi:

> **Untuk setiap Telegram callback, kita selalu tahu siapa yang menekan, callback berasal dari message atau inline message, target persis apa, peer bagaimana diperoleh, apakah user berhak, apakah callback masih valid, apakah callback sudah di-answer, operasi Telegram apa yang harus dipanggil, bagaimana error dipetakan, dan apakah operasi tersebut idempotent.**

Itulah baseline yang menurut saya layak disebut **production-grade Assistant subsystem**.

Dan setelah audit ini, **saya tidak menyarankan kita mengubah kode lagi sekarang**. Tahap berikutnya harus membuat **Assistant v2 technical specification + migration map** terlebih dahulu, termasuk mapping setiap fitur Ultroid (`start`, `ownerinfo`, `mainmenu`, `settings`, `stats`, `broadcast`, `timezone`, callback, inline) ke architecture baru. Ultroid source menunjukkan fitur-fitur tersebut memang merupakan bagian nyata dari Assistant, bukan sekadar menu dummy.
