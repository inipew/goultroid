Siap. Berdasarkan audit sebelumnya, **Assistant v2 sebaiknya bukan sekadar refactor `internal/assistant`**, tetapi rebuild boundary interaksi Assistant agar `callback → target → peer → RPC → lifecycle` menjadi deterministic.

# Assistant v2 — Technical Specification + Migration Map

## 1. Target akhir

Target Assistant v2:

> **Telegram Assistant interaction layer yang deterministic, type-safe, idempotent, transport-aware, dan memiliki behavioral parity dengan Ultroid tanpa mewarisi kelemahan abstraksi Telethon/implementasi lama.**

Prioritas:

1. Tidak ada lagi `MESSAGE_ID_INVALID` akibat target/message identity yang salah.
2. Callback query selalu mempunyai lifecycle yang jelas.
3. Callback answer maksimal sekali.
4. Delete/edit menggunakan target Telegram yang benar.
5. Message callback dan inline callback dipisahkan secara struktural.
6. Peer/access-hash resolution menjadi boundary tersendiri.
7. Close/delete idempotent.
8. Menu tidak bergantung pada `TelegramServicer` yang terlalu besar.
9. Authorization berada sebelum business handler.
10. `/ping` dan `/alive` Assistant memiliki semantic parity dengan userbot.
11. Restart/shutdown Assistant deterministic.
12. Semua komponen dapat dites tanpa Telegram network.

# 4. `interaction` — boundary paling penting

Ini adalah perubahan paling fundamental.

## 4.1 Target

Jangan lagi:

```go
CallbackContext {
    ChatID
    MsgID
    Target
    Service
    ...
}
```

yang kemudian mencoba memahami semua kemungkinan.

Gunakan typed target.

```go
type Target interface {
    target()
}

type MessageTarget struct {
    Peer      tg.InputPeerClass
    MessageID int
}

type InlineTarget struct {
    QueryID   int64
    MessageID string
}
```

Secara konseptual:

```text
MessageTarget
 ├── peer
 └── message ID

InlineTarget
 ├── inline message ID
 └── query identity
```

Dengan demikian:

```go
Delete(MessageTarget)
```

valid.

Sedangkan:

```go
Delete(InlineTarget)
```

secara API memang tidak tersedia.

Ini lebih baik daripada:

```go
if ctx.IsInline() {
    return ErrUnsupported
}
```

di dalam implementation.

Itu urusan userbot/core service.

# 7. Stale access hash recovery

Ini wajib.

Flow:

```text
RPC
 │
 ├── success
 │
 └── ACCESS_HASH_INVALID
          │
          ▼
     invalidate cache
          │
          ▼
     resolve entity
          │
          ▼
       retry once
          │
      ┌───┴───┐
      ▼       ▼
   success   fail
```

**Tidak boleh infinite retry.**

Kontrak:

# 16. Close semantics

Close harus mempunyai semantic:

> Desired state = message does not exist.

Bukan:

> RPC delete harus selalu sukses.

Flow:

```text
Close
 ↓
Answer callback
 ↓
Delete target
 ↓
 ├── success → done
 ├── MESSAGE_ID_INVALID → already absent → done
 ├── message not found → already absent → done
 └── other RPC → error
```

Dengan ini Close menjadi idempotent.

# 42. Definition of Done

Assistant v2 **belum dianggap selesai** hanya karena menu terlihat bekerja.

Harus memenuhi:

### Correctness

* [ ] message target immutable
* [ ] peer selalu tersedia untuk message mutation
* [ ] access hash resolution reliable
* [ ] stale hash recovery
* [ ] callback answer exactly-once
* [ ] delete idempotent
* [ ] inline/message structurally separated

### Architecture

* [ ] no dependency on broad `TelegramServicer`
* [ ] callback lifecycle centralized
* [ ] menu separated from transport
* [ ] rendering separated from mutation
* [ ] authorization before handler

### Reliability

* [ ] restart-safe
* [ ] shutdown deterministic
* [ ] duplicate callback safe
* [ ] stale callback safe
* [ ] RPC errors classified
* [ ] retry bounded

# 43. Urutan implementasi yang saya rekomendasikan

**Jangan mulai dari menu.**

Urutan paling aman:

```text
1. interaction target
        ↓
2. peer resolver
        ↓
3. Telegram message interaction
        ↓
4. callback payload
        ↓
5. callback lifecycle
        ↓
6. authorization
        ↓
7. callback router
        ↓
8. menu controller
        ↓
9. renderer
        ↓
10. commands
        ↓
11. inline
        ↓
12. lifecycle hardening
        ↓
13. tests
        ↓
14. remove legacy
```

Alasannya sederhana:

**Menu adalah layer paling atas.** Kalau kita memperbaiki menu sekarang sementara `peer/message identity` masih salah, kita hanya akan mengulang bug `MESSAGE_ID_INVALID` dalam bentuk lain.

## 44. Target arsitektur akhir

```text
                    ┌───────────────────┐
                    │   Telegram/gotd   │
                    └─────────┬─────────┘
                              │
                              ▼
                    ┌───────────────────┐
                    │ Assistant Client  │
                    └─────────┬─────────┘
                              │
                 ┌────────────┼────────────┐
                 ▼            ▼            ▼
            Commands       Callback      Inline
                 │            │            │
                 │            ▼            │
                 │      Target Resolver    │
                 │            │            │
                 │            ▼            │
                 │      Peer Resolver      │
                 │            │            │
                 │            ▼            │
                 │       Interaction      │
                 │            │            │
                 └────────────┼────────────┘
                              ▼
                     Menu / Controller
                              │
                              ▼
                         Presentation
                              │
                              ▼
                       Telegram RPC
```

**Inilah baseline yang menurut saya layak dijadikan Assistant v2 production architecture.**

Dan yang paling penting: **jangan langsung melakukan big-bang rewrite.** Implementasikan v2 berdampingan, migrasikan satu boundary pada satu waktu, lalu hapus legacy setelah behavior dan test parity terbukti. Ini akan jauh lebih aman daripada mengubah `client.go`, `handler.go`, `callback`, dan `service_adapter` sekaligus.
