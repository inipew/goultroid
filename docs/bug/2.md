## Gambaran arsitektur sebenarnya

Hal terpenting: **Worker, Task, Job, dan Scheduler sekarang bukan empat executor berbeda**. Mereka sudah jauh lebih dekat ke layering yang benar.

| Layer                    | Tanggung jawab aktual                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------ |
| **Scheduler**            | Memutuskan **kapan** logical occurrence harus dibuat                                                   |
| **JobManager**           | Mengelola **logical/durable work**: definition, occurrence, attempt, retry, recovery                   |
| **Task / WorkSpec**      | Representasi immutable dari **satu physical execution attempt**                                        |
| **TaskEngine**           | Satu-satunya **execution authority**: admission, queue, fairness, resources, dispatch, cancel, timeout |
| **Worker**               | Physical execution slot yang hanya menjalankan assignment dari TaskEngine                              |
| **Admission Controller** | Queueing, DRR fairness, quota, ordering-key serialization                                              |
| **PersistencePump**      | Jalur bounded khusus untuk durable acknowledgement                                                     |
| **SQLite Job Store**     | Source of truth durable untuk Job/Occurrence/Attempt/Schedule                                          |

Ini sesuai ADR: Scheduler tidak boleh menjalankan feature handler, Job menghasilkan Task, dan Worker hanyalah physical executor.

Secara konseptual:

# 1. Task: kontrak physical execution

`tasks.WorkSpec` adalah fondasi execution baru. Ia bukan mutable Task object yang sekaligus menjadi queue item, worker state, dan job state. Ia adalah **execution specification**.

WorkSpec membawa `ID`, `Scope`, `QuotaOwner`, `Pool`, `PriorityClass`, `OrderingKey`, queue deadline, execution timeout, `HandlerRef`, immutable input, resource requirement, optional Job occurrence reference, handler, durable `Commit`, dan completion callback. Input divalidasi dan dibekukan sebelum admission dipublikasikan.

State machine physical-nya:

```text
Created
  │
  ▼
Admitted
  │
  ▼
Queued
  │
  ▼
Dispatching
  │
  ▼
Running
  │
  ├──────────── ephemeral ────────────► Terminal
  │
  └──────────── durable ──────────────► CommitPending
                                          │
                           ┌───────────────┴──────────────┐
                           ▼                              ▼
                       Terminal                  RecoveryRequired
```

Terminal normal meliputi `Completed`, `Failed`, `Cancelled`, `TimedOut`; `RecoveryRequired` berarti physical execution sudah selesai tetapi durable acknowledgement tidak bisa dipastikan.

Ini desain yang bagus karena **physical completion tidak disamakan dengan durable completion**.

Ticket juga cukup bersih: `TaskID`, `State`, `Done`, `Result`, dan `Wait`. Producer tidak mendapat Worker atau Queue handle.

# 2. TaskEngine: pusat execution sebenarnya

TaskEngine sekarang menggunakan model **single-writer coordinator**.

Hampir seluruh mutable execution state dimiliki oleh satu `runLoop`. Submit, cancel, worker-started, worker-completed, commit ack, resource configuration, worker retirement, snapshot, dan stats semuanya masuk sebagai message ke bounded engine inbox.

Ini menghilangkan banyak class race yang biasanya muncul jika:

```text
submit goroutine
worker goroutine
cancel goroutine
scheduler goroutine
cleanup goroutine
```

semuanya mengubah Task object secara langsung.

Sekarang bentuknya:

```text
many producers
      │
      ▼
 bounded inbox
      │
      ▼
┌─────────────┐
│  runLoop    │  <── sole execution-state writer
└──────┬──────┘
       │ assignment
       ▼
 physical worker
       │ started/completed
       └──────────────► inbox
```

Submit juga punya **linearization protocol** yang cukup sophisticated. Setelah request masuk inbox, producer cancellation tidak boleh menyebabkan kasus ambigu:

```text
Submit() returns error
BUT task actually got accepted
```

`submitCell` menggunakan atomic decision state untuk menentukan siapa yang menang: coordinator acceptance/rejection atau caller cancellation.

Ini salah satu bagian implementasi yang menurut saya paling matang.

# 3. Admission, queue, fairness

TaskEngine tidak sekadar punya `chan Task`.

Ada Admission Controller tersendiri dengan **hierarchical Deficit Round Robin**.

Fairness berlangsung dua level:

```text
Priority Class
    │
    ├── Interactive  quantum 8
    ├── Normal       quantum 4
    ├── Background   quantum 2
    └── Maintenance  quantum 1
          │
          ▼
       Owner DRR
          │
          ▼
       ReadyQueue
```

Owner juga punya default quota:

```text
MaxWaiting       50
MaxActive        10
Weight            1
MaxPayload       50 MiB
```

Pool mempunyai backlog dan payload budget tersendiri. Ordering key menjadi serialization lock sehingga dua task dengan ordering key yang sama tidak berjalan bersama.

Resource requirement juga diperiksa **sebelum dispatch**, bukan di dalam handler.

Production defaults:

```text
process  = 2
media    = 2
download = 3
```

dan JobManager otomatis memberikan requirement tertentu berdasarkan pool.

Dengan demikian:

```text
worker concurrency != resource concurrency
```

Contohnya pool mungkin mempunyai banyak worker, tetapi cuma dua task yang memakai resource `process` yang dapat aktif.

Ini jauh lebih fleksibel daripada menaruh semaphore di masing-masing feature.

# 4. Worker bukan lagi subsystem orchestration

Worker sekarang sangat tipis.

Setiap physical slot mempunyai mailbox bounded `capacity=1`. Coordinator hanya mengirim assignment ke **idle slot yang sudah dimiliki coordinator**.

Worker melakukan kira-kira:

```text
wait assignment
      │
      ▼
validate/use permit
      │
      ▼
Started event
      │
      ▼
handler(ctx)
      │
      ├── panic recovery
      ├── execution timeout
      ├── cancellation
      └── normal/error result
      │
      ▼
Completed event
      │
      ▼
Idle event
```

Executor sendiri tidak membuat retry, tidak memilih task berikutnya, tidak menyimpan Job state, dan tidak melakukan schedule.

Itu boundary yang tepat.

### Physical permit

Dispatch bukan hanya “kirim TaskID”.

Coordinator membuat private permit berisi:

```text
pool
worker slot
pool generation
task ID
dispatch epoch
```

Permit hanya boleh dipakai sekali.

Saat `Started` maupun `Completed`, coordinator memastikan permit pointer, generation, dan dispatch epoch masih cocok.

Jadi late completion seperti:

```text
old worker
   │
   └── finishes very late

meanwhile TaskID has been evicted/reused
```

tidak bisa mengubah record baru.

Ini merupakan fencing mechanism yang bagus.

# 5. Adaptive worker pool

Worker adalah physical slots dengan:

```text
MinConcurrency <= current workers <= MaxConcurrency
```

Saat queue mempunyai work tetapi tidak ada idle worker, TaskEngine dapat spawn sampai hard maximum. Setelah idle timeout, worker boleh retire tetapi tidak boleh turun di bawah minimum.

Default-nya roughly:

```text
general        max 8   min 1
interactive    max 32  min 2
download       max 3   min 1
media-process  max 2   min 1
scheduler      max 4   min 1
```

Jadi idle goroutine footprint jauh lebih kecil daripada selalu mempertahankan seluruh maximum pool.

Dan `runLoop` sendiri tidak polling queue terus menerus. Deadline timer hanya di-arm pada deadline terdekat; jika tidak ada queue deadline maka channel timer dinonaktifkan.

Secara architecture, idle TaskEngine sudah cukup event-driven.

# 6. Backpressure sekarang berlapis

Ini bukan sekadar `queue length`.

Ada beberapa pressure boundary berbeda:

```text
Producer
  │
  ├─ bounded engine inbox
  │
  ├─ pool backlog limit
  │
  ├─ pool payload byte budget
  │
  ├─ owner waiting limit
  │
  ├─ owner payload budget
  │
  ├─ result credit capacity
  │
  ├─ global retained memory
  │
  ├─ callback delivery reservation
  │
  ├─ resource capacities
  │
  └─ persistence queue / durability lane
```

Memory accounting juga lumayan disiplin.

Default global retained cap adalah 256 MiB, result output per task 1 MiB, failure field 4 KiB. Mutable/opaque input object graphs tidak diterima; `[]byte` dicopy setelah budget check berhasil.

Ini penting: queue bounded berdasarkan count saja masih bisa OOM jika satu task membawa 100 MB payload. Goultroid sekarang meng-account byte ownership juga.

# 7. Durable Task: physical execution dan persistence dipisahkan

Untuk normal interactive task:

```text
Running
   │
handler finished
   │
   ▼
Terminal
   │
Ticket.Done
```

Untuk Job durable:

```text
Running
   │
handler finished
   │
   ├── physical worker immediately free
   │
   ▼
CommitPending
   │
PersistencePump
   │
SQLite transaction
   │
   ├── acknowledged ──────► physical result becomes terminal
   │
   └── uncertain/failure ─► RecoveryRequired
```

Ini desain yang sangat penting.

Physical slot **tidak ditahan sambil menunggu SQLite**. Tetapi result credit tetap dipegang sampai durable resolution. Jadi persistence yang macet tidak menghentikan physical workers secara langsung, tetapi lama-lama menekan admission melalui result capacity.

PersistencePump sendiri mempunyai concurrency dan queue bounded; production menggunakan concurrency `2`, queue `256`. Operation diberi hard timeout dan tidak meminjam TaskEngine execution slot.

Artinya dependency cycle ini dihindari:

```text
Task worker waits DB
DB worker waits Task worker
```

Jika pump penuh, terdapat bounded durability fallback; jika bahkan itu penuh, result menjadi `RecoveryRequired`, bukan membuat goroutine rescue tanpa batas.

# 8. Completion callback juga tidak bisa meledakkan goroutine

`OnComplete` dahulu merupakan tempat yang mudah menyebabkan:

```go
go callback(...)
go callback(...)
go callback(...)
...
```

tanpa bound.

Sekarang completion callback mempunyai worker pool dan queue bounded sendiri, dan credit-nya bahkan **di-reserve saat task admission**.

Jika downstream callback macet, akhirnya producer akan mendapat admission backpressure. Tidak ada unbounded detached callback goroutine.

Ini desain pressure propagation yang benar.

# 9. Job: logical durable state machine

Job bukan Task.

JobDefinition menyatakan **WHAT**:

```text
handler type
version
payload
pool
class
timeout
retry policy
scope owner
quota owner
```

Schedule menyatakan **WHEN**.

Occurrence adalah **satu logical invocation**.

Attempt adalah **satu physical execution attempt**.

Hubungannya:

```text
JobDefinition
      │
      ├──────── JobSchedule
      │              │
      │              ▼
      └────────► JobOccurrence
                       │
                       ├── Attempt #1 ──► Task #1
                       │
                       ├── Attempt #2 ──► Task #2
                       │
                       └── Attempt #N ──► Task #N
```

Ini berarti retry **tidak menjalankan ulang Task yang sama**. Retry menghasilkan Attempt/Task baru.

Itu semantic yang tepat.

# 10. Job submission flow

`SubmitOccurrence()` melakukan:

```text
resolve JobDefinition
      │
      ▼
MaterializeOccurrence
      │
      ├─ occurrence_key makes logical run idempotent
      ▼
PrepareAttemptLease
      │
      ├─ attempt ID
      └─ lease epoch
      │
      ▼
construct durable WorkSpec
      │
      ▼
TaskEngine.Submit()
      │
      ▼
physical execution
      │
      ▼
CommitAttemptResult()
```

`occurrence_key` mempunyai uniqueness sehingga duplicate logical trigger mendapat canonical occurrence yang sama. Attempt juga diberi lease epoch untuk fencing stale commit.

Commit callback yang masuk ke WorkSpec bukan arbitrary completion side effect; ia adalah persistent state transition untuk attempt tersebut.

Dengan real TaskEngine + PersistencePump + SQLite, test bahkan memastikan Ticket durable baru resolve sesudah commit durable tersedia.

# 11. Retry dan recovery

Retry policy punya:

```text
MaxAttempts
InitialDelay
MaxDelay
BackoffMultiplier
```

Setelah attempt terminal, JobManager monitor melihat Ticket result.

Jika berhasil:

```text
Occurrence -> completed
```

Jika physical attempt gagal:

```text
failed/timedout/panic/aborted
       │
       ▼
attempt count < max ?
       │
   yes │             no
       ▼              ▼
   backoff       finalize failed
       │
       ▼
new attempt lease
       │
       ▼
new Task
```

Ada juga recovery scan startup + periodic setiap 30 detik untuk unresolved durable occurrences.

Jadi recovery authority pada dasarnya store, bukan memory TaskEngine.

# 12. Scheduler sekarang lebih tepat posisinya

Scheduler tidak lagi menjadi executor.

Untuk redesigned schedule:

```text
EarliestScheduleDue()
        │
        ▼
sleep until due / wake event
        │
        ▼
ProcessDueSchedules()
        │
        ▼
materialize JobOccurrence
        │
        ▼
JobManager.driveAttempt()
        │
        ▼

```

Physical concurrency bukan lagi milik Scheduler. Bahkan `SetMaxConcurrency()` sekarang deprecated dan praktis hanya mengatur ukuran claim batch.

Persistent Scheduler masih mempertahankan legacy/cutover path untuk migration compatibility, tetapi bahkan jalur legacy yang sudah claim row tetap akhirnya menyerahkan execution ke JobManager/TaskEngine.

Jadi tidak ada lagi dua physical executor untuk scheduled task pada jalur normal.

# 13. Periodic runtime scheduler

Periodic task yang in-memory menggunakan indexed min-heap.

Heap sendiri sudah benar:

```text
Push       O(log N)
Remove     O(log N)
Fix        O(log N)
Peek       O(1)
PopDue     O(K log N)
```

dan entry hanya membawa timing reference/generation, bukan execution closure sebagai executor.

Periodic coordinator lalu mengubah tick menjadi durable Job occurrence dan execution tetap melalui JobManager → TaskEngine.

Idempotency tick juga bagus. Key dibentuk dari:

```text
definition + registration generation + scheduled slot
```

bukan wall-clock waktu saat admission akhirnya berhasil.

Artinya kalau TaskEngine sedang penuh:

```text
tick 12:00
  admission reject
  retry 200ms
  admission reject
  retry
```

semuanya tetap logical tick **12:00 yang sama**, bukan menciptakan tick baru setiap retry.

# 14. Scheduler policy belum seluruhnya benar-benar implemented

Di domain terdapat:

```text
OverlapForbid
OverlapReplace
OverlapAllowBounded

MisfireSkip
MisfireRunOnce
MisfireCatchUpBounded
```

Tetapi implementation redesigned belum setara dengan model tersebut.

SQLite `MaterializeDueSchedule()` benar-benar mengimplementasikan `OverlapForbid`: ia mengecek occurrence `ready/dispatched`, lalu hanya mengadvance schedule tanpa menciptakan occurrence baru.

Namun:

```text
OverlapReplace       -> belum ada replace semantics
OverlapAllowBounded  -> belum ada "bounded" enforcement
```

Selain itu `MisfirePolicy` memang disimpan di tabel, tetapi `ProcessDueSchedules()` tidak melakukan branching berdasarkan `MisfireSkip/RunOnce/CatchUpBounded`.

Jalur redesigned saat ini secara efektif lebih dekat ke:

```text
missed interval(s)
       │
       ▼
materialize at most current due occurrence
       │
       ▼
advance next_due until > now
```

alias **run-once style convergence**.

Jadi type system Scheduler lebih maju daripada policy implementation aktual.

Ini functional gap yang perlu diperbaiki sebelum policy tersebut dianggap benar-benar supported.

# 16. Shutdown/lifecycle

Startup topological.

Shutdown reverse dependency:

```text
Scheduler
    ↓
Jobs
    ↓
TaskEngine
    ↓
PersistencePump
    ↓
Database
```

dan Runtime mempunyai:

```text
Quiesce
   ↓
Drain
   ↓
Stop
   ↓
ForceStop if graceful budget exhausted
```

TaskEngine graceful drain menunggu admitted work selesai dan menunggu completion callbacks. Forced shutdown mem-fence execution dan untuk durable physical task yang status external effect-nya tidak pasti, state dipindah ke `RecoveryRequired`, bukan secara salah diklaim `Cancelled`.

Ini semantic shutdown yang benar.

Satu nuance: `JobManager.Drain()` saat ini no-op. Artinya runtime menjamin durable state tetap recoverable, tetapi tidak menjamin seluruh retry decision selesai sebelum JobManager dihentikan. Retry yang belum diproses dapat dikonvergensikan pada startup recovery berikutnya.

# 17. Plugin isolation

Plugin tidak menerima global TaskEngine client secara mentah.

`TaskClient()` membuat wrapper yang selalu menimpa:

```text
Scope.Owner      = plugin:<name>
Scope.Generation = current plugin generation
QuotaOwner       = plugin:<name>
```

dan plugin hanya boleh cancel/snapshot task dalam scope miliknya sendiri.

Scope plugin sendiri punya cancellation tree, monotonic generation, bounded unmanaged goroutine count, cleanup dan resource tracking.

Ini integrasi lifecycle yang cukup baik.

Tetapi ada satu policy hole: scoped wrapper **tidak menimpa atau membatasi `Pool` dan `PriorityClass`**.

Plugin dengan `CapTasks` masih bisa meminta misalnya:

```go
Pool:  "interactive"
Class: PriorityInteractive
```

walaupun logically work-nya maintenance/background.

Owner quota masih melindungi sistem sebagian, tetapi priority domain belum authoritative.

Idealnya producer hanya mengirim semantic workload class, lalu policy layer menentukan physical pool/class, atau scoped client memiliki allowed pool/class policy.

# 19. Performa saat benar-benar idle

TaskEngine sendiri bagus.

Saat tidak ada work:

```text
runLoop      blocked on inbox
workers      blocked on mailbox
deadline     disabled unless needed
extra worker retire after idle timeout
```

Sehingga CPU scheduler activity TaskEngine semestinya sangat rendah.

Persistence workers blocked pada queue.

JobManager sedikit berbeda. Ia memiliki:

```text
4 retry workers        blocked
1 recovery goroutine   wakes every 30s
1 outbox goroutine     wakes every 1s
```

Outbox goroutine tetap mempunyai ticker `1s` walaupun tidak ada pending event.

Scheduler persistent memakai heartbeat maksimum 60s ketika tidak ada due schedule dan tidak ada tracked claims.

Periodic coordinator yang benar-benar kosong bisa tidur tanpa periodic heartbeat sampai wake signal.

Jadi secara rough:

```text
TaskEngine idle        excellent / event-driven
Periodic scheduler     excellent when truly empty
Main scheduler idle    low overhead, 60s heartbeat
Job recovery           30s wake
Job outbox              1s wake
```

Kalau target Anda adalah **mendekati zero wakeup saat seluruh system idle**, Job outbox 1-second ticker adalah kandidat pertama untuk dibuat event/deadline-driven.

---

# 20. Performa saat ada inflight work

Ada perbedaan penting antara idle kosong dan “sedang menunggu task panjang”.

Persistent Scheduler memiliki tracked claims dan membatasi delay menjadi paling lama **1 detik** supaya bisa query occurrence state.

Periodic coordinator juga melakukan reconciliation paling lambat setiap satu detik selama ada occurrence inflight.

Jadi long-running task 30 menit akan menghasilkan periodic store reads selama 30 menit.

Lebih ideal kalau TaskEngine/JobManager mempunyai **completion notification stream** ke Scheduler sehingga:

```text
poll every second
```

bisa menjadi:

```text
sleep indefinitely
    │
job terminal event
    ▼
wake exactly once
```

Durable outbox yang sudah ada bahkan menyediakan fondasi ke arah ini.

---

# 21. Bottleneck CPU/control plane

TaskEngine memakai single-writer runLoop.

Ini memberi correctness yang sangat bagus tetapi berarti semua:

```text
submit decision
cancel
worker started
worker completed
commit ack
stats
worker idle
resource mutation
```

melewati satu coordinator.

Untuk workload bot normal, ini masuk akal dan kemungkinan jauh dari bottleneck.

Tetapi pada throughput sangat tinggi, **control loop adalah serial portion Amdahl**.

Untungnya handler tidak berjalan di loop dan persistence juga tidak berjalan di loop. Jadi critical section coordinator relatif kecil.

Desainnya lebih tepat dipertahankan sampai benchmark menunjukkan saturation daripada premature sharding.

# 22. Periodic scheduler masih mempunyai O(N) scan yang seharusnya tidak perlu

Ini salah satu performance gap paling jelas.

Walaupun memakai indexed heap O(log N), setiap loop masih memanggil:

```go
syncHeapLocked()
```

yang mengiterasi **seluruh registration**.

Padahal register/unregister/update sudah mengetahui entry yang berubah.

Jadi saat ada `N` periodic registrations:

```text
current:
every scheduler iteration ≈ O(N)
```

sementara idealnya:

```text
mutation         O(log N)
next deadline    O(1)
due              O(K log N)
idle             O(1)
```

Lebih buruk lagi, kalau ada inflight occurrence, loop bisa bangun 1 Hz.

Dengan `N=10,000` timer, scan 10,000 registrations setiap detik tanpa ada schedule mutation sama sekali itu unnecessary work.

Ini cocok untuk redesign menjadi **strict mutation-driven indexed heap**.

# 23. P1 yang saya temukan di Job retry monitor

Ini temuan correctness/liveness yang menurut saya paling penting dari pembacaan aktual HEAD.

JobManager memakai:

```text
retryQueueCap = 256
retryWorkers  = 4
```

Setelah Task berhasil disubmit:

```go
m.track(occurrenceID, ...)
m.enqueueRetry(...)
```

`enqueueRetry()` non-blocking.

Kalau queue penuh:

```go
default:
    m.signalRecovery()
```

dan occurrence **tetap berada dalam `tracked`**.

Masalahnya recovery kemudian melakukan:

```go
if activelyTracked {
    report.Stale++
    continue
}
```

karena asumsi bahwa setiap `tracked` occurrence sudah mempunyai retry worker yang bertanggung jawab.

Tetapi pada saturation tadi asumsi tersebut salah:

```text
tracked == true
watcher == none
```

Flow bermasalah:

```text
Submit attempt
   │
   ▼
tracked[occ] = true
   │
   ▼
retry queue FULL
   │
   ├── no retry watcher assigned
   └── signalRecovery()
             │
             ▼
       Recover()
             │
             ▼
      sees tracked=true
             │
             ▼
           SKIP
```

SQLite hanya otomatis membuat occurrence terminal untuk attempt `completed` atau `cancelled`. Failed/timed-out/aborted attempt memang ditinggalkan non-terminal supaya JobManager dapat membuat retry.

Jadi khusus failure pada occurrence yang kehilangan retry watcher:

```text
attempt = failed
occurrence = dispatched
tracked = true
retry watcher = none
recovery = always skip
```

Occurrence bisa stranded.

Lebih buruk lagi, empat retry worker menjalankan:

```go
ticket.Wait()
```

secara blocking dan bahkan tidur selama retry backoff di worker tersebut.

Jadi hanya empat concurrent occurrence dapat mempunyai active retry decision driver; sisanya memenuhi queue 256.

### Redesign yang lebih tepat

Saya tidak akan mengatasi ini hanya dengan memperbesar `256`.

Ownership state perlu eksplisit:

```text
tracked occurrence
   !=
retry driver owned
```

Misalnya:

```text
tracked {
    taskID
    monitorState:
        unowned
        watching
        backoff
}
```

Jika enqueue monitor gagal:

```text
monitorState = unowned
```

dan Recovery **harus boleh mengambil ownership**.

Lebih jauh lagi, backoff sebaiknya masuk indexed deadline heap daripada menahan salah satu dari empat retry workers.

Dengan model itu jumlah occurrence bisa ribuan tanpa membutuhkan satu goroutine/waiter per occurrence.

Saya belum menemukan regression test yang mensimulasikan retry-monitor queue saturation; test Job saat ini kuat pada durable commit/recovery dasar, tetapi bukan case ini.

# 24. Scope tombstone punya edge case lifecycle

TaskEngine menyimpan cancelled scope tombstone agar:

```text
plugin unloaded
       │
late submit from stale client
       │
       ▼
rejected
```

Bagus.

Tetapi tombstone dibatasi default `4096` dan yang tertua akhirnya dihapus.

Sementara stale scoped TaskClient tidak memeriksa sendiri apakah plugin Scope context-nya sudah ditutup sebelum Submit; ia hanya mengirim owner+generation ke TaskEngine.

Setelah tombstone lama ter-evict akibat banyak lifecycle generations, client stale secara teori bisa submit lagi.

Lebih kuat kalau state-nya berbentuk:

```text
owner -> minimum_valid_generation
```

atau:

```text
owner -> last_closed_generation
```

sehingga memory O(number of owners), bukan O(number of cancelled generations), dan seluruh generation lama tetap permanently fenced.

Alternatif tambahan: scoped TaskClient menolak Submit jika Scope context sudah cancelled.

# 25. Dynamic worker config punya caveat

`ConfigurePool()` bisa mengubah `IdleTimeout`, tetapi worker membaca timeout satu kali ketika `physicalWorker()` mulai.

Akibatnya live config:

```text
IdleTimeout 60s -> 5s
```

tidak langsung berlaku ke worker yang sudah hidup.

Ada juga kemungkinan read/write map overlap antara worker baru yang membaca `poolIdleTimeouts` dan coordinator yang melakukan live config. Jalur ini layak mendapat race test khusus.

Lebih bersih jika `spawnWorker()` memberikan immutable worker runtime config sebagai parameter, atau retirement deadline dikelola oleh coordinator sendiri.

# Kesimpulan arsitektur saya

Mental model yang saya pakai untuk kode ini sekarang adalah:

```text
Scheduler = TIME AUTHORITY
JobManager = DURABLE LOGICAL WORK AUTHORITY
TaskEngine = EXECUTION AUTHORITY
Admission = FAIRNESS + PRESSURE AUTHORITY
Worker = PHYSICAL EXECUTION MECHANISM
PersistencePump/Store = DURABILITY AUTHORITY
Runtime = LIFECYCLE AUTHORITY
```

Boundary tersebut sudah cukup jelas di HEAD.

Bagian terkuat sekarang adalah TaskEngine: single-writer coordination, physical permit fencing, bounded admission, byte accounting, adaptive workers, resource reservation, distinct durability phase, bounded callback delivery, dan shutdown fencing semuanya saling konsisten.

Bagian yang menurut saya paling membutuhkan pekerjaan berikutnya adalah **Job occurrence driver/retry ownership**, kemudian **Scheduler policy completion + removal polling/O(N) scans**. Setelah itu baru hardening producer authority seperti Pool/Class dan scope-generation fencing.

Prioritas teknis yang saya pegang setelah studi ini adalah: **P1** perbaiki retryQueue/tracked ownership hole; **P1/P2** implement penuh Misfire/Overlap semantics; **P2** ubah retry/backoff menjadi event/deadline-driven daripada empat blocking watchers; **P2** hilangkan `syncHeapLocked()` O(N) dan reconciliation polling 1 Hz lewat terminal notification; **P2** enforce Pool/Class policy di producer boundary; **P2** ganti bounded scope tombstones dengan generation watermark; lalu **P3** benahi benchmark suite agar mengukur actual idle CPU/wakeups, end-to-end latency dan p50/p95/p99 secara benar.

Saya sekarang sudah punya model yang cukup lengkap untuk melanjutkan audit atau refactor Worker–Task–Job–Scheduler di branch ini tanpa perlu mengulang pemetaan arsitektur dari awal.
