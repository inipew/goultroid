# Callback & Inline Implementation Audit and Completion Plan

Date: 2026-09-06

Repositories audited:
- GoUltroid: https://github.com/inipew/goultroid
- Reference behavior: https://github.com/TeamUltroid/Ultroid
- Telegram MTProto / gotd references

## 1. Executive summary

The current GoUltroid tree already contains a real Callback and Inline foundation. This is no longer a placeholder:

- `internal/services/callback` has a namespace router, versioned payloads, temporary state, authorization checks and automatic callback acknowledgement.
- `internal/services/inline` has handler registration, keyword resolution, result caching, pagination and MTProto serialization.
- `internal/telegram/dispatcher.go` is wired to `OnBotCallbackQuery`, `OnInlineBotCallbackQuery` and `OnBotInlineQuery`.
- `internal/telegram/service.go` exposes callback acknowledgement and inline-result answering.
- `internal/ui/button.go` can emit callback, URL and switch-inline buttons.
- `internal/app/app.go` currently constructs both callback and inline subsystems and installs three default inline handlers.

However, the implementation is not yet complete or production-grade. The main problem is not missing event hooks; it is that the abstraction does not yet model the complete Telegram interaction lifecycle. The current callback context assumes a normal chat message and therefore cannot correctly edit inline-origin messages. Inline results are currently serialized as `InputBotInlineResult` of type `article` only, which makes the feature much narrower than Telegram/Ultroid capabilities. Callback payloads also lack strong validation, expiry semantics at the protocol layer, replay protection, and explicit ownership/scope metadata.

The recommended direction is to keep the existing Go-native architecture and upgrade it into a first-class interaction subsystem rather than copying Telethon/Ultroid APIs.

## 2. Current implementation inventory

### 2.1 Dispatcher

`internal/telegram/dispatcher.go` now registers:

- normal message updates;
- edit/delete updates;
- `OnBotCallbackQuery`;
- `OnInlineBotCallbackQuery`;
- `OnBotInlineQuery`;
- reactions.

The dispatcher creates a `core.CallbackQueryEvent` for both normal and inline callback queries. The inline callback path currently does not preserve an inline message identifier in the domain event.

### 2.2 Callback router

`internal/services/callback/router.go` currently provides:

- namespace registration;
- `v1:<namespace>:<action>:<opaque-id>` parsing;
- state lookup;
- allowed-user validation;
- handler dispatch;
- automatic `AnswerCallbackQuery` fallback.

This is a good base and should be retained.

### 2.3 Callback state

`StateStore` is an in-memory TTL map with cryptographically random 64-bit opaque identifiers. It supports user restriction and pruning.

This is appropriate for ephemeral UI state but must not become the source of truth for durable workflows.

### 2.4 Inline engine

`internal/services/inline/engine.go` currently provides:

- exact first-token handler selection;
- catch-all handler;
- cache;
- pagination;
- correlation IDs;
- `tg.InputBotInlineResult` article serialization;
- callback/URL/switch-inline markup inside inline result messages;
- `messages.setInlineBotResults` through `TelegramServicer`.

### 2.5 UI button layer

`internal/ui/button.go` supports:

- callback buttons;
- URL buttons;
- switch-inline buttons;
- pagination rows;
- confirm/cancel rows.

This is useful, but the button abstraction needs to grow into a complete Telegram interaction model.

## 3. Important correctness bugs / design gaps

### P0 — Inline callback cannot be edited correctly

`CallbackContext` only contains `ChatID` and `MsgID`, and `Edit()` constructs an `InputPeerChat`. This is fundamentally wrong for `UpdateInlineBotCallbackQuery`.

Telegram distinguishes callbacks originating from ordinary bot messages and callbacks originating from messages sent through inline mode. Inline callbacks carry an `InputBotInlineMessageID` rather than an ordinary peer + message ID. MTProto exposes `messages.editInlineBotMessage` specifically for this case.

Current result:

- normal callback: potentially editable;
- inline callback: `MsgID` is absent/zero and no inline message ID is retained;
- `CallbackContext.Edit()` cannot target an inline message.

Required fix:

Introduce an explicit callback origin:

```go
type CallbackOrigin int

const (
    CallbackOriginMessage CallbackOrigin = iota
    CallbackOriginInline
)
```

and model the target separately:

```go
type CallbackTarget struct {
    Origin          CallbackOrigin
    Peer            tg.InputPeerClass
    MessageID       int
    InlineMessageID *tg.InputBotInlineMessageID
}
```

`CallbackQueryEvent` must preserve the complete target. `OnBotCallbackQuery` populates `Peer` + `MessageID`; `OnInlineBotCallbackQuery` populates `InlineMessageID`.

`CallbackContext.Edit()` must dispatch to:

- `messages.editMessage`/existing message edit service for normal messages;
- `messages.editInlineBotMessage` for inline messages.

This is mandatory for production correctness.

### P0 — `CallbackQueryEvent` loses inline message identity

The inline callback handler currently creates the same generic event but only copies query ID, user ID and data. It drops the MTProto inline message target.

Do not reconstruct it later. Preserve the exact `tg.InputBotInlineMessageID` at the update boundary.

### P0 — `CallbackContext.Edit()` uses an incorrect peer model

The current implementation constructs `InputPeerChat` from `ChatID`. This does not correctly represent:

- users;
- channels/supergroups;
- inline messages;
- peers requiring access hashes.

The callback layer should never manually infer Telegram peer type from a numeric ID. It should consume the resolved peer/target supplied by the dispatcher.

### P1 — Callback acknowledgement is coupled to handler completion

Telegram expects the callback query to be answered promptly so the client loading state disappears. The current router waits for `handler.HandleCallback()` and only then automatically answers if the handler did not answer itself.

For slow handlers this creates unnecessary UI latency.

Recommended behavior:

1. Validate and authorize callback.
2. Immediately acknowledge with an empty toast, unless the handler explicitly needs to own the acknowledgement.
3. Execute the action.
4. If the action fails, optionally send a second user-visible message/edit; do not depend on the callback spinner as the error channel.

Alternative API:

```go
type CallbackHandlerOptions struct {
    AutoAnswer bool
    DefaultText string
    DefaultAlert bool
}
```

Default should be `AutoAnswer=true`.

### P1 — Callback payload format is too permissive

`ParseCallbackData()` accepts any four-part string beginning with `v1`, including empty namespace/action/opaque ID values. There is no maximum size, character validation or canonical encoding.

Implement:

- maximum callback data length;
- non-empty namespace/action;
- allowed character set for namespace/action;
- opaque ID validation;
- version dispatch instead of one hard-coded parser;
- explicit error for expired state;
- optional signed/stateless payload mode.

Telegram callback data is compact, so payload design should be intentionally bounded.

### P1 — Expired state is indistinguishable from unknown state

`StateStore.Get()` returns `(nil, 0, false)` for both unknown and expired IDs. The router declares `ErrStateExpired` but does not actually use it.

Required:

```go
Get(id string) (StateEntry, error)
```

with errors:

- `ErrStateNotFound`;
- `ErrStateExpired`;
- `ErrStateUnauthorized`.

This lets the UI tell the user whether a button is stale versus invalid.

### P1 — StateStore is not lifecycle-managed

The store has `Prune()` but no background pruning loop or explicit shutdown. Long-running processes can accumulate expired entries until another operation touches them.

Add:

```go
Start(ctx context.Context)
Stop()
```

with a bounded periodic cleanup interval.

### P1 — Callback state is not scoped to message/chat

`allowedUserID` is useful, but authorization should also be able to constrain:

- originating chat;
- originating message;
- command/session;
- plugin namespace;
- expiration;
- optional capability/role.

A callback generated in one chat should not accidentally become valid in another context simply because the same user clicked it.

Recommended state metadata:

```go
type StateScope struct {
    UserID        int64
    ChatID        int64
    MessageID     int
    Namespace     string
    ExpiresAt     time.Time
    SingleUse     bool
}
```

### P1 — Replay protection is missing

A callback button can be clicked multiple times. Some actions are harmless, but confirmation, deletion, mutation, pagination state changes and financial/admin operations may not be.

Add optional `SingleUse` state. The state must be atomically consumed before invoking a protected handler.

Do not implement `Get()` followed by `Delete()` as two independent operations for single-use state; that is race-prone. Implement `Consume()` atomically under the same lock.

### P1 — Inline cache key is incomplete

The cache key is currently effectively the trimmed query. This can leak results between users or chats when handlers produce user-specific or permission-specific data.

Cache policy must explicitly support:

- global cache;
- per-user cache;
- per-chat cache;
- no-cache.

Recommended key:

```text
handler/version + query + offset + user-scope + chat-scope + locale
```

Only include identity dimensions when the handler declares them relevant.

### P1 — Inline pagination is logically coupled to the cached full result set

The engine computes all results, caches all results, then paginates. This is acceptable for small local result sets but does not scale to expensive/network-backed search.

The handler API should support two modes:

1. materialized results for cheap local data;
2. native page fetching where `Offset` is passed to the handler.

Recommended interface:

```go
type InlineHandler interface {
    Pattern() string
    Execute(ctx *InlineContext) (*InlineResponse, error)
}

type InlineResponse struct {
    Results []InlineResult
    NextOffset string
    Cache CachePolicy
}
```

Do not force every provider to generate every page before Telegram sees the first page.

### P1 — Inline results are article-only

The current engine serializes every result as `tg.InputBotInlineResult{Type: "article"}`.

Telegram inline mode supports many result/content forms, including photos, videos, documents, GIFs, audio, locations, contacts, games and media-backed results. MTProto also exposes the corresponding `InputBotInlineResult*` constructors.

This is a major functional limitation compared with a mature userbot.

Introduce a result abstraction with explicit type:

```go
type InlineResultType string

const (
    ResultArticle  InlineResultType = "article"
    ResultPhoto    InlineResultType = "photo"
    ResultDocument InlineResultType = "document"
    ResultVideo    InlineResultType = "video"
    ResultGif      InlineResultType = "gif"
    ResultAudio    InlineResultType = "audio"
    ResultVenue    InlineResultType = "venue"
    ResultGeo      InlineResultType = "geo"
    ResultContact  InlineResultType = "contact"
    ResultGame     InlineResultType = "game"
)
```

Prefer typed result structs or a sealed interface rather than a large struct full of optional fields.

### P1 — Inline response lacks `switch_pm` / `switch_webview`

The MTProto API supports `switch_pm` and newer `switch_webview` response controls. They are useful for onboarding, settings, authorization and configuration flows.

Expose them in `InlineResponse`.

### P1 — Inline gallery/private semantics are missing

`messages.setInlineBotResults` supports `gallery` and `private` flags. Current `TelegramServicer.AnswerInlineQuery()` only receives results, next offset and cache time.

Extend the service API to carry response policy:

```go
type InlineAnswerOptions struct {
    Gallery bool
    Private bool
    CacheTime int
    NextOffset string
    SwitchPM *InlineSwitchPM
    SwitchWebView *InlineSwitchWebView
}
```

### P1 — Inline feedback is not modeled

MTProto can deliver `updateBotInlineSend` when an inline result is chosen/sent, when feedback collection is enabled. This is useful for analytics, debugging and adaptive caching.

Add an optional event:

```go
type InlineResultChosenEvent struct {
    At       time.Time
    UserID   int64
    Query    string
    ResultID string
    Message  *tg.InputBotInlineMessageID
}
```

This should be observational only; it must not be a hard dependency for functional correctness.

### P2 — Handler matching is keyword-only

Current inline resolution uses the first whitespace-separated token. Ultroid's `in_pattern` supports regex/event filtering. GoUltroid should not copy the Python decorator API, but it should support equivalent matching power.

Recommended matcher abstraction:

```go
type InlineMatcher interface {
    Match(query string) (args []string, ok bool)
}
```

Implement at least:

- exact keyword;
- prefix;
- regexp;
- catch-all.

Order handlers by explicit priority rather than relying on registration order.

### P2 — No inline authorization policy

Ultroid supports owner-restricted inline handlers. GoUltroid currently only has generic user ID in `InlineContext`.

Add declarative handler policy:

```go
type InlineAccessPolicy struct {
    OwnerOnly bool
    SudoOnly bool
    AllowedUsers []int64
    AllowedChats []int64
}
```

Authorization must happen before expensive handler execution and before cache lookup when the result is private.

### P2 — Error UX for inline is too weak

On handler errors the engine currently answers with empty results. That hides failures from the user and makes debugging difficult.

Provide a safe fallback article for development/debug modes and a generic “unable to load results” article for production. Never expose raw stack traces or secrets to Telegram.

### P2 — Callback errors are swallowed at dispatcher boundary

The dispatcher calls `cbRouter.Dispatch()` and discards its error. This is acceptable for Telegram update handlers only if the router logs the error with correlation metadata. Currently logging is not sufficiently structured around callback IDs/user/chat/action.

Add correlation fields:

- query ID;
- user ID;
- chat ID;
- namespace;
- action;
- opaque ID;
- inline/normal origin.

### P2 — No interaction metrics

Add counters/histograms for:

- callback received;
- callback invalid;
- callback unauthorized;
- callback expired;
- callback handler duration;
- callback handler error;
- inline query received;
- inline cache hit/miss;
- inline handler duration;
- inline answer error;
- result count;
- pagination depth.

## 4. Recommended architecture

Keep the following layers separate:

```text
Telegram Update
      |
      v
telegram.Dispatcher
      |
      +---- CallbackQueryEvent ----> callback.Router
      |                                  |
      |                                  +--> authorization
      |                                  +--> state/capability lookup
      |                                  +--> handler
      |                                  +--> interaction response
      |
      +---- InlineQueryEvent ------> inline.Engine
                                         |
                                         +--> matcher
                                         +--> authorization
                                         +--> cache policy
                                         +--> handler/provider
                                         +--> pagination
                                         +--> result serializer
                                         +--> Telegram answer
```

The dispatcher should only translate Telegram updates into domain events. It should not contain callback/inline business logic.

## 5. Callback implementation target

### 5.1 Domain event

Replace the current minimal event with a target-aware event:

```go
type CallbackQueryEvent struct {
    At        time.Time
    QueryID   int64
    UserID    int64
    ChatID    int64
    Data      []byte
    Origin    CallbackOrigin
    MessageID int
    Peer      tg.InputPeerClass
    InlineID  *tg.InputBotInlineMessageID
    ChatInstance int64
}
```

`Peer` should be the resolved target when available; otherwise keep the original Telegram peer information without guessing its type.

### 5.2 Callback context

Expose high-level methods:

```go
Answer(text string, alert bool) error
EditText(text string) error
EditMarkup(markup tg.ReplyMarkupClass) error
Edit(text string, markup tg.ReplyMarkupClass) error
Delete() error
GetMessage() (*tg.Message, error)
ConsumeState() error
```

`Edit`, `Delete` and `GetMessage` must choose normal-message or inline-message APIs based on `Origin`.

### 5.3 Payload codec

Use a codec interface:

```go
type Codec interface {
    Encode(CallbackPayload) ([]byte, error)
    Decode([]byte) (CallbackPayload, error)
}
```

Payload should contain only routing information. Do not serialize arbitrary state into Telegram callback data.

Recommended logical payload:

```text
v1:<namespace>:<action>:<opaque-id>
```

For security-sensitive stateless callbacks, add a signed variant later:

```text
v2:<namespace>:<action>:<claims>.<signature>
```

### 5.4 State lifecycle

```text
Create state
   -> bind user/chat/message/namespace
   -> generate opaque ID
   -> attach TTL
   -> emit button

Callback
   -> decode
   -> lookup
   -> validate TTL
   -> validate scope
   -> optionally atomically consume
   -> handler
   -> cleanup
```

## 6. Inline implementation target

### 6.1 Event

Introduce:

```go
type InlineQueryEvent struct {
    At       time.Time
    QueryID  int64
    UserID   int64
    Query    string
    Offset   string
    PeerType tg.InlineQueryPeerType
}
```

### 6.2 Context

Add:

```go
type InlineContext struct {
    Ctx context.Context
    QueryID int64
    UserID int64
    RawQuery string
    Pattern string
    Args []string
    Offset string
    CorrelationID string
    Locale string
    PeerType tg.InlineQueryPeerType
}
```

### 6.3 Response

Use:

```go
type InlineResponse struct {
    Results []InlineResult
    NextOffset string
    Cache CachePolicy
    Gallery bool
    Private bool
    SwitchPM *SwitchPM
    SwitchWebView *SwitchWebView
}
```

### 6.4 Result serialization

Use one serializer per result type:

```text
InlineResult
  -> ArticleSerializer
  -> PhotoSerializer
  -> DocumentSerializer
  -> VideoSerializer
  -> GifSerializer
  -> AudioSerializer
  -> GeoSerializer
  -> VenueSerializer
  -> ContactSerializer
  -> GameSerializer
```

This prevents `engine.go` from becoming a huge type switch.

## 7. Telegram/gotd facts that must drive the implementation

Telegram's official API defines callback queries as the interaction generated by callback buttons. The callback must be answered using `messages.setBotCallbackAnswer`; Telegram's bot documentation likewise requires `answerCallbackQuery`. citeturn0search0turn0search14

Inline mode is not simply “search text and return articles”. Telegram supports multiple inline result types and result-level keyboards. The MTProto flow uses `messages.setInlineBotResults`; `next_offset` controls pagination and `private`/`gallery` influence result presentation and caching. citeturn0search5turn0search13

Inline-origin callbacks are a separate protocol case. Telegram sends an `updateInlineBotCallbackQuery` containing an `InputBotInlineMessageID`, and the correct edit operation is `messages.editInlineBotMessage`. This is the core reason the current generic `ChatID + MsgID` callback context is insufficient. citeturn0search5

The gotd ecosystem already demonstrates the intended Go-native pattern: `UpdateDispatcher` exposes `OnBotInlineQuery`, and gotd has a dedicated inline example and inline-result helpers. citeturn0search6turn0search7

Ultroid's current architecture treats callback and inline as first-class assistant event types. Its callback decorator supports user/admin/owner restrictions, while its inline decorator supports pattern matching and owner-aware fallback behavior. fileciteturn91file0L2-L10

## 8. UX requirements

Callback UX should follow a consistent interaction contract:

1. Button press immediately clears Telegram loading state.
2. Long-running work edits the originating message to show progress.
3. Completion edits the same message whenever possible.
4. Errors are shown as concise toast/alert plus durable message state when appropriate.
5. Unauthorized users get a clear alert.
6. Expired buttons say they are stale rather than “invalid”.
7. Single-use destructive actions disable/remove their buttons after success.
8. Pagination updates the same message rather than sending a new message.
9. Inline-origin messages are edited through the inline-message API.

The current UI button abstraction is a good starting point: it already supports callback, URL and switch-inline buttons and has reusable pagination/confirm rows. fileciteturn77file0L2-L10

## 10. Implementation order

### Phase 1 — Correctness

1. Preserve inline message ID in `CallbackQueryEvent`.
2. Introduce callback origin/target model.
3. Implement `EditInlineBotMessage` service operation.
4. Rewrite `CallbackContext.Edit()` around target type.
5. Fix callback state expiry error semantics.
6. Add atomic `Consume()` for single-use state.
7. Add state scope validation.
8. Add callback/inline correlation logging.

### Phase 2 — Inline engine completeness

1. Introduce `InlineResponse`.
2. Separate pagination from result generation.
3. Add cache policy and scoped cache keys.
4. Add `gallery`/`private`/`switch_pm`/`switch_webview`.
5. Introduce matcher abstraction.
6. Add access policy.
7. Add typed result serializers.
8. Support the high-value result types first: article, photo, document, video, GIF, audio.

### Phase 3 — UX

1. Standard callback acknowledgement.
2. Standard progress/edit lifecycle.
3. Standard pagination.
4. Standard confirm/cancel.
5. Expired/unauthorized/error UX.
6. Inline fallback/help result.
7. Common result buttons.

### Phase 4 — Production hardening

1. Metrics.
2. Timeouts per handler class.
3. Rate limiting for callback/inline separately from command rate limiting.
4. Panic recovery around third-party/plugin handlers.
5. bounded result count and serialized payload sizes.
6. memory limits for inline cache/state.
7. shutdown-aware state cleanup.
8. integration tests against a real Telegram test account/bot where possible.

## 11. Definition of done

Callback is complete when:

- normal and inline-origin callbacks are distinct and correctly editable;
- authorization and state scope are enforced;
- stale/replayed callbacks are safe;
- callback acknowledgement is prompt;
- destructive actions can be single-use;
- all callback operations have deterministic error behavior;
- tests cover normal, channel and inline targets.

Inline is complete when:

- handlers support deterministic matching and authorization;
- pagination is native rather than forced through full-result caching;
- cache scope is explicit;
- response policy supports Telegram's important inline controls;
- multiple result types are supported through typed serializers;
- inline callbacks can edit their originating messages;
- errors are observable and user-safe;
- metrics and limits prevent an expensive inline query from becoming a resource-exhaustion vector.

## 12. Final assessment

Current GoUltroid Callback/Inline implementation is a **strong foundation but not complete**.

The most important correction is the callback target model. Do not attempt to fix inline callbacks by inventing a chat ID or message ID. Telegram's inline-message identity is a different target and must remain a first-class value from update ingestion through the service layer.

Likewise, do not expand `InlineResult` into an unbounded optional-field struct merely to match Telegram's many result types. Use typed result variants and serializers. This keeps the Go-native design clean and makes future plugins easy to implement.

The existing architecture should therefore be **extended, not replaced**.
