> **Audit date:** 2026-09-06  
> **Repository:** `inipew/goultroid`  
> **Branch:** `main`  
> **Audited HEAD:** `0703b5d3a6927d093c571b86123e8f93be35c4bb`

---

## 1. Executive verdict

**GoUltroid is not yet equivalent to Ultroid in functionality or user-facing coverage.**

The important architectural conclusion is different from a Python-to-Go port:

> GoUltroid should **not** reproduce Ultroid's Python implementation line-by-line. It should reproduce the important user-facing capabilities and behavioral contracts with a native Go architecture.

The current Go architecture is already substantially more structured than a simple port would need to be. It has a useful command router, explicit execution sources, permission middleware, SQLite persistence, durable scheduling, peer caching, bounded process execution, media resource guards, addon IPC/capability boundaries, callback/inline abstractions, and reusable UI builders.

The remaining problem is primarily **feature completeness and behavioral completeness**, not lack of architectural sophistication.

### Overall status

| Area | Status | Verdict |
|---|---|---|
| Go-native architecture | Strong | Keep and extend |
| Command routing | Good | Production foundation |
| Permission model | Good | Needs more capability/scope semantics |
| Telegram MTProto integration | Good foundation | Several peer and lifecycle edge cases |
| Scheduler | Strong foundation | Still has execution-context design debt |
| Database/durability | Good | Strong MVP foundation |
| Media pipeline | Real implementation | Narrow compared with Ultroid |
| Downloader | Real implementation | Provider coverage is narrow |
| Addon runtime | Real IPC foundation | UX/install lifecycle incomplete |
| Callback/inline | Framework exists | Feature ecosystem is tiny |
| Assistant | Minimal | Far behind Ultroid |
| Voice chat | Not wired | Missing |
| Admin/moderation | Partial | Far behind |
| User logs | Partial | Several event/peer gaps |
| Telegram UI/UX | Basic reusable system | Not yet feature-rich |
| Ultroid feature parity | Low | **Not equivalent** |

A realistic current classification is **“well-architected Go userbot framework + partial Ultroid-compatible feature set”**, not “Ultroid-equivalent userbot”.

# 3. Current architecture — strengths

## 3.1 Command router

`internal/core/router.go` provides normalized command names, aliases, duplicate detection, quoted arguments, escaped characters, and raw argument preservation.

**Assessment: good.**

This should remain the canonical command abstraction instead of attempting to clone Python decorators.

### Recommended next metadata

Each command should eventually declare:

- execution source compatibility;
- target type;
- reply requirement;
- group/private/channel scope;
- required Telegram rights;
- rate-limit class;
- whether scheduling is allowed;
- whether assistant execution is allowed;
- whether callback/inline invocation is allowed;
- idempotency characteristics;
- expected media/resource class.

---

## 3.2 Explicit execution source

The new `ExecutionSource` model is the correct direction:

```text
Interactive
Scheduled
Assistant
System
```

This fixes the conceptual mistake of using `Message.IsOutgoing` as a universal execution-mode flag.

`FilterMiddlewareForSource()` now correctly applies GroupOnly/PrivateOnly restrictions to non-interactive execution.

**Assessment: strong improvement.**

However, the scheduler still constructs a fake Telegram message and then calls the legacy `Execute()` path. The canonical `ExecuteExecution()` API exists but is not yet used by the scheduler. This leaves avoidable semantic debt.

---

## 3.3 Permissions

Owner/sudo/everyone permission tiers are implemented and dynamic sudo users are loaded from SQLite.

**Assessment: good foundation.**

The next step is not simply more permission levels. It is **scope-aware authorization**:

```text
principal
  + execution source
  + chat scope
  + target scope
  + capability
  + command policy
  -> authorization decision
```

This becomes important for addons, scheduler jobs, moderation, broadcasts, and assistant commands.

---

## 3.4 SQLite persistence

The database layer has durable scheduler state, job history, claims, leases, retry information, peer storage, addon records, moderation state, PM permit state, and other persistent settings.

**Assessment: strong MVP/production foundation.**

The database is one of the project's strongest areas and should be preserved.

---

## 3.5 Scheduler

The scheduler has:

- persistent jobs;
- claim tokens;
- lease renewal;
- bounded concurrency;
- retry/backoff;
- recurring jobs;
- misfire policy;
- execution history;
- scoped cancellation/history APIs;
- cancellation of active local workers;
- explicit at-least-once semantics.

The scoped scheduler APIs now prevent the earlier obvious cross-chat cancellation/history problem.

**Assessment: strong infrastructure.**

The remaining scheduler issues are mainly execution semantics, idempotency, and user-facing command parity.

---

## 3.6 Process runner

`internal/services/process/service.go` now correctly rejects shell execution and uses direct argv execution:

```text
exec.CommandContext(ctx, command, args...)
```

It also has:

- concurrency limits;
- timeout;
- bounded stdout/stderr;
- process-group cancellation;
- sensitive environment filtering;
- working-directory validation.

**Assessment: strong improvement and materially safer than the previous shell-string design.**

Do not regress this abstraction by adding generic shell execution back into it.

---

## 3.7 Downloader

The HTTP downloader has:

- HTTP/HTTPS scheme restriction;
- SSRF checks;
- redirect limit;
- size limits;
- timeout;
- bounded streaming;
- filename sanitization;
- provider abstraction;
- extractor provider support.

**Assessment: good security foundation.**

However, the safe transport uses environment proxy support. If the process is configured with a proxy that can reach internal destinations, the proxy can become an SSRF bypass because the local TCP guard only sees the proxy endpoint.

### Required hardening

For untrusted URL downloads, either:

1. disable proxy environment inheritance; or
2. validate the final destination through a controlled resolver/proxy-aware policy.

# 4. Critical and high-priority findings

## P0-01 — Scheduler still uses a synthetic Telegram message

### Location

`internal/scheduler/engine.go` → `executeCommand`

Current behavior creates a context approximately equivalent to:

```text
Message.ID = 0
Message.IsOutgoing = true
ReplyToID = 0
```

and then calls the legacy executor.

### Why this is wrong

A scheduled command does not have a real Telegram trigger message.

Using a fake message makes command handlers believe they are operating on a Telegram message that exists when it does not.

This can break commands using:

- `EditOrReply()`;
- `Reply()`;
- `Delete()`;
- reply target resolution;
- message metadata;
- album/topic context;
- command-message lifecycle assumptions.

### Correct implementation

Use `CommandExecution` directly:

```text
ExecutionSource = Scheduled
TriggerMessage = nil
Chat = persisted destination
PeerID = persisted destination peer
Sender = creator/principal
Principal = creator principal
```

Then every response must go through an explicit scheduled response policy.

### Acceptance criteria

A scheduled command must never attempt to edit `Message.ID=0` and must never require a nonexistent trigger message.

---

## P0-02 — Addon IPC can block shutdown indefinitely

### Location

`internal/addon/ipc.go`

`callLocked()` starts a goroutine which holds `r.mu` while waiting on `ReadBytes('\n')`.

`Stop()` also needs `r.mu` before it can close the process/stdio state.

### Failure mode

If an addon becomes unresponsive:

```text
Call()
  -> reader goroutine
  -> holds r.mu
  -> blocks waiting for addon output

Stop()
  -> waits for r.mu
  -> cannot close/kill process
```

The shutdown path can therefore hang behind a broken addon.

### Fix

Do not hold the runtime mutex while blocking on IPC I/O.

Prefer a dedicated reader goroutine with:

```text
stdout reader
   ↓
response dispatcher by request ID
   ↓
per-call channel
```

and make process cancellation close the reader/process independently.

Also ensure every pending request is failed when the runtime exits.

---

## P0-03 — Addon runtime lifecycle is not connected to application shutdown

`addon.Manager` exposes `ShutdownRuntimes()`, but `internal/app/shutdown.go` does not call it directly, and the addon plugin currently does not expose a context-aware shutdown hook.

Therefore an actively running external addon can outlive the logical plugin shutdown sequence.

### Required fix

Make addon management implement the plugin shutdown contract:

```text
App.Shutdown
  -> PluginManager shutdown
     -> addon plugin shutdown
        -> Manager.ShutdownRuntimes
```

The shutdown must be context-aware and bounded.

---

## P1-01 — User-log destination peer reconstruction is unsafe

### Location

`internal/services/userlog/service.go`

For a negative chat ID the code currently constructs:

```go
&tg.InputPeerChannel{ChannelID: -chatID}
```

This is not a correct general conversion from Telegram's externally encoded `-100...` channel ID to the MTProto channel ID.

It also omits the channel access hash.

### Impact

Logging to a configured supergroup/channel can fail with invalid peer/access-hash errors.

### Correct design

Persist the destination as a proper peer record:

```text
peer type
peer ID
access hash
```

or resolve it through the existing peer resolver before sending.

Do not derive MTProto peer IDs by arithmetic on the display/chat ID.

---

## P1-02 — Broadcast constructs peers without access hashes

### Location

`plugins/broadcast/broadcast.go`

Broadcast target construction creates `InputPeerUser`/`InputPeerChannel` values without access hashes.

The service has peer-resolution helpers, but the broadcast send path should guarantee normalization before sending.

### Impact

Broadcast can fail for users/channels that require access hashes, especially when the dialog object does not already provide a fully resolved `InputPeer`.

### Fix

Make broadcast target discovery return canonical peer objects from the peer manager/resolver rather than rebuilding them from numeric IDs.

---

## P1-03 — Scheduler is durable but external side effects remain at-least-once

The implementation correctly documents that a Telegram action can be duplicated after a crash between Telegram success and database completion.

This is not a bug in the lease mechanism; it is an inherent distributed-side-effect problem.

### Required design

For every scheduled action classify it as:

```text
safe-to-repeat
best-effort
idempotent-by-key
non-idempotent
```

Where possible, persist an idempotency key and make the command/action layer aware of it.

---

## P1-04 — Rate limiting is now wired, but policy is globally coarse

The executor receives a single limiter policy:

```text
60 / minute
burst 30
```

This is better than an unused limiter, but a single global policy is not sufficient for a userbot with expensive commands.

Media conversion, downloads, broadcast, scheduler creation, and simple `.ping` should not necessarily consume the same budget.

### Recommended model

```text
RateClassCheap
RateClassTelegram
RateClassMedia
RateClassExternalNetwork
RateClassAdmin
RateClassBroadcast
```

with per-user and optionally per-chat dimensions.

---

## P1-05 — Help splitting is byte-based and can break HTML structure

`plugins/help/help.go` splits at `4096` bytes.

Telegram message limits are not safely modeled by a simple UTF-8 byte count, and hard cutting HTML-formatted content can split tags/entities.

### Correct approach

Create a Telegram-aware formatter that:

1. measures the effective Telegram text length correctly;
2. splits on semantic blocks;
3. never splits an HTML tag/entity;
4. falls back to plain text only when necessary.

---

## P1-06 — Restart notification can lose its durable state on send failure

`checkRestartState()` removes `data/restart.json` before it knows that edit/send succeeded.

If Telegram is unavailable at that moment, the restart notification is lost.

### Fix

Use:

```text
read state
 -> attempt edit
 -> fallback send
 -> delete state only after successful delivery
```

Add an expiration timestamp so stale restart notifications do not live forever.

# 5. Medium-priority code and architecture findings

## P2-01 — Telegram service peer normalization is inconsistent

Some service methods call `ensureChannelAccessHash()` / `ensureUserAccessHash()`, while basic `SendMessage()` and `EditMessage()` do not normalize peers before sending.

This creates a hidden contract:

> callers must sometimes provide a fully resolved peer and sometimes can rely on the service to resolve it.

That is error-prone.

### Fix

Choose one rule:

> Every public Telegram service operation normalizes the peer at the service boundary.

Then enforce it consistently.

---

## P2-02 — Fallback peer construction still allows access-hash-zero peers

`ResolveTargetUser()` and some dispatcher paths can fall back to:

```go
&tg.InputPeerUser{UserID: uid}
```

when resolution fails.

That is acceptable as a representation of an unresolved target, but it should not silently reach Telegram RPC methods that require the access hash.

### Fix

Introduce explicit peer states:

```text
ResolvedPeer
UnresolvedPeer
InvalidPeer
```

and make operations requiring a hash fail with a useful resolver error rather than an eventual MTProto error.

---

## P2-03 — Addon installation is still primarily manifest registration

The addon runtime now exists, including IPC, protocol handshake, capability broker, executable validation, and SHA-256 verification.

However, `.addon install` itself only installs the manifest/record. It does not provide a complete end-user lifecycle such as:

```text
source URL
 -> download artifact
 -> verify digest/signature
 -> store artifact
 -> install manifest
 -> start runtime
 -> health check
 -> persist runtime artifact
```

The current command text says “installed successfully” while no executable artifact is installed by that command.

### UX correction

Either:

- make `install` explicitly mean **manifest registration**, or
- implement a true artifact installation flow.

The latter is required for an Ultroid-like extensibility experience.

---

## P2-04 — Addon runtime has no supervisor/restart policy

If an addon process crashes after being started, the manager does not currently provide a durable supervisor state with restart/backoff/health policy.

Required future states:

```text
installed
starting
running
stopping
stopped
crashed
backoff
blocked
```

---

## P2-05 — Media format UX is broader than actual codec support

`.convert <format>` accepts arbitrary format text, while the transcoder has a limited set of explicit codec policies.

Unknown formats eventually fall through to FFmpeg behavior rather than being rejected at command validation time.

### Fix

Expose an explicit supported format registry:

```text
mp4
mp3
aac
m4a
webm
ogg
opus
...
```

and reject unsupported values before downloading/processing media.

---

## P2-06 — Media resource protection is good but feature coverage is narrow

The media service has actual FFmpeg processing, output limits, disk checks, concurrency guards, and probing.

But compared with Ultroid it lacks the broad user-facing tool ecosystem:

- richer video controls;
- resize/crop utilities;
- audio tools;
- compression profiles;
- PDF conversion;
- image manipulation;
- watermark/logo operations;
- metadata manipulation;
- broader sticker tooling;
- broader upload/download workflows.

The current architecture is suitable for implementing these; the missing part is feature implementation.

# 7. Telegram UI/UX audit

## 7.1 What is already good

`internal/ui` provides reusable primitives:

- cards;
- key/value formatting;
- badges;
- buttons;
- URL buttons;
- switch-inline buttons;
- pagination rows;
- confirmation/cancel rows;
- progress bars;
- byte/duration formatting;
- alert/error/success formatting;
- expandable blockquotes.

The help command also has a reasonable edit-in-place userbot UX and category-based navigation.

This is a good foundation.

---

## 7.2 The main UI/UX problem: primitives are ahead of feature usage

The UI system has reusable components, but the actual feature surface does not yet use them at the breadth expected from Ultroid.

A mature userbot UX should consistently provide:

```text
command
  ↓
validate
  ↓
acknowledge quickly
  ↓
progress/status
  ↓
result card/media
  ↓
cleanup/replace temporary message
```

For expensive operations:

```text
⏳ Starting...
   ↓
progress / stage
   ↓
completion
   ↓
retry/help action
```

Current plugins often use one-off strings rather than a shared interaction state model.

---

## 7.3 Missing UX behaviors

The following should become standard:

- consistent success/error/status cards;
- consistent progress updates;
- cancel buttons for long operations;
- retry buttons for recoverable failures;
- pagination for large lists;
- confirmation for destructive operations;
- compact vs verbose output modes;
- consistent permission/error explanations;
- consistent “reply required” prompts;
- consistent link/button presentation;
- localized strings instead of hardcoded English/Indonesian mixtures;
- callback state ownership and expiration;
- message cleanup policy.

---

## 7.4 Help UX needs a second generation

Current `.help` is useful, but Ultroid-style discoverability needs:

```text
.help
  -> categories
     -> commands
        -> usage
        -> examples
        -> permissions
        -> aliases
        -> reply requirements
        -> media requirements
```

For large categories, use callback pagination rather than sending a very large message.

---

## 7.5 Inline/callback UX is infrastructure, not product parity

GoUltroid has callback and inline abstractions, but the current application registers only a very small default inline surface.

A framework being present is not equivalent to Ultroid's inline feature set.

The roadmap should therefore distinguish:

```text
framework complete
!=
feature complete
```

# 9. Voice chat audit

The current application deliberately does not wire a fake voice backend anymore.

That is the correct decision: a mock VC backend must not be presented as production functionality.

However, this means voice chat is currently **missing**, not partially implemented.

Ultroid parity requires a real implementation covering at minimum:

- join/leave;
- play audio;
- pause/resume;
- stop;
- queue;
- current track;
- volume;
- seek;
- download/decode pipeline;

- shell execution rejected;
- bounded process output;
- process timeouts;
- process-group kill;
- secret environment filtering;
- URL scheme validation;
- SSRF destination filtering;

- executable permission validation;
- optional SHA-256 verification;

## Remaining security priorities

1. Make downloader proxy behavior SSRF-safe.
2. Make addon IPC cancellation and process lifecycle robust.
3. Make addon artifact installation cryptographically trustworthy, preferably signature-based rather than only optional hashes.
4. Make every Telegram peer boundary resolver-backed.

6. Treat addon-provided content as untrusted for HTML/UI output.
7. Add audit logging for security-sensitive addon capability use.
8. Add per-command and per-feature resource budgets.

# 11. Reliability and lifecycle audit

## Good

- scheduler has explicit lifecycle;
- scheduler jobs have leases;
- plugin manager shuts down in reverse registration order;
- rate limiter is closed;
- database closes during application shutdown;
- logger sync handling was hardened for portability;
- process children are placed in their own process group;
- addon runtime has explicit stop support.

## Remaining

### 11.1 External runtime supervision

Addon crashes are not yet a first-class durable state machine.

### 11.2 Background goroutine ownership

Every background goroutine should be attributable to an application context and have a deterministic shutdown path.

This is especially important for:

- addon IPC readers;
- peer warm-up;
- restart notification;
- userlog handlers;
- assistant client;
- scheduler heartbeats.

### 11.3 Side-effect idempotency

Scheduler leases protect durable state but do not make Telegram side effects exactly-once.

This must remain explicit in the architecture.

# 15. Definition of parity

GoUltroid should not be declared “Ultroid parity” because it contains similarly named plugins.

A feature is considered parity-complete only when all of the following are true:

### Functional

- same important user-facing capability exists;
- primary command aliases exist or documented equivalents exist;
- arguments behave equivalently;
- reply/media targeting works;
- errors are handled;
- permissions are equivalent in intent.

### Telegram behavior

- private/group/supergroup/channel semantics are correct;
- access hashes are resolved correctly;
- edits/deletes/replies behave correctly;
- FloodWait is handled;
- media upload/download works.

### Persistence

- settings survive restart where Ultroid persists them;
- jobs/filters/notes/profile state survive restart.

### UX

- command acknowledgement is immediate for long operations;
- output is readable on mobile Telegram;
- destructive actions have confirmation where appropriate;
- progress/cancel/retry exists where useful;
- help and examples are discoverable.

### Reliability

- bounded concurrency;
- cancellation;
- retry behavior;
- no unbounded goroutines;
- no resource leaks;
- deterministic shutdown.

### Security

- user-controlled input cannot become shell code;
- URL fetches cannot become SSRF;
- addon capabilities are explicit;
- sensitive data is not logged;
- authorization is enforced at the domain boundary.

# 16. Final assessment

### What GoUltroid is doing right

The project should **not** be rewritten from scratch.

The current architecture already contains the right ingredients for a serious Go userbot:

```text
Telegram
   ↓
Dispatcher
   ↓
Execution envelope
   ↓
Permission / source / filter middleware
   ↓
Command
   ↓
Domain service
   ↓
Persistence / Telegram / process / media / external provider
```

That architecture is the correct long-term direction.

### What is currently wrong

The main problem is that the product layer has not yet caught up with the architecture.

There are three distinct maturity levels:

```text
Architecture       ████████░░  strong
Infrastructure     ███████░░░  good
Ultroid features   ███░░░░░░░  incomplete
UI/UX ecosystem    ███░░░░░░░  incomplete
```

The project therefore has a **good foundation but low functional parity**.

### Most important next action

Do not add random plugins one by one before fixing the remaining execution-boundary bugs.

First make these invariants true:

```text
1. Every execution has an explicit source.
2. Non-interactive commands never impersonate Telegram messages.
3. Every Telegram peer is resolved consistently.
4. Every background worker has an owned lifecycle.
5. Every external process has bounded resources and cancellation.
6. Every addon runtime can be safely stopped.
7. Every scheduled side effect has an explicit at-least-once/idempotency policy.
8. Every long operation has consistent Telegram UX.
```

After those invariants are stable, the fastest route toward Ultroid parity is a **feature-family implementation program**, not a Python-to-Go translation.
