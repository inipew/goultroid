## 1. Executive Summary & Architectural Evaluation

PMPermit in a userbot is not simply an "auto-reply warning bot"; it is an **Application-Level Private Message Access Control System (PM-ACS)** built on top of Telegram MTProto updates (`UpdateNewMessage`).

### Current Evaluation Scorecard
| Subsystem Area | Current Score | Critical Deficiencies |
|---|:---:|---|
| **Core PM Gate** | **8.5/10** | Solid basic interception via dispatcher, clean package structure |
| **Persistent Storage** | **7.5/10** | Durable SQLite records exist, but read-modify-write on JSON `warn_msg_ids` has race risks; missing list/count queries |
| **Warning System** | **7.0/10** | Warn count increments, but lacks burst/flood rate-limiting and structured reason metadata |
| **Outgoing Auto-Approve** | **4.5/10** | **P0 Contradiction**: blocked users cannot be unblocked by owner outgoing chat; **P0 Automation Leak**: automated messages (scheduler, broadcast, addons) inadvertently auto-approve targets |
| **MTProto Peer Handling** | **5.5/10** | `resolvePeer` creates bare `InputPeerUser` without `AccessHash`; `DeleteMessage` in `telegram/service.go` omits `ensureUserAccessHash` |
| **Error Handling & Resilience**| **4.5/10** | Silent error swallowing on RPC calls (`BlockUser`, `UnblockUser`, `DeleteMessage`, `SendMessage`) |
| **Actor Classification** | **5.0/10** | Only checks `ownerID` and `IsSudoID`; bots and verified users receive warnings and get blocked |
| **Blocked User Behavior** | **5.0/10** | Sends repetitive "You are blocked" replies to blocked incoming PMs, creating loop/spam vulnerability |
| **Ultroid Parity & UX** | **5.0/10** | Missing `.pmpermit unblock`, `.pmpermit list`, `.pmpermit status`, `.pmpermit test`, inline callback actions |

**Overall Maturity: 5.8 / 10**

## 2. Deep Root Cause Analysis of P0 / P1 Vulnerabilities

```
                  Telegram Private Message Update
                               │
                               ▼
                    dispatcher.dispatch()
                               │
            ┌──────────────────┴──────────────────┐
            │ msg.Out == true                     │ msg.Out == false
            ▼                                     ▼
   Is genuine human outgoing?            Classify Actor
   (Not Bot / Not Command)               (Self/Owner/Sudo/Bot/Verified)
            │                                     │
     ┌──────┴──────┐                       ┌──────┴──────┐
     │ YES         │ NO (Automation)       │ Bypass      │ Regular User
     ▼             ▼                       ▼             ▼
AutoApprove   Do nothing                 ALLOW         Evaluate State
• Approve                                         (Approved / Blocked / Pending)
• Unblock                                                │
• Delete Warns                                           ▼
                                                   Rate-Limit Check
                                                         │
                                                  Warning / Block RPC
```

### 2.1 [P0] Contradiction in `AutoApproveOutgoing`: Policy Clash with `IsBlocked`
* **Source Location:** [`plugins/pmpermit/pmpermit.go:52-54`](file:///home/dhimas/any/random/ultroid-go/plugins/pmpermit/pmpermit.go#L52-L54)
* **The Defect:**
  ```go
  // In plugins/pmpermit/pmpermit.go:
  if p.svc.IsBlocked(ctx, targetID) {
      return nil
  }
  _ = p.svc.AutoApproveOutgoing(ctx, peer, targetID)
  ```
  While `AutoApproveOutgoing` in [`internal/services/pmpermit/service.go:168-170`](file:///home/dhimas/any/random/ultroid-go/internal/services/pmpermit/service.go#L168-L170) explicitly performs:
  ```go
  if svc := s.getService(); svc != nil {
      _ = svc.UnblockUser(ctx, peer)
  }
  ```
* **Impact:** If the owner deliberately sends a message to a previously blocked user from their official Telegram app (Phone, Desktop), the plugin drops the message at line 52. The user remains blocked in Telegram and SQLite, and `AutoApproveOutgoing` is never executed. This directly violates the core principle: **an explicit outgoing message from the owner is the ultimate signal of communicative intent**.
* **Remediation:** Remove the `IsBlocked` bail-out in `pmpermit.go`. When an authorized owner initiates an outgoing PM, it must always execute `AutoApproveOutgoing`, which transitions the user to `StatusApproved`, resets warnings, cleans old warning messages, and issues `UnblockUser`.

### 2.2 [P0] Over-Aggressive Outgoing Auto-Approve (Human vs Automation)
* **Source Location:** [`plugins/pmpermit/pmpermit.go:33-41`](file:///home/dhimas/any/random/ultroid-go/plugins/pmpermit/pmpermit.go#L33-L41)
* **The Defect:**
  In Telegram MTProto, **any** message sent by the authenticated account has `msg.Out == true`. This includes:
  1. Messages typed by the user in Telegram mobile or desktop clients.
  2. Automated messages sent by GoUltroid plugins (Scheduler engine, Broadcast service, AI auto-replies, Downloader notifications, Addon plugins).
  
  Currently, `pmpermit.go` attempts to detect non-human messages via `strings.HasPrefix(msg.Message, ".")` and `IsPMPermitMessage(msg.Message)`.
  If a background scheduler task or broadcast sends a normal text (e.g. `"Meeting reminder at 3 PM"` or `"Your download completed"`), `msg.Out` is true, it is not a dot command, and it does not match warning signatures. As a result, **the recipient is automatically approved without the owner's conscious decision**.
* **Remediation:**
  Implement a thread-safe tracker for bot-generated outgoing messages (`BotSentTracker` / `OutgoingOriginTracker`). When `svc.SendMessage`, `svc.SendMedia`, etc., are invoked by GoUltroid, the emitted message ID is recorded with a sliding TTL (e.g. 2 minutes). When `UpdateNewMessage` arrives with `msg.Out == true`:
  - If `msg.ID` exists in `BotSentTracker`, it was generated programmatically by GoUltroid $\rightarrow$ **DO NOT auto-approve**.
  - If `msg.ID` does NOT exist in `BotSentTracker`, it originated from an external Telegram client typed by the human owner $\rightarrow$ **AUTO-APPROVE**.

### 2.3 [P0] Peer Resolution and Access Hash Loss in Telegram RPCs
* **Source Location:** [`internal/services/pmpermit/service.go:149-151`](file:///home/dhimas/any/random/ultroid-go/internal/services/pmpermit/service.go#L149-L151), [`internal/telegram/service.go:414-420`](file:///home/dhimas/any/random/ultroid-go/internal/telegram/service.go#L414-L420)
* **The Defect:**
  1. `service.go:resolvePeer(userID)` constructs a bare `&tg.InputPeerUser{UserID: userID}` with `AccessHash: 0`.
  2. While `telegram/service.go:BlockUser` and `UnblockUser` call `ensureUserAccessHash`, `telegram/service.go:DeleteMessage` **only calls `ensureChannelAccessHash`** and omits `ensureUserAccessHash`:
     ```go
     func (s *Service) DeleteMessage(ctx context.Context, peer tg.InputPeerClass, msgIDs []int) error {
         if len(msgIDs) == 0 { return nil }
         peer = s.ensureChannelAccessHash(ctx, peer) // <--- OMITTED ensureUserAccessHash!
         ...
     ```
  3. When `Approve` or `AutoApproveOutgoing` calls `svc.DeleteMessage(ctx, peer, ids)` after a bot restart or with a bare `InputPeerUser`, MTProto returns `PEER_ID_INVALID` or `CHANNEL_INVALID`, causing message cleanup to fail silently.
* **Remediation:**
  - Add `peer = s.ensureUserAccessHash(ctx, peer)` inside `telegram/service.go:DeleteMessage`, `React`, and `GetMessage`.
  - In `pmpermit.Service`, enhance `resolvePeer(ctx, userID)` to look up `AccessHash` from `peers.Storage` or entity cache when available.

### 2.4 [P0] Silent Error Swallowing in Service State Transitions
* **Source Location:** [`internal/services/pmpermit/service.go:163,169,185,191,212,222,254,263`](file:///home/dhimas/any/random/ultroid-go/internal/services/pmpermit/service.go#L163-L263)
* **The Defect:**
  Every Telegram RPC call is ignored with `_ =`:
  - `_ = svc.DeleteMessage(ctx, peer, ids)`
  - `_ = svc.UnblockUser(ctx, peer)`
  - `_ = svc.BlockUser(ctx, peer)`
  - `msg, _ := svc.SendMessage(...)`
  If `BlockUser` fails due to Telegram RPC network failure or flood wait:
  - Database status is set to `StatusBlocked`.
  - Telegram blocklist does NOT contain the user.
  - The operator has zero visibility because no error is logged to `zap.Logger`.
* **Remediation:**
  - Log all RPC errors using structured `zap.Logger`.
  - Implement retry with backoff for transient errors.
  - Track operation metrics (`blocked_count`, `block_failures`, `unblock_failures`, `delete_failures`).

### 2.5 [P0] Warning Message Storage Concurrency Race Condition
* **Source Location:** [`internal/database/pmpermit.go:137-149`](file:///home/dhimas/any/random/ultroid-go/internal/database/pmpermit.go#L137-L149)
* **The Defect:**
  `AddWarnMsgID` uses a classic Read-Modify-Write pattern on a JSON column:
  ```go
  ids, _ := db.GetWarnMsgIDs(ctx, userID)
  ids = append(ids, msgID)
  b, _ := json.Marshal(ids)
  _, err := db.ExecContext(ctx, "UPDATE pm_permit_records SET warn_msg_ids = ? WHERE user_id = ?", string(b), userID)
  ```
  If an unapproved user rapidly sends two messages concurrently:
  - Goroutine 1 reads `[101]`.
  - Goroutine 2 reads `[101]`.
  - Goroutine 1 writes `[101, 102]`.
  - Goroutine 2 writes `[101, 103]` (overwriting 102).
  When the user is approved, message `102` is orphaned and cannot be deleted.
* **Remediation:**
  Synchronize `AddWarnMsgID` and `ClearWarnMsgIDs` at the service layer using a mutex or serialize database execution to guarantee atomicity.

### 2.6 [P1] Missing Bot, Self, and Verified User Bypass
* **Source Location:** [`plugins/pmpermit/pmpermit.go:64-75`](file:///home/dhimas/any/random/ultroid-go/plugins/pmpermit/pmpermit.go#L64-L75)
* **The Defect:**
  Ultroid checks:
  ```python
  if user.bot or user.is_self or user.verified:
      return
  ```
  In Goultroid, `HandleIncomingMessage` only inspects `senderID`:
  ```go
  senderID := peerUser.UserID
  ```
  If a verified Telegram official service (e.g. Telegram service notifications, verified company bots, or regular bots interacting in PM) messages the userbot, GoUltroid issues warning messages and eventually blocks them.
* **Remediation:**
  Create an actor classification helper `ClassifyActor(userID, entities)`:
  - If `user.Bot` $\rightarrow$ bypass (allow).
  - If `user.Verified` $\rightarrow$ bypass (allow).
  - If `user.IsSelf` $\rightarrow$ bypass (allow).

### 2.7 [P1] Repetitive Spam Loop on Blocked Users
* **Source Location:** [`internal/services/pmpermit/service.go:240-247`](file:///home/dhimas/any/random/ultroid-go/internal/services/pmpermit/service.go#L240-L247)
* **The Defect:**
  ```go
  if rec, _ := s.db.GetPMRecord(ctx, senderID); rec != nil && rec.Status == StatusBlocked {
      if svc := s.getService(); svc != nil {
          msg, _ := svc.SendMessage(ctx, peer, "⛔ You are blocked from private messaging.")
          if msg != nil {
              s.addWarnID(senderID, msg.ID)
          }
      }
      return true, nil
  }
  ```
  If `contacts.Block` failed or if the user is in a DC propagation delay, every subsequent message sent by the blocked user triggers another `"You are blocked"` message from the bot. A spammer can weaponize this to force the bot into `FloodWait` or rate-limits.
* **Remediation:**
  Once a user is marked `StatusBlocked`, all incoming messages from that user must be **silently dropped** (`return true, nil` without sending any reply).

### 2.8 [P1] Warning Flood & Burst Rate-Limiting
* **The Defect:**
  Currently, if a sender bursts 5 messages in 200ms:
  - Message 1 $\rightarrow$ Send warning 1/4.
  - Message 2 $\rightarrow$ Send warning 2/4.
  - Message 3 $\rightarrow$ Send warning 3/4.
  - Message 4 $\rightarrow$ Block + Send limit reached.
  The sender gets instantly blocked in under 1 second without any reasonable human opportunity to read the warning.
* **Remediation:**
  Implement a per-user warning rate limiter:
  - Minimum 2.5 seconds cooldown between successive warning responses per user.
  - Extra messages sent during the cooldown window are counted towards message attempts or dropped without sending burst warning replies.

### 2.9 [P1] State Cleanup: Elimination of Ambiguous `StatusDenied`
* **Source Location:** [`internal/services/pmpermit/service.go:16`](file:///home/dhimas/any/random/ultroid-go/internal/services/pmpermit/service.go#L16)
* **The Defect:**
  `StatusDenied = "denied"` exists in the constant definitions but has no semantic definition, no transitions, and is never set in business logic.
* **Remediation:**
  Clean up status model into a strict 3-state machine:
  1. `StatusPending` ("pending")
  2. `StatusApproved` ("approved")
  3. `StatusBlocked` ("blocked")

## 4. Remediation Plan

### Phase 1: Core Security & Bug Fixes (P0)
1. **Outgoing Auto-Approve**: Remove `IsBlocked` guard in `pmpermit.go`.
2. **Bot-Sent Message Tracker**: Introduce `BotSentTracker` in `internal/telegram/service.go` so automated outgoing messages (scheduler, broadcast, addon) do not trigger `AutoApproveOutgoing`.
3. **Peer Resolution & Access Hash**: Add `ensureUserAccessHash` to `telegram/service.go:DeleteMessage`, `React`, and `GetMessage`. Enhance `resolvePeer` in `pmpermit.Service` to query `peers.Storage`.
4. **Structured Error Logging**: Replace `_ =` on RPC calls with logging to `zap.Logger` and retry on transient errors.
5. **Thread-Safe Warning Management**: Ensure atomic updates for warning message IDs.

### Phase 2: Parity, Robustness & Filtering (P1)
1. **Actor Classification**: Add bypass for bots (`user.Bot`), self (`user.IsSelf`), and verified accounts (`user.Verified`).
2. **Blocked Loop Elimination**: Silently drop incoming messages from users with `StatusBlocked`.
3. **Warning Reply Rate-Limiting**: Enforce a 2.5-second cooldown between warning messages per user.
4. **State Machine Cleanup**: Remove `StatusDenied`; standardize on `pending`, `approved`, `blocked`.
5. **Command Expansion**:
   - `.pmpermit unblock <user>`
   - `.pmpermit list [approved|blocked|pending]`
   - `.pmpermit status`
   - `.pmpermit test`
   - Group chat resolution support (reply, `@username`, user ID).

### Phase 3: EventBus & Audit Logging (P1)
1. Emit typed domain events (`EventTypePMPermit` / `core.PMPermitEvent`) on approval, disapproval, blocking, unblocking, and warnings.
2. Allow `UserLog` to ingest PMPermit audit events without direct coupling.
