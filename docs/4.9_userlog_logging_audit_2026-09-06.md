## 1. Executive Summary & Assessment

An in-depth research and source code audit of GoUltroid's logging subsystems was conducted, examining:
1. **Application/Runtime Logging** (`go.uber.org/zap`, `LOG_LEVEL`, structured fields)
2. **UserLog Service & Plugin** (`internal/services/userlog`, `plugins/userlog`)
3. **Event Ingestion & Routing** (Mentions, PMs, Admin Actions)
4. **Reliability & Concurrency** (Worker pool, queue sizing, race conditions, graceful drain)
5. **Observability & Diagnostics** (Delivery health states, metrics, dropped event tracking, `.log test`)
6. **Parity with Ultroid** (Media detection, reply bridges, destination validation, `@username` detection)

### Scorecard Summary
- **Internal Runtime Logger:** **8.0/10** (Clean `zap` integration, proper levels, needs standard field taxonomy)
- **UserLog Destination Representation:** **4.0/10** (Negative integer encoding, dropped `AccessHash`, Channel ID confusion)

## 2. Root Cause Analysis & Detailed Findings

### 2.1 [P0] Channel/Supergroup Peer Resolution & Access Hash Loss
* **Location:** [`plugins/userlog/userlog.go:174-179`](file:///home/dhimas/any/random/ultroid-go/plugins/userlog/userlog.go#L174-L179), [`internal/services/userlog/service.go:107-115`](file:///home/dhimas/any/random/ultroid-go/internal/services/userlog/service.go#L107-L115)
* **The Problem:**
  When `.setlog` is invoked inside a channel or supergroup:
  ```go
  case *tg.InputPeerChannel:
      chatID = -peer.ChannelID
  ```
  `peer` (`*tg.InputPeerChannel`) contains both `ChannelID` and `AccessHash`. Saving only `-peer.ChannelID` drops `AccessHash`.
  Later, when dispatching a log:
  ```go
  if chatID < 0 {
      peer = &tg.InputPeerChannel{ChannelID: -chatID}
  }
  ```
  `InputPeerChannel` is constructed with `AccessHash: 0`. Telegram MTProto servers reject messages sent without an access hash with `CHANNEL_INVALID` unless cached in memory.
  Furthermore, Telegram Bot API channel IDs use `-100<ChannelID>` while MTProto channel IDs are positive integers without `-100`. Encoding destination types using the sign of an integer is fragile and lossy.
* **Fix Required:**
  Define a structured `LogDestination`:
  ```go
  type LogDestinationType string
  const (
      LogDestinationChat    LogDestinationType = "chat"
      LogDestinationChannel LogDestinationType = "channel"
  )

  type LogDestination struct {
      Type       LogDestinationType `json:"type"`
      ID         int64              `json:"id"`
      AccessHash int64              `json:"access_hash,omitempty"`
      Title      string             `json:"title,omitempty"`
  }
  ```
  Store normalized destination in `user_log_settings` and preserve `AccessHash`.

### 2.2 [P0] Incomplete Mention Detection (Misses `@username` and `msg.Mentioned`)
* **Location:** [`plugins/userlog/userlog.go:142-150`](file:///home/dhimas/any/random/ultroid-go/plugins/userlog/userlog.go#L142-L150)
* **The Problem:**
  Mention detection currently only iterates over `msg.Entities` searching for `*tg.MessageEntityMentionName` with `m.UserID == p.ownerID`.
  In Telegram:
  1. Standard `@username` tags are sent as `*tg.MessageEntityMention` (which does not contain user IDs, only text offsets).
  2. Replies to the owner's messages in groups automatically flag `msg.Mentioned = true` on the Telegram message.
  Because both were omitted, any mention of the user's `@username` or reply in a group was completely ignored by UserLog.
* **Fix Required:**
  - Check `msg.Mentioned == true` first (built-in MTProto flag).
  - Check `*tg.MessageEntityMentionName` matching `p.ownerID`.
  - Check `*tg.MessageEntityMention` matching `@ownerUsername` (case-insensitive).

### 2.3 [P0] Silent Error Swallowing in Service and Queue
* **Location:** [`internal/services/userlog/service.go:98-100`](file:///home/dhimas/any/random/ultroid-go/internal/services/userlog/service.go#L98-L100), [`plugins/userlog/userlog.go:138,165`](file:///home/dhimas/any/random/ultroid-go/plugins/userlog/userlog.go#L138)
* **The Problem:**
  - `sendToLogChat` executes:
    ```go
    chatID, err := s.GetLogChat(ctx)
    if err != nil || chatID == 0 {
        return nil
    }
    ```
    If database queries fail, the error is discarded and logging silently reports success.
  - In `plugins/userlog/userlog.go`, queue jobs execute `_ = p.svc.LogPM(...)` and `_ = p.svc.LogMention(...)`. If delivery fails, no log is emitted to `zap.Logger`, leaving operators blind when logging breaks.
* **Fix Required:**
  - Return explicit errors when DB lookup fails, distinguishing between unconfigured (`nil`) and query error.
  - Log delivery failures using structured Zap logging: `s.logger.Error("userlog delivery failed", zap.String("category", category), zap.Error(err))`.
  - Maintain delivery health stats (`Healthy`, `Degraded`, `Failed`).

### 2.4 [P1] Destination Validation on `.setlog` & Missing `.log test`
* **Location:** [`plugins/userlog/userlog.go:169-186`](file:///home/dhimas/any/random/ultroid-go/plugins/userlog/userlog.go#L169-L186)
* **The Problem:**
  `.setlog` writes the chat ID directly to the database without checking if the userbot has permissions to write to that chat. If the userbot lacks write rights (`ChatWriteForbidden`) or is banned/not in the channel, `.setlog` says "Log destination set!" but all subsequent logs silently fail.
  Additionally, there is no command to test delivery (`.log test`).
* **Fix Required:**
  - When `.setlog` runs, send a verification message immediately to the target chat. If sending fails, abort and return a user-friendly error without persisting.
  - Support setting log destination by username/ID argument: `.setlog @my_log_channel` or `.setlog -100...`.
  - Implement `.log test` to send a test message and report roundtrip delivery latency.

### 2.5 [P1] Queue Capacity, Drop Tracking, and Shutdown Race
* **Location:** [`plugins/userlog/userlog.go:15, 53-62, 67-85`](file:///home/dhimas/any/random/ultroid-go/plugins/userlog/userlog.go#L15-L85)
* **The Problem:**
  - Queue size is fixed to 32: `make(chan func(), 32)`. A sudden burst of mentions drops events silently.
  - Shutdown calls `close(p.queue)`: if an incoming message arrives at `enqueue()` while shutdown is closing the channel, Go panics (`send on closed channel`).
  - Worker passes `p.ctx` with no timeout: an MTProto RPC stall can lock up workers.
* **Fix Required:**
  - Expand queue buffer to 256.
  - Add an atomic flag `closing` and `sync.RWMutex` to guard `enqueue` against closing channel panics.
  - Add atomic counters for `enqueued`, `delivered`, `failed`, `dropped`.
  - Apply a per-job delivery timeout (e.g. 15s) so workers never freeze.

### 2.6 [P1] Unsafe Unicode Truncation
* **Location:** [`internal/services/userlog/service.go:128-130, 153-155`](file:///home/dhimas/any/random/ultroid-go/internal/services/userlog/service.go#L128-L130)
* **The Problem:**
  ```go
  if len(snippet) > 200 {
      snippet = snippet[:200] + "..."
  }
  ```
  `len()` measures bytes. For multibyte UTF-8 characters (emojis, accented characters, Cyrillic, Asian scripts), slicing at byte 200 splits a code point, causing invalid UTF-8 rendering.
* **Fix Required:**
  Use rune-based truncation: `runes := []rune(str)` or UTF-8 safe boundary truncation.

### 2.7 [P1] Disconnected Admin Action Logging (`LogAction`)
* **Location:** [`internal/services/userlog/service.go:171-183`](file:///home/dhimas/any/random/ultroid-go/internal/services/userlog/service.go#L171-L183)
* **The Problem:**
  `LogAction` exists in `userlog.Service`, but zero callers exist in the codebase. When `.ban`, `.kick`, `.mute`, or `.warn` commands succeed, no log is delivered to the log channel.
* **Fix Required:**
  - Introduce `AdminActionEvent` in `internal/core/events.go`.
  - Have admin/moderation actions publish `AdminActionEvent` upon execution.
  - UserLog subscribes to `AdminActionEvent` via `EventBus` and records: Action, Actor, Target, Chat, Reason, Result (Success/Failure), and Timestamp.

---

### 2.8 [P1] Bot, Self, and Log-Channel Loop Filtering
* **Location:** [`plugins/userlog/userlog.go:114-140`](file:///home/dhimas/any/random/ultroid-go/plugins/userlog/userlog.go#L114-L140)
* **The Problem:**
  - If a bot mentions the user or sends a PM, UserLog records it, which can spam the log channel.
  - If a message occurs in the log chat itself, UserLog could attempt to log it back into the log chat.
* **Fix Required:**
  - Check `msg.PeerID`: if it matches the log chat destination, skip.
  - Check sender: if `userObj.Bot`, ignore.
  - Configurable privacy policy: PM logging default toggle and filters.

## 4. Implementation Phasing & Work Items

### Phase 1: Correctness & Core Stability (P0)
1. **Destination Model (`LogDestination`)**:
   - Create `LogDestination` struct with `Type`, `ID`, `AccessHash`, `Title`.
   - Update `userlog.Service` to store and load `LogDestination` (JSON in DB).
   - Ensure backward compatibility with numeric `log_chat_id`.
2. **Proper InputPeer Resolution**:
   - Construct `&tg.InputPeerChannel{ChannelID: dest.ID, AccessHash: dest.AccessHash}` for channels.
   - Construct `&tg.InputPeerChat{ChatID: dest.ID}` for basic groups.
3. **Mention Detection Overhaul**:
   - Implement multi-stage detection: `msg.Mentioned`, `MessageEntityMentionName`, and `@ownerUsername` via `MessageEntityMention`.
4. **Queue Concurrency & Shutdown Fix**:
   - Add `sync.RWMutex` + `atomic.Bool closing` to `Plugin`.
   - Increase queue capacity to 256.
   - Track `atomic.Int64` for enqueued, delivered, failed, dropped.
5. **No Silent Error Swallowing**:
   - Return real DB errors in `GetDestination` and `sendToLogChat`.
   - Add structured Zap logging in service on delivery errors.

### Phase 2: Parity, Diagnostics & Observability (P1)
6. **Destination Validation & `.log test`**:
   - In `.setlog`, send test verification message before persisting.
   - Support `.setlog <arg>` (ID or `@channel_username`).
   - Implement `.log test` command.
7. **Delivery Retry for Transient Errors**:
   - Add retry with exponential backoff (100ms, 300ms) for transient network/RPC errors.
   - Fail-fast on permanent permissions errors.
8. **Rune-safe Truncation & Rich Formatting**:
   - Replace byte slicing with rune-based truncation.
   - Format rich logs with clickable user profile links (`tg://user?id=...`), chat links, timestamps, and media indicators.
9. **Admin Action Event Bus Wiring**:
   - Introduce `AdminActionEvent` in `internal/core/events.go`.
   - Publish from `AdminFacade` / admin plugin on actions.
   - Subscribe in UserLog and format administrative audit logs.
10. **Loop & Bot Filtering**:
    - Filter out messages sent in the log chat itself.
    - Filter out bot senders (`userObj.Bot`).

### Phase 3: Advanced UX (P2)
11. **`.log status` Health Dashboard**:
    - Show `HEALTHY`, `DEGRADED`, `FAILED`, `UNCONFIGURED` status.
    - Display queue depth, delivered count, dropped count, last delivery timestamp.
12. **Configurable Toggles**:
    - Support `.log [tags|pms|actions] [on|off]`.

## 5. Test Matrix

1. **Destination Serialization**:
   - Save and retrieve Channel destination with `AccessHash`.
   - Save and retrieve Chat destination.
   - Legacy fallback from numeric string.
2. **Delivery & InputPeer**:
   - Delivery to channel uses `InputPeerChannel` with exact channel ID and access hash.
   - Delivery to basic group uses `InputPeerChat`.
   - DB error propagation (no silent success).
3. **Mention Detection**:
   - Detection via `msg.Mentioned == true`.
   - Detection via `MessageEntityMentionName`.
   - Detection via `@owner` `MessageEntityMention`.
   - Non-mention message ignored.
4. **Filtering**:
   - Bot sender ignored.
   - Message in log destination chat ignored.
   - Outgoing message (`msg.Out == true`) ignored.
5. **Concurrency & Shutdown**:
   - Enqueue under concurrent shutdown does not panic.
   - Dropped events increment drop counter when queue is full.
   - Graceful drain on shutdown.
6. **UTF-8 Safety**:
   - Emojis and multi-byte characters truncated cleanly without split code points.
7. **Verification & Diagnostics**:
   - `.setlog` fails when write forbidden.
   - `.log test` dispatches test notification and reports status.
