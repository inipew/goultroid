# Modular Feature Architecture

Goultroid is moving toward a feature-oriented modular monolith. A feature becomes the primary ownership boundary for behavior, persistence, migrations, callbacks, and tests. The application remains one Go binary; this is not a microservice split.

## Compile-time registry

Built-in features use a generated compile-time registry. `internal/app/generated_modules.go` is generated by `tools/featuregen` from plugin directories that expose a package-level `Module` value.

There is deliberately no runtime reflection, dynamic Go plugin loading, or side-effect `init()` registration for feature discovery. The generated registry keeps startup deterministic and the dependency graph visible to the compiler.

The existing `internal/plugin.Manager` remains the runtime registration and lifecycle authority. A feature module is a composition boundary above a plugin, not a replacement for the plugin lifecycle system.

## Dependency rules

- `app` may depend on features, core, application, and infrastructure.
- Features may depend on core, application contracts, and approved platform abstractions.
- Features must not depend on other features by default.
- Platform/infrastructure must never depend on features.
- Core must never depend on concrete features.
- Features must not import `app`.
- Feature persistence types and repositories should be owned by the feature, not the generic database package.

These rules should eventually be enforced by automated import-graph tests.

## Module contract

`internal/module.Module` exposes a stable `Manifest()` and explicit `Register(context.Context, *module.Runtime)` operation. The runtime is an explicit dependency bundle, not a `map[string]any` service locator.

## Migration contract

`internal/database.Migration` is the new feature-owned schema contract. New migration IDs must be namespaced, for example `clone.001` and `clone.002`.

Existing integer migrations are immutable history and must not be renumbered or rewritten. Migration adoption will bridge legacy versions to namespaced feature migrations without executing equivalent SQL twice.

## Clone pilot

Clone is the first module. The first pilot step moves composition into the module boundary while deliberately keeping the current clone repository and legacy migrations unchanged. This isolates the architecture change from a data migration.

Next gates:

1. Add namespaced clone migration adoption.
2. Test fresh and existing database upgrade paths.
3. Move `CloneState` and clone SQL into the clone feature.
4. Remove the legacy clone database implementation only after compatibility tests pass.

## Operational goal

A new persistent feature should ultimately require one feature directory and no manual edit to the global plugin catalog. The generated registry removes the final global registration edit while retaining compile-time safety.
