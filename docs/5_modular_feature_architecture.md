# Modular Feature Architecture

Goultroid is moving toward a feature-oriented modular monolith. A feature is the primary ownership boundary for behavior, persistence, migrations, callbacks, and tests. The application remains one Go binary; this is not a microservice split.

## Compile-time registry

Built-in features currently live under `plugins/<feature>` and expose a package-level `Module` value. `internal/app/generated_modules.go` is generated by `tools/featuregen` and is the only built-in module registry.

There is deliberately no runtime reflection, dynamic Go plugin loading, or side-effect `init()` registration for feature discovery. The generated registry keeps startup deterministic and the dependency graph visible to the compiler.

The existing `internal/plugin.Manager` remains the runtime registration and lifecycle authority. A feature module is a composition boundary above a plugin, not a replacement for the plugin lifecycle system.

## Dependency rules

- `app` may depend on features, core, application, and infrastructure.
- Features may depend on core, application contracts, and approved platform abstractions.
- Features must not depend on other feature packages by default.
- Platform/infrastructure must never depend on features.
- Core must never depend on concrete features.
- Features must not import `app`.
- Feature persistence types, repositories, SQL, and migrations are owned by the feature.

These rules are enforced by `internal/architecture/imports_test.go` for the primary feature boundaries and should expand as additional boundaries are introduced.

## Module contract

`internal/module.Module` exposes a stable `Manifest()` and explicit `Register(context.Context, *module.Runtime)` operation. The runtime is an explicit dependency bundle, not a `map[string]any` service locator.

Persistent modules additionally implement `database.MigrationProvider` and expose deterministic feature migrations.

## Migration contract

New migrations use namespaced IDs such as `clone.001` and `clone.002`. They execute transactionally through `database.SQLExecutor` and record checksums in `feature_schema_migrations`.

Existing integer migrations are immutable history and must not be renumbered or rewritten. `LegacyVersions()` allows an equivalent feature migration to be adopted from an existing integer migration without executing the SQL twice.

## Clone pilot

Clone is the first complete feature-ownership pilot.

Its persistence contract and SQLite implementation now live under `plugins/clone`, and its schema migrations are `clone.001` and `clone.002`. Existing legacy migrations 15 and 16 are no longer registered as new migrations; existing databases adopt those versions into `feature_schema_migrations`.

The pilot has tests for both fresh databases and legacy databases containing the old migration versions. The legacy `internal/database/clone.go` and `internal/database/clone_migration.go` ownership files have been removed.

## Operational goal

A new persistent feature should ultimately require one feature directory and no manual edit to the global plugin catalog. The generated registry removes the final global registration edit while retaining compile-time safety.
