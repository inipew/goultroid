# Modular Feature Architecture

Goultroid is moving toward a feature-oriented modular monolith. A feature is the primary ownership boundary for behavior, persistence, migrations, callbacks, and tests. The application remains one Go binary; this is not a microservice split.

## Current execution status

The first five roadmap stages are now implemented in the repository:

1. Module foundation was stabilized: runtime dependencies are grouped into core, Telegram, and reusable service capabilities, and feature-owned moderation state was removed from the global runtime.
2. Feature migration safety was hardened: invalid records, ambiguous legacy ownership, checksum drift, invalid IDs/descriptions, and database read errors are rejected explicitly.
3. Architecture guards were expanded: generated module invariants and the remaining legacy feature-persistence surface are CI-tested.
4. Clone and Notes provide persistent feature-ownership examples; Admin is the second deliberate migration pilot for a legacy feature-owned schema.
5. Admin now owns the moderation warning repository and `admin.001` migration, while the generic moderation service receives a repository interface instead of depending on `internal/database`.

The next phases should continue feature-by-feature rather than adding more fields to `module.Runtime`.

## Compile-time registry

Built-in features currently live under `plugins/<feature>` and expose a package-level `Module` value. `internal/app/generated_modules.go` is generated by `tools/featuregen` and is the only built-in module registry.

There is deliberately no runtime reflection, dynamic Go plugin loading, or side-effect `init()` registration for feature discovery. The generated registry keeps startup deterministic and the dependency graph visible to the compiler. Generation is deterministic by module ID and rejects duplicate aliases and IDs.

The existing `internal/plugin.Manager` remains the runtime registration and lifecycle authority. A feature module is a composition boundary above a plugin, not a replacement for the plugin lifecycle system.

## Dependency rules

- `app` may depend on features, core, application, and infrastructure.
- Features may depend on core, application contracts, and approved platform abstractions.
- Features must not depend on other feature packages by default.
- Platform/infrastructure must never depend on features.
- Core must never depend on concrete features.
- Features must not import `app`.
- Feature persistence types, repositories, SQL, and migrations are owned by the feature.

These rules are enforced by `internal/architecture/imports_test.go` for the primary feature boundaries. The test also freezes the remaining legacy feature-persistence files so the old architecture cannot grow while migration continues.

## Module contract

`internal/module.Module` exposes a stable `Manifest()` and explicit `Register(context.Context, *module.Runtime)` operation. The runtime is an explicit dependency bundle, not a `map[string]any` service locator.

Runtime dependencies are grouped into `CoreRuntime`, `TelegramRuntime`, and `ServiceRuntime`. New feature-specific business services or repositories must not be added to `ServiceRuntime`; the feature should construct them from the narrow capabilities it needs.

`Manifest.Dependencies` is validated and resolved deterministically with dependency-before-dependent ordering and cycle detection.

Persistent modules additionally implement `database.MigrationProvider` and expose deterministic feature migrations.

## Migration contract

New migrations use namespaced IDs such as `clone.001`, `clone.002`, and `admin.001`. They execute transactionally through `database.SQLExecutor` and record checksums in `feature_schema_migrations`.

Existing integer migrations are immutable history and must not be renumbered or rewritten. `LegacyVersions()` allows an equivalent feature migration to be adopted from an existing integer migration without executing the SQL twice.

The migration runner now rejects duplicate feature IDs, duplicate/ambiguous legacy ownership, invalid legacy versions, empty descriptions/checksums, malformed persisted migration records, and non-`sql.ErrNoRows` errors while probing legacy history. Legacy adoption can optionally verify physical schema invariants before recording the feature migration.

## Clone pilot

Clone is the first complete feature-ownership pilot.

Its persistence contract and SQLite implementation now live under `plugins/clone`, and its schema migrations are `clone.001` and `clone.002`. Existing legacy migrations 15 and 16 are no longer registered as new migrations; existing databases adopt those versions into `feature_schema_migrations`.

The pilot has tests for both fresh databases and legacy databases containing the old migration versions. The legacy `internal/database/clone.go` and `internal/database/clone_migration.go` ownership files have been removed.

## Admin pilot

Admin is the second deliberate persistence-ownership pilot.

The moderation warning repository now lives under `plugins/admin`, while `internal/services/moderation` contains only reusable moderation behavior and depends on a `WarningRepository` interface. `admin.001` owns the feature migration and adopts immutable legacy migration 8. The old `internal/database/moderation.go` repository was removed.

This establishes the intended pattern for future migrations:

```text
plugins/admin/
    module.go
    repository.go
    migration.go
    plugin behavior
        |
        v
internal/services/moderation/
    reusable business behavior
        |
        v
WarningRepository interface
        |
        v
plugins/admin SQLite implementation
```

## Operational goal

A new persistent feature should ultimately require one feature directory and no manual edit to the global plugin catalog. The generated registry removes the final global registration edit while retaining compile-time safety.

The obsolete empty `internal/app/catalog.go` has been removed. The remaining legacy database files are now an explicit migration backlog rather than an open-ended extension point.
