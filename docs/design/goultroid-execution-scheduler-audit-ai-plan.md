No live workload, production trace, or CPU profile was collected. ## Scope and execution map

```text
Schedule API → durable schedule/legacy row → due-time wake → claim/materialize
    → Jobs occurrence → fenced attempt lease → TaskEngine admission
    → resource-qualified dispatch → durable attempt commit → Jobs settlement
    → scheduler compatibility-row reconciliation (legacy claims only)
```

The redesigned path uses `jobs.Manager.ProcessDueSchedules` and `job_schedules`; `MaterializeDueSchedule` advances a schedule and materializes its occurrence in one SQLite transaction (`internal/jobs/manager_schedule.go`, `internal/jobs/sqlite/store.go`). The compatibility path uses `ClaimDueScheduledJobs` with a three-minute lease, then `SubmitOccurrence` and an in-memory tracked claim (`internal/scheduler/engine.go`, `repository.go`). Jobs prepares an attempt lease before TaskEngine submission and commits the result through the task's durability callback (`internal/jobs/manager_attempt.go`). TaskEngine selects only candidates whose resources are available and reserves those resources at dispatch (`internal/taskengine/engine_dispatch.go`). These are distinct ownership paths; a measurement of legacy claim reconciliation must not be attributed to all redesigned schedules.

## Findings and evidence level

| ID | Evidence in this HEAD | What remains unknown |
| --- | --- | --- |
| **S1 — scheduler worker hold (R5)** | A resource-bearing scheduled command submits a child task and waits on its ticket inside a `scheduler.action` wrapper. The wrapper uses the `scheduler` pool, default concurrency four; the child uses a resource-selected pool. Four waiting wrappers can therefore occupy all four scheduler workers (`internal/app/scheduled_action.go`, `internal/scheduler/engine.go`, `internal/taskengine/engine_config.go`). The historical short contention harness reproduced full occupancy. | Whether representative sustained contention delays independent scheduler work materially, how often the 90-second wrapper timeout fires, and whether any resource cycle or starvation occurs. No deadlock or production incident is established. Resource-free commands execute in the wrapper; `ActionJob` directly uses the target definition and does not create this wrapper. |
| **S2 — reconciliation cost (R6)** | Each scheduler loop pass copies all tracked **legacy** claims and reads the scheduled row and usually its Jobs occurrence for each. Active claims impose a 30-second safety wake; schedule/settlement notifications and immediate continued batches can cause more passes. The historical SQLite 1,000-claim fixture measured 75.6–79.5 ms and 2,000 reads per pass. `GetScheduledJob` errors now preserve tracking (`internal/scheduler/engine.go`). | Actual legacy claim cardinality, wake/pass rate, query time under shared production DB contention, and whether the 1,000-claim fixture represents usage. The historical benchmark alone does not justify a refactor or prove acceptability. |
| **S3 — cancellation of already materialized redesigned work** | `Scheduler.Cancel` deletes the compatibility row and disables the redesigned schedule. It cancels a tracked occurrence only when a legacy claim exists. A redesigned occurrence is not entered into that map; `DisableSchedule` only stops future materialization. `Jobs.Manager.CancelOccurrence` exists as a durable cancellation boundary (`internal/scheduler/engine.go`, `internal/jobs/manager.go`). | Whether product semantics promise cancellation of work already materialized when a schedule is deleted, and whether any separate caller closes that occurrence. The existing scheduler cancellation test checks row removal, not a blocked active redesigned occurrence. Treat this as a **conditional contract gap**, not a proven user-visible bug. |
| **S4 — recovery and duplicate side effects** | Legacy claim tokens fence compatibility-row completion; occurrence keys identify a due slot. Redesigned materialization uses a transactional occurrence key and Jobs attempt leases. Jobs recovery skips in-memory tracked attempts, scans at startup and on wake, and has a 30-second safety interval (`internal/scheduler/repository.go`, `internal/jobs/manager_recovery.go`, `internal/jobs/sqlite/store.go`). | Whether process loss at each boundary yields one logical occurrence and acceptable physical side-effect behavior. Durable idempotence does not by itself prove exactly-once Telegram side effects. Long-running legacy occurrences relative to the three-minute compatibility lease need a controlled test before any duplicate-execution claim. |
| **S5 — shutdown and resource release** | Runtime quiesces and stops components in reverse dependency order. Scheduler quiesce waits for a claim batch, not all task attempts; Jobs stops retry monitors, while TaskEngine owns dispatch cancellation and drain (`internal/runtime/runtime.go`, `internal/scheduler/engine.go`, `internal/jobs/manager.go`, `internal/taskengine/shutdown.go`). | Drain latency and lease/attempt convergence with blocked child tasks, DB errors, and a forced deadline. No resource leak is established from source inspection. |

TaskEngine's bounded backlogs and dispatch-time resource reservation limit admission and resource hold, but they do not free an already running scheduler wrapper that is waiting on a child ticket. Jobs retry monitors are separately bounded to four workers with a 256-item queue and durable recovery fallback (`internal/jobs/manager_retry.go`). A full audit of worker contention must observe both groups rather than count them as one pool.

## Audit and implementation sequence

1. **A0 — Fix the workload contract and collect a baseline.** Record whether the deployment uses redesigned schedules, legacy claims, or both; schedule and active-claim distributions; command mix and resource capacities; target concurrency; SQLite connection settings; and the expected meaning of deleting a schedule with active work. Use sanitized IDs and no Telegram credentials. Capture idle and representative load before setting a performance threshold.
2. **A1 — Sustained S1 acceptance.** Extend the existing `internal/app/runtime_execution_e3_r5_test.go` harness for controlled 30–90 second resource contention. Hold all four wrappers, submit independent scheduler work, then release the child resource. Record scheduler running/waiting depth, child queue p50/p95/p99, independent-work admission/start latency, wrapper completion and timeout counts, and cancellation latency. Repeat with resource-free commands and direct `ActionJob` as controls. A correctness failure or a material latency increase relative to the agreed workload baseline opens a narrowly scoped orchestration fix; otherwise retain the current design and record the measured limit.
3. **A2 — Representative S2 acceptance.** Count legacy claims and scheduler loop passes by wake reason (due timer, completion/schedule notification, safety wake, error retry). Record reads/pass, reads/second, reconciliation p50/p95/p99, SQLite busy time, and CPU/DB share at the observed claim distribution, plus 1/100/1,000 stress controls using the existing benchmark. Determine cost from `claim count × pass rate`, including burst processing. Only if measured cost is material, evaluate due-only reconciliation or a bounded sweep; prove that missed wake and restart convergence still hold.
4. **A3 — Correctness probes.** Use fault-injecting stores and a persistent SQLite restart fixture for cancellation before materialization, after materialization but before submit, while queued, while a child runs, during durable commit, and after lease expiry. Check one logical occurrence per slot, attempt-budget accounting, final compatibility-row state, no resource hold after terminal settlement, and the chosen cancellation contract. Inject transient scheduled-row and occurrence reads and a failed commit. Distinguish a repeated external side effect from a repeated durable attempt.
5. **A4 — Conditional minimal changes.** Implement only a defect or material cost established by A1–A3. Keep schedule timing in Scheduler, durable occurrence and retry ownership in Jobs, and physical resource admission in TaskEngine. For any proposed change, document state transitions, rollback/recovery, persistence compatibility, and before/after metrics. Do not redesign TaskEngine as a prerequisite.

## Release gates for any later code change

- Performance acceptance must report workload duration, claim distribution, hardware, Go/SQLite versions, and before/after throughput, p50/p95/p99 latency, DB reads/second, CPU, and allocations. Compare an independent scheduler task under blocked wrappers, not only the blocked tasks themselves. Set the materiality threshold from the deployment workload before choosing an optimization.
- Run focused package tests, `go test -race ./... -count=1 -timeout=180s`, `go vet ./...`, and `go build ./cmd/goultroid` after implementation; inspect `internal/architecture` tests and verify generated registration only if plugin wiring changes. Report exact failures and CI state rather than carrying forward historical PASS results.
- Closure requires a written R5 and R6 decision with measured evidence, an explicit active-work cancellation contract, and restart/shutdown outcomes. Until then, S1/S2 remain performance risks and S3–S5 remain probes, not confirmed incidents.

### A3–A4: correctness result and change

The active redesigned `ActionJob` cancellation test failed before the fix: its handler kept running after `Scheduler.Cancel` returned. A second probe covers a queued occurrence. `Scheduler.Cancel` now disables future schedule materialization, closes the scheduler-owned scope, cancels active redesigned occurrences through Jobs, cancels a tracked legacy occurrence durably, and only then deletes the compatibility row. SQLite supplies a schedule-scoped active-occurrence lookup through a new Jobs store port. A failed durable cancellation is returned to the caller while the compatibility row and legacy claim remain available for retry. `CancelOccurrence` retains its existing cancel-epoch fencing. An SQLite file test confirms a canceled, materialized occurrence remains canceled and rejects a new attempt after reopen.

The contract chosen here is: deleting a schedule requests cancellation of both future runs and already materialized active work. A side effect already completed before cancellation cannot be undone, and a handler that ignores context may continue physical work even after durable cancellation; this update does not claim exactly-once external effects. Existing lease, retry, recovery, TaskEngine shutdown, and scheduler registration tests provide adjacent coverage, but this session did not run a live process-crash or Telegram side-effect replay fixture. S4/S5 remain open for that acceptance.

An independent review found two further cancellation races. First, a legacy occurrence could survive after restart or between durable claim and in-memory tracking. `Scheduler.Cancel` now serializes against its legacy claim batch and resolves the occurrence by the durable due-slot key; a test that discards claim tracking failed before this change and passed afterward. Second, Jobs could prepare an attempt and pause before TaskEngine submission while `CancelOccurrence` committed and returned. Admission and cancellation now share a short-lived, per-occurrence gate across lease preparation, TaskEngine submission, and durable cancellation. A controlled paused-admission test failed before the gate and passed afterward. The gate is per occurrence, so unrelated jobs do not share a Manager-wide submission lock.

Final local verification on the complete change set: `go test ./internal/scheduler ./internal/jobs ./internal/jobs/sqlite ./internal/taskengine ./internal/app -count=1 -timeout=120s`, `go test -race ./... -count=1 -timeout=180s` (including `internal/architecture`), `go vet ./...`, `go build ./cmd/goultroid`, and `git diff --check` all passed. CI was not inspected. R5/R6 performance decisions remain open until a representative workload and pass-rate measurements exist.

### A3 unknown-effect recovery hardening

The expired-lease boundary above is now an explicit durable state transition in the production SQLite store. After restart, Jobs recovery atomically changes a `dispatched` occurrence with the latest `leased` or `running` attempt past `lease_until` to `blocked`. The transition checks attempt identity, epoch, latest attempt number, and current state in one SQLite write. A result commit that wins first remains authoritative; a late result after blocking loses fencing. The attempt budget is unchanged and no handler is resubmitted. Recovery can quarantine the occurrence even if its definition or handler is unavailable after restart.

`blocked` means the external effect is unknown and requires operator review. Jobs diagnostics expose the durable blocked count. `ListBlockedOccurrences` returns a bounded review page, and `ResolveBlockedOccurrence` accepts only `completed`, `failed`, or `cancelled` with a nonempty reason; the resolution and an `occurrence_resolved` outbox record commit in one transaction. Repeating the same reviewed resolution is idempotent; conflicting resolution and reopening for automatic retry are rejected. Ordinary schedule deletion preserves blocked work. This API is internal; no Telegram command or operator UI was added.

The scheduler compatibility path treats a blocked occurrence as a permanent failed row, including both a tracked claim and a reclaimed slot after restart. Redesigned schedules with `OverlapForbid` count blocked work as active, so a later slot cannot silently overlap an unknown effect. These transitions use existing state and outbox columns; no schema migration is required.

A fresh review found three bypasses and the follow-up regressions now cover them. Legacy `MisfireSkip` previously advanced a reclaimed recurring row before checking the old occurrence; it now checks that due slot first. Ordinary schedule cancellation previously changed blocked work to cancelled; it now leaves the blocked record for explicit review. A fast operator resolution previously let legacy reconciliation see only `completed` and advance the recurring row; the durable `occurrence_resolved` event now preserves unknown-effect history so the compatibility row still fails permanently. A failed read of the occurrence or its review marker now retains the existing legacy claim and due slot instead of releasing it for a new run. The extra occurrence read remains limited to the `MisfireSkip` branch rather than every legacy claim.

A combined forced-stop/SQLite-reopen fixture found and fixed a second bug: TaskEngine correctly marked a forced in-flight durable task as needing recovery, but the Jobs retry monitor interpreted its shutdown ticket as a final cancellation while the attempt remained `leased`. The monitor now leaves that nonterminal attempt for lease-expiry quarantine. The fixture forces shutdown while an uncooperative handler runs, advances the stored lease deadline, reopens SQLite, and verifies one blocked occurrence with no replay. It and the direct crash fixture passed 20 repeated runs. This does not claim exactly-once external effects: an old process could have completed a Telegram side effect before losing its durable acknowledgement. Automatic replay remains disabled for that ambiguous case; an idempotent replay policy would require a durable per-effect key and separate acceptance.

Final A3 follow-up verification: targeted unknown-effect scheduler regressions passed 20 repetitions; `go test -race ./... -count=1 -timeout=180s`, `go vet ./...`, `go build -v ./cmd/goultroid`, and `git diff --check` passed on the final tree. No live Telegram acceptance was run.
