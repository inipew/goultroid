## 1. P5 objective

P5 is the final cross-surface acceptance gate for the userbot UX redesign.

P5 is not a new runtime, callback protocol, executor, downloader, retry system,
or monitoring subsystem. The objective is to compose the already-implemented
P0-P4 authorities in one realistic lifecycle/resource workload and prove that
all logical state and owned resources return to their expected idle/terminal
state afterward.

The final workload must cover:

```text
normal userbot commands
  + Assistant navigation
  + callback burst
  + input session lifecycle
  + downloader cancel/retry
  + inline edit
  + plugin disable/reload
  + shutdown
  + resource settling
```

Only production defects exposed by this acceptance workload should be patched
during P5.

---

## 2. Standing constraints

These remain mandatory:

- run `gofmt` before every commit that changes Go;
- do not inspect or poll CI unless explicitly requested;
- do not create a second runtime, command registry, TaskEngine, RPC executor,
  callback protocol, downloader, retry engine, or lifecycle manager;
- physical long-running work continues through canonical TaskEngine admission;
- Telegram RPC continues through the shared RPC execution boundary;
- a2 interaction/runtime remains the canonical Assistant interaction authority;
- keep caches, interaction state, metrics cardinality, and resource tracking
  bounded;
- do not loosen actor/target/revision/generation validation to make acceptance
  pass;
- do not increase resource thresholds to hide a leak.

## 5. Important current findings

### 5.1 P8-I should be extended, not replaced

The existing P8-I test is already the correct process/resource skeleton.
P5-B should factor or extend its fixture rather than create another independent
resource framework.

### 5.2 The missing coverage is mostly composition

The repository already has focused regression coverage for:

- semantic response anchoring;
- actor/target/revision validation;
- one-shot bounded input claims;
- input expiry and cleanup;
- terminal session reclamation;
- downloader cancel/retry validation;
- progress coalescing;
- inline generation fencing;
- plugin generation replacement;
- TaskEngine zero-idle settling;
- bounded inline and RPC metrics.

P5-B therefore should not rewrite these primitives. It must prove they continue
to hold while several lifecycles overlap.

### 5.3 Old P8-H file is not an authority

`internal/assistant/p8h_reload_acceptance_test.go` is not present at this HEAD.
Do not recreate it merely because an older handoff mentioned it.

Current shell generation coverage is in
`internal/assistant/client/shell_interaction_test.go`, and P8-I already covers
runtime restart invalidation.

### 5.4 Peak state is currently under-recorded

P8-I samples process baseline and settled process state, while TaskEngine active
resource state is inspected separately.

P5-B should make the three lifecycle samples explicit:

```text
baseline
peak / active
settled
```

The peak sample is diagnostic evidence that the workload actually exercised the
expected ownership/resources before cancellation and shutdown.

Prefer one deterministic acceptance flow rather than many unrelated load tests.

```text

  |
  +-- normal outgoing userbot command

  |
  +-- downloader
  |     select -> run -> progress -> cancel
  |     retry -> controlled success/failure
  |
  +-- inline/self-inline
  |     typed action -> edit same inline target
  |
  +-- active peak snapshot
  |

  |     cancel tasks + interactions

  |     old token rejected
  |     fresh session works
  |
  +-- Close / shutdown
  |
  +-- GC + bounded eventual settle
  |
  `-- final logical/process snapshot
```

## 8. P5-B deterministic terminal invariants

The combined test should prefer exact logical invariants over loose process
thresholds.

Required settled state includes:

```text
interaction Inputs            == 0
closed/disabled Sessions       == 0
TaskEngine download Used       == 0
TaskEngine process Used        == 0
TaskEngine idle workers        == 0 after retirement
ResourceManager TotalActive    == 0 for touched owners
ResourceManager Leaked         == 0 for touched owners
old callback token             rejected
old generation callback        rejected
new generation session         succeeds
inline cache                   remains bounded
RPC metrics labels             remain bounded
```

Then retain the existing P8-I process envelope:

```text
goroutines <= baseline + 32
heap       <= baseline + 64 MiB
RSS        <= baseline + 128 MiB
```

Do not tighten these process thresholds without evidence. Logical zero-leak
assertions are the primary correctness signal.

## 9. P5-C rule when acceptance fails

For every P5-B failure:

1. reproduce the smallest failing lifecycle;
2. identify the existing ownership authority responsible for cleanup/state;
3. patch that authority instead of adding a parallel mechanism;
4. add a focused regression test near the owner;
5. run `gofmt` on changed Go files;
6. rerun the focused test;
7. rerun P5 acceptance.

Do not redesign unrelated components during P5.

## 10. P5-D final regression matrix

P5 can only be closed when the permanent final gate covers all of these:

| Scenario | Required terminal proof |
|---|---|
| Userbot command | response anchor reused, no retained worker/resource |
| Assistant navigation | deterministic Back/Home, Close reclaims session |
| Callback burst | bounded state, stale/wrong actor rejected |
| Input session | `Inputs == 0`, no orphan claim |
| Downloader cancel | physical task/resources released |
| Downloader retry | new attempt does not reuse stale physical task |
| Inline edit | inline target remains isolated from message target |
| Plugin disable | scope work + sessions cancelled |
| Plugin reload | old generation invalid, new generation usable |
| Runtime shutdown | runtime + TaskEngine close cleanly |
| Final settle | zero logical leaks + process envelope respected |

Only after this matrix passes locally, together with build/vet/targeted tests,
should the P0-P5 userbot UX redesign be called complete.
